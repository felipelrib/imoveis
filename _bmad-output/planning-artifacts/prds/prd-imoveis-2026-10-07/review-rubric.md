# PRD Quality Review — Imoveis — Deal Tracker (2026-10-07, v0.14 re-scope)

Calibration: solo-operator internal tool, brownfield, **chain-top** (feeds `bmad-architecture` → `bmad-create-epics-and-stories` → bmad-loop). Rigor bar is light on persona/UX formality and heavy on done-ness and downstream extractability. Reviewed against `prd.md`, `addendum.md`, the superseded 2026-08-05 PRD, `sprint-status.yaml`, and the cited code paths (all resolve at `main` 31995d8f).

## Overall verdict

This is a genuinely good PRD: it has a thesis (one operator, two named searches, agent-first, honest absence), every new FR carries testable consequences, decisions are stated as decisions with the reversals (FR-31, FR-35/36 redefinitions, personas retired) named and confirmation-tagged, and the brownfield grounding checks out line-for-line. What is at risk is done-ness at the seams between FRs — the Property↔Listing granularity of the `aluguel-2027` cost cap, the undefined soft score, and the four carried FRs (FR-33/34/37/38) that this wave will build but which have no acceptance consequences anywhere — plus one product decision the PRD has not noticed it is making: personal home/family coordinates committed to version-controlled `configs/`. None of these is critical; all four high findings are one-paragraph fixes that should land before `bmad-architecture` consumes the document.

## Decision-readiness — strong

Decisions read as decisions: §0 "the product's primary job moves from … to …"; FR-35 "Map travel-time bands … become a secondary UI consumer of this data, not the FR's definition"; §5 "Adopting Strata … is a spike with exit criteria, not an FR"; §4.2 explicitly records tracker truth over the change signal's "FR-30 done" claim. The addendum's *Alternatives considered* table names what was rejected for each theme, which is exactly what this dimension asks for. The two `[NOTE FOR PM]` callouts sit at real tensions (FR-30 status vs tracker; FR-31 deferral reversal), not at safe checkpoints. §9's open questions are real — Q2 (transit provider vs NFR-1) and Q3 (Epic 2 vs v0.14 ordering) have genuine cost on both sides and are routed to the right owner/moment.

Two things a decision-maker cannot judge from the text: whether the Strata spike is even feasible on the operator's host (§6.4 states the model's ≥ 32 GB RAM / ~80 GB NVMe need and Q6 says it "may rule it out quickly", but the PRD never states the host's RAM or free NVMe — the GPU is named in §1, the rest is not), and where the Anchor coordinates will physically live (see finding below — the PRD treats it as config hygiene, NFR-2, but it is a privacy decision that contradicts §2.1's contextual JTBD).

### Findings
- **high** Anchors are personal home/family coordinates in version-controlled config (§3 *Anchor*, FR-35 consequence 1, NFR-2, §2.1 Contextual JTBD) — The glossary says Anchors (igreja, casa da Nala, casa da mãe, current home) are "versioned beside the Search Profiles" in `configs/` under version control, and NFR-2 says "versioned files in `configs/`". Every `finish-feature.sh` pushes `main` to origin, so the operator's home, mother's and partner's addresses leave the box — in tension with §2.1 "Everything on the operator's machine; … listing data never leaves the box". §9 Q2 notices the egress risk for *property* coordinates under a cloud routing provider but not for Anchors, which are more sensitive. *Fix:* decide and state it: Anchors and Search Profiles load from a git-ignored `configs/*.local.yaml` (schema committed, values not) **or** the repo is accepted as private and the PRD says so under §5/NFR-3. Add a sentence to Q2: "a cloud provider also receives Anchor coordinates (home), not only property coordinates."
- **medium** Spike feasibility cannot be judged — host specs absent (§6.4 *Bounds*, §9 Q6) — "host needs ≥ 32 GB RAM (64 recommended; model loads 35–55 GB)" is stated as a requirement; the operator host's RAM/NVMe is never stated, so "may rule it out quickly" is unverifiable from the document. *Fix:* add the host's RAM and free NVMe to the §1 hardware sentence (next to "AMD RX 7900 XT 20 GB"), and turn Q6 into a two-line go/no-go pre-check ("if host RAM < 32 GB → defer spike, FR-39/40 baseline on qwen2.5vl:7b").
- **low** "Default here:" answers in Q4, Q6, Q7 are decisions pending veto, not open questions (§9) — Each gives a default the PRD proceeds on. That is fine, but downstream will not know whether to block on them. *Fix:* relabel those three as "Decided unless overridden by <date/pass>" so `bmad-architecture` treats them as inputs, and keep Q1, Q2, Q3, Q5 as the truly blocking set.

## Strategic coherence — strong

The thesis is explicit and the feature set is derived from it in §4.3's description paragraph: hold the searches as objects (FR-41) → know the Attributes they depend on (FR-39) → know what a flat costs (FR-31) → know how far it is from the operator's life (FR-35) → expose quality as facets (FR-36) → produce decision data (FR-40) → through an interface an agent can read (FR-42). §6.3 orders the wave foundation → decision data → agent surface, and FR-38 is explicitly "UI-only and lowest priority". SMs validate the thesis (SM-1 decision latency, SM-2 attribute truth, SM-5 visit yield) rather than activity. Scope kind is problem-solving and the scope logic matches.

The one place the arc breaks is UJ-6: the compra-2028 journey's climax is "a market read, not a shortlist: price/m² by neighbourhood for the fitting cohort … which neighbourhoods keep the Anchors within acceptable minutes" — and no FR produces a cohort aggregate. FR-30 (Epic 2, in flight) is a per-Property percentile; FR-42 lists per-Property Fit rows. §6.5 only waives Fit-status *history* analytics. The second of the two searches the product exists for has no capability behind its headline answer.

### Findings
- **high** UJ-6's climax has no FR behind it (§2.3 UJ-6 vs FR-30/FR-42, §6.5) — "price/m² by neighbourhood for the fitting cohort" and "which neighbourhoods keep the Anchors within acceptable minutes" require a per-profile aggregate grouped by neighbourhood; nothing in FR-39–FR-42 or FR-30 produces one, and the §6.5 waiver covers only "how many fits per week". *Fix:* either (a) add an FR-42 consequence — "a per-profile cohort summary endpoint returns, per neighbourhood: fitting-Property count, price/m² median and quartiles, and median car/transit minutes per Anchor" — or (b) state in §6.5 that the agent derives the market read from the Fit-status listing and raise the FR-42 one-call bound accordingly (the ≤ 5 s / 200-row assumption will not hold for a BH sale cohort). Option (a) is the honest one given UJ-6 is one of the two searches.
- **medium** Wave size is not prioritized for a single operator (§4.3, §6.3) — v0.14 carries seven new/redefined FRs, four carried FRs, the FR-32 Alertas-panel/desktop-push leftover, the Strata spike, and (per Q3) possibly Epic 2's five remaining stories. The only internal priority stated is "FR-38 lowest". Without tiers, the epics pass will have to invent them. *Fix:* add a two-tier split to §6.3: **Must** (FR-41, FR-39, FR-31, FR-35 car mode, FR-40, FR-42, FR-33/34 for liveness) / **Should, first to slip to v0.15** (FR-35 transit mode if Q2 lands on local GTFS, FR-36, FR-37, FR-38, Alertas panel + push). Record the slip rule in the exit criteria.

## Done-ness clarity — adequate

The new FRs are well above the bar: FR-39's five consequences include a fixture-set threshold, a provenance-precedence rule, and a photo-gate degradation rule; FR-31 nails periodicity and zero-vs-unknown; FR-35 enumerates the `unknown` reasons and bans km; FR-40 distinguishes "not computed yet" from "computed, not available"; FR-42 bounds latency with numbers and tags them as planning assumptions. Adjective scan is clean — "within the operator's patience" is immediately bounded, "trustworthy answer" appears only in the description paragraph. The exit criteria are measurable.

The gaps are at the joints. The `aluguel-2027` cap is a hard constraint on a **Property** (FR-41) computed from a figure that exists per **rent Listing** (FR-31 "per rent Listing") — the PRD's own Vision ("one physical home, one Property, many Listings") guarantees Properties with two totals, one of them possibly `bundled` or incomplete, and no rule says which decides. "Soft score" is sorted on (FR-42), bundled (FR-40) and ranks within status (FR-41) but is never defined. And FR-33/34/37/38 — which this wave *builds* — inherit prose-only definitions: the 2026-08-05 §4.5 has no per-FR consequences, only a one-sentence wave exit criterion, so "exit conditions as stated in the 2026-08-05 PRD §4.5" resolves to very little.

### Findings
- **high** Property-level Fit vs Listing-level Total Monthly Cost — no aggregation rule (FR-41 table + consequence 4, FR-31 definition + consequence 4) — A Property with a QuintoAndar Listing at R$ 3.900 complete and a ZapImóveis Listing with IPTU `unknown` is either `fits` or `fits-pending-verification` depending on an unstated choice. Same gap for the sale carrying-cost context. *Fix:* add to FR-41 consequences: "For a cost cap the Property's figure is the **lowest complete** Total Monthly Cost among its active rent Listings; if no Listing has a complete total the Property is `fits-pending-verification`; the deciding Listing id is recorded in the FR-40 bundle and a cheaper incomplete Listing is surfaced as 'verify'." Mirror a one-line note in FR-31.
- **high** FR-33/34/37/38 have no testable consequences anywhere (§4.3 "FR-33, FR-34, FR-37, FR-38 — unchanged"; 2026-08-05 §4.5) — The prior PRD defines them in prose only (cooldown "per-listing", budget "modest", drift "turns the chip amber"), with no Consequences blocks; the §4.5 exit criterion is one sentence for the whole wave. They are planned scope of **this** PRD's target and the first things epics will carve. *Fix:* give each 2–3 consequences here (FR-33: cooldown and global daily budget as config keys with defaults; 403/Cloudflare/timeout → `unknown`, never `gone`, never bumps freshness. FR-34: gone only after N consecutive **successful** runs without the Listing; resurrection annotates price history and clears gone in one transaction. FR-37: deviation threshold expressed against both baselines; reason string enumerates the signal (`duration`, `yield`, `finished-early`). FR-38: N most-recent values per picker, de-duplicated, local-only) — or, if that is deliberately delegated, say so with a `[NOTE FOR PM]` so epics knows it owns the ACs.
- **medium** Soft score undefined (FR-41 consequence 5, FR-40 "soft-preference scores", FR-42 "sortable by soft score") — Direction, weighting, and `unknown` handling are unspecified; a story cannot test "orders Properties within a status". *Fix:* one consequence under FR-41: "each soft preference evaluates to satisfied / not satisfied / `unknown`; soft score = satisfied ÷ (satisfied + not satisfied); `unknown` never lowers it; ties break by Total Monthly Cost ascending" — or delegate explicitly to architecture with a `[NOTE FOR PM]`.
- **medium** "2 bedrooms" — exactly two or at least two? (FR-41 table, UJ-5) — A hard constraint must be arithmetic. UJ-5 says "second bedroom suitable as home office", implying a three-bedroom flat would also fit. *Fix:* write `bedrooms ≥ 2` (or `== 2`) and `parking ≥ 1` in the table; same for compra-2028's "3–4" (inclusive range).
- **medium** Facet value type and seed derivations undefined (FR-36) — "facets are filterable" but a facet value is never typed (boolean? score? tri-state?), and how `seguro` / `reformado` / `silencioso` are derived from the FR-24 sub-scores, FR-26 flags and FR-39 Attributes is not stated, so consequence 2 ("states what produced it") has nothing concrete to test against. *Fix:* define facet value as `present | absent | unknown` with provenance (consistent with NFR-10), and add a three-row seed table to the addendum (facet → source signal → threshold/normalization).
- **medium** Departure-time assumption has no value (FR-35 definition, glossary *Travel time*) — Transit minutes vary 2× by hour; "with a departure-time assumption" without a default makes SM-4 and the Dossier numbers unreproducible. *Fix:* name the default in FR-35 (e.g. "weekday 08:00 local for both modes; configurable per Anchor") and require it in the stored shape the addendum already sketches.
- **low** `out-of-scope` on geography is not testable (glossary *Fit status*, FR-41) — "wrong listing type or geography" needs a predicate. *Fix:* "geography = Property city equals the profile's city, or Property point within the union of the profile's neighbourhood polygons (FR-22)".
- **low** UJ-6 "lower-cadence intent" has no Search Profile field (§2.3, FR-41 definition) — FR-41 lists listing type, geography, hard, soft, horizon. *Fix:* add an optional `cadence` to the profile (affects only recheck/alert frequency) or drop the phrase from UJ-6.
- **low** Sale-side FR-31 has no consequence (FR-31 "Sale Listings carry condo fee and IPTU/month as carrying-cost context, not a total") — *Fix:* one line: "a sale Listing exposes `condo_fee_monthly` and `iptu_monthly` with the same `unknown`/periodicity rules; no total is computed".
- **low** "unfurnished" hard constraint vs ZapImóveis — The addendum's coverage table shows Zap has no furnished field, so every Zap-only aluguel candidate will be `fits-pending-verification` by construction. Correct per the semantics, but SM-3 and the exit criteria do not anticipate it. *Fix:* add to NFR-6/SM-3: "pending-verification share per platform is a reported figure", so the number is expected rather than alarming.
