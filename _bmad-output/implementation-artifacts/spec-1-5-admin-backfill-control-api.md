## Intent

**Problem:** Story 1.3 hardened the backfill runner into a lease-governed, pausable, resumable core with a published control state, but the only way to drive it is `scripts/dev/backfill_gemma.py` on the operator's shell — FR-28's "graduates from `scripts/dev` to an operator-facing operation" is unmet, and story 1.6's Operações card has no API to talk to. An active run is likewise invisible to anyone not reading a terminal: nothing in `src/api/` exposes the lease holder, the published state, today's budget consumption or the checkpoint.

**Approach:** Add an auth-gated `/admin/backfill` control surface (`status`, `start`, `pause`, `resume`) that constructs the *same* story-1.3 Redis primitives against the *same* keys — a control plane, never a second runner or a second quota consumer. Because the API container carries no `GEMINI_API_KEY` and the runner is host-side by design, "start" is a **start request** (a new `BackfillControl` level key) that a new host-side CLI supervisor mode (`--serve`) consumes to launch the ordinary `--continuous` run; the API refuses with 409 when the lease is already held and reports honestly whether any runner is present to honor the request.

## Boundaries & Constraints

**Always:** The API only ever *reads and requests* — it never enriches, never spawns a runner process, never touches the DB, and never beats the `:active` heartbeat (a beating heartbeat blocks `migrate-primary.sh`). One control path: every key access goes through the story-1.3 primitives in `src/core/backfill_runner.py`, which stays framework-free and injectable (no `adapters`/`api`/DB import — AD-1). Routes live behind the router-level `verify_admin_access` gate and every mutation is recorded via `log_audit_action` (AD-6). Unexpected failures go through `raise_api_error` so no internals leak; 4xx details are operator-actionable. New wire shapes are Pydantic response models in `src/api/schemas.py` with `response_model=` on the route, and the state enum on the wire stays `idle|running|paused|backing-off|blocked` (English wire enum, pt-BR rendering is story 1.6). `start` clears stale pause/stop requests exactly as the CLI does and reports what it discarded.

**Block If:** Nothing. The intent is resolved from epics.md story 1.5, epic-1-context.md (AD-6/AD-8/AD-13) and the shipped story-1.3 code. No operator-only external action is required to *land* this story; the operator-visible workflow change (a host-side `--serve` supervisor must be running for the UI's start button to launch a run) is documented, not performed mid-story.

**Never:** Do NOT add a stop endpoint (the epic's surface and UX-DR5's card are start/pause/resume; CLI `--stop` stays the way to end a run). Do NOT add coverage, throughput, ETA or any DB-derived telemetry — that is story 1.4, and the runner's Redis state must never become a second progress metric (FR-29). Do NOT build UI (story 1.6). Do NOT run `run_backfill`, a Celery task, or a subprocess from an API request thread (AD-4/AD-10), and do NOT put the cloud key in the API container. Do NOT change `run_backfill`, the lease/budget/checkpoint semantics, `migrate-primary.sh`, the primary docker stack, AI prompts or clients. Do NOT fix open ledger items (DW-8..DW-26) — in particular DW-20 (state decays to `idle` under one slow row) is *worked around* by reporting the lease separately, not fixed here.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Status, nothing running | no lease, no state key | 200: `state=idle`, `active=false`, `lease=null`, `runner_present=false`, budget/checkpoint/pacing populated, `pending_requests=[]` | No error |
| Status, run live | lease held, state `running` | 200: `active=true`, `lease.owner/acquired_at/last_seen/seconds_since_last_seen`, `heartbeat_active=true` | No error |
| Status, state decayed under a slow row (DW-20) | lease held, state key expired | 200: `state=idle` **and** `active=true` — the lease, not the state key, is the liveness signal | No error |
| Status, requests pending | pause key set, start key set | 200: `pending_requests=["pause"]`, `start_requested_at=<iso>` | No error |
| Start, lease free | no lease | 202: `requested=true`, `already_requested=false`, `runner_present`, `discarded_requests=[…]`; start key set; audited | No error |
| Start, lease held | lease held by CLI or prior start | 409 naming the holder (owner + how long it has held it + last seen); no start key written; audited as refused | `HTTPException(409)` |
| Start, already requested | start key already set | 202 with `already_requested=true`; the original `requested_at` is preserved | No error |
| Start clears stale requests | pause+stop keys set, lease free | pause/stop deleted, `discarded_requests=["pause","stop"]` in body and audit payload | No error |
| Pause / Resume | any state | 200 with the refreshed status body; pause sets the pause level, resume clears pause **and** stop (`request_resume`) | No error |
| Any endpoint, Redis unreachable | `get_redis()` raises / times out | 500 with generic detail via `raise_api_error`; full exception logged server-side only | Never leaks internals |
| Unauthenticated / non-admin | no `X-API-Key`, bad key | 401 / 403 from the router-level gate before any handler runs | No Redis touched |
| Supervisor consumes a start request | `--serve` idle, start key set | key consumed atomically, ordinary `--continuous` run launched, supervisor returns to waiting afterwards | A second supervisor loses the lease race → prints refusal, keeps serving |
| Supervisor idle | no start request | beats `<prefix>:supervisor:active`, sleeps `control_poll_seconds`, no lease taken, no DB touched | No error |
| Stale start request | key older than its TTL | expires on its own — a start never fires days later (contrast DW-23) | No error |

**Acceptance Criteria:**
- Given a backfill holding the lease, when `POST /admin/backfill/start` is called, then the response is 409 naming the active run (owner and how long it has held the lease), no second runner is created, no start request is written, and the refusal is audited.
- Given a live or idle backfill, when `GET /admin/backfill/status` is called, then state, liveness, lease holder, pending requests, today's budget consumed/remaining and pacing come back from the same Redis keys the CLI uses, with no DB query and no coverage/ETA figure invented.
- Given the admin surface, when any backfill endpoint is called without admin credentials, then it is refused by the router-level gate before any Redis access, and every successful mutation appears in the `admin_audit` trail.
- Given a host-side `--serve` supervisor and a start request from the API, when the supervisor polls, then it consumes the request exactly once and runs the ordinary continuous backfill under the shared lease and pacer — no second quota consumer, no cloud key in the API container.
- Given the API schema changed, when the story completes, then `bash scripts/agent/validate.sh backend` is green including `src/tests/contract/`, and `src/core/` still imports nothing from `adapters`/`api`.

## Design Notes

**Why start is a request, not an execution.** The runner needs `GEMINI_API_KEY`, which lives only in the operator's host shell — `docker-compose.yml` gives the api/worker containers no such variable, and NFR-3 keeps cloud keys env-only. An API that spawned `run_backfill` in-process would also be a second driver inside a request-serving process, contradicting AD-4/AD-10 and the multi-day run profile. So the endpoint writes a level key and a host-side supervisor picks it up — the same shape as pause/stop, which story 1.3 already proved out. `runner_present` (supervisor heartbeat **or** lease held) is reported so story 1.6 can tell the operator that nothing is listening rather than showing a button that silently queues into the void.

**Liveness is the lease, not the state key.** DW-20 is open: a single in-flight row longer than the 120s state TTL makes a live run read back as `idle`. The status contract therefore exposes `state` (what the runner published) and `active` (does anyone hold the lease) as separate fields, and story 1.6 renders liveness from `active`.

**Snapshot shape (the wire contract story 1.6 codes against):**

```python
{"state": "running", "active": True, "runner_present": True, "heartbeat_active": True,
 "migration_active": False, "pending_requests": ["pause"], "start_requested_at": None,
 "lease": {"owner": "host:4711", "acquired_at": "…", "last_seen": "…", "seconds_since_last_seen": 3.1},
 "budget": {"limit": 14000, "consumed": 512, "remaining": 13488, "seconds_until_reset": 43120.0},
 "checkpoint": {"last_property_id": "…", "last_run_date": "2026-08-11", "processed_total": 1234},
 "quarantined": 7,
 "pacing": {"requests_per_property": 3, "rpm_limit": 30, "concurrency": 1, "tpm_limit": 16000}}
```

**Why the start key expires in an hour.** Pause/stop are 7-day levels because a runner must observe them whenever it wakes. A start is an intent to begin *now*: DW-23 records how a self-expiring level surprises an operator, and the mirror hazard — a week-old start request firing a multi-day cloud spend unattended — is worse. One hour is far longer than the supervisor's poll and short enough that a forgotten request dies quietly; `start_requested_at` keeps it visible meanwhile.
