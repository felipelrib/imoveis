# Backfill Runner Hosting — a committed, supervised home for the consumer

> Feature branch: `feat/v0.13-s3.1-backfill-runner-hosting` · Story: `v0.13-s3.1` · Status: implemented

## Problem

`POST /admin/backfill/start` only **records** a request. The thing that consumes
it is `scripts/dev/backfill_gemma.py --serve`, and nothing kept that alive: no
unit was committed anywhere, no installer existed, and the only guidance was an
example systemd unit pasted inside story 1.5's feature doc. A supervisor that is
simply never started leaves the Operações dashboard's Start button permanently
un-actionable — FR-28's stated outcome unmet, filed as **DW-27**.

That example unit was also incomplete as an env contract:

- no `DATABASE_URL` — `DatabaseConfig` defaults to database `imoveis`, while the
  primary stack's database is `realestate`, so a host-side run would connect to
  a database that does not exist;
- no `REDIS_URL` — a workspace publishing Redis on a non-default port would talk
  to the wrong Redis;
- `GEMINI_API_KEY` was absent from `.env.local.example` entirely;
- the default stop timeout could `SIGKILL` a draining run mid-property, and
  without `StartLimitIntervalSec=0` a burst of early exits could park the unit
  in `failed` — the silent-button failure, one layer down.

## Approach

- **A committed systemd unit template + an operator installer**, recorded in
  [ADR 0006](../adr/0006-backfill-runner-hosting.md). The runner stays exactly
  where it already runs in production: host-side, as the operator's own user,
  out of the repo `.venv`, against the primary stack's *published* ports.
- **No runner, admin or domain code changes.** `ExecStart` points at
  `scripts/dev/backfill_gemma.py --serve`; a unit test pins that target to a
  file that must exist, which is what actually stops the path from drifting.
- **Rejected: a dedicated compose service** — it would put `GEMINI_API_KEY` in a
  container that deliberately has none, `scripts/` is not copied into
  `Dockerfile.worker`, and starting it is a compose action against the
  inviolable primary project.
- **Rejected: promoting the runner out of `scripts/dev`** — 2117 lines and 85
  CLI tests, and an installed console script would supervise nothing by itself.
- **Secrets are env-only (NFR-3).** The unit reads the git-ignored `.env.local`
  via `EnvironmentFile=`; the installer checks that variables are *set* and
  never reads back, prints or logs a value — only names.
- **Unattended recovery (AD-13 / NFR-6):** `Restart=always`, `RestartSec=10`,
  `StartLimitIntervalSec=0`, `WantedBy=multi-user.target`. **Drain-safe stop:**
  `KillSignal=SIGTERM` with `TimeoutStopSec` ≥ the 900 s lease TTL (the
  installer raises it if `backfill.lease_ttl_seconds` ever grows).
- **`After=network-online.target docker.service` without `Requires=`** — Docker
  Desktop hosts have no `docker.service` unit at all, and the supervisor's poll
  loop already retries Redis/DB failures.
- **No double-start:** `--serve` never acquires the lease, request consumption
  stays the existing atomic `GETDEL`, and one unit name means a re-install
  upgrades in place instead of adding a second heartbeat holder.

## How to Test

```bash
bash scripts/agent/validate.sh fast
```

Unprivileged manual checks (safe anywhere, no sudo, no containers):

```bash
# Rendered unit — no @@placeholder@@ survives, ExecStart points at the runner
bash scripts/install-backfill-runner.sh --print --user u --python /bin/sh --env-file /tmp/e

# Preflight only — names any missing variable, never its value
bash scripts/install-backfill-runner.sh --check
```

Operator (privileged, **not** performed by an agent):

```bash
bash scripts/install-backfill-runner.sh          # sudo install + enable + restart
systemctl status imoveis-backfill-serve
journalctl -u imoveis-backfill-serve -f
```

Then, with the primary stack up: press Start in Operações (or
`POST /admin/backfill/start`) and confirm `runner_present: true` and a run
beginning with no manual host-side step.

## Notes / Follow-ups

- **Operator-visible install/upgrade step.** `bash scripts/install-backfill-runner.sh`
  must be run **once per host** (and again after a repo move, a rebuilt `.venv`
  or an upgrade — it rewrites the same unit name in place). Uninstall:
  `bash scripts/install-backfill-runner.sh --uninstall`. Run it from the
  **primary checkout**; it refuses from a linked git worktree, whose path is
  disposable.
- **`.env.local` contract:** `GEMINI_API_KEY` and `DATABASE_URL` are required
  (`DATABASE_URL` because the config default DB name is not the primary
  `realestate`); `REDIS_URL` is required whenever `REDIS_PORT` is not 6379. The
  installer fails on the first two and warns on the third.
- **Cloud-routing precondition:** `--serve` validates scope + AI routing + the
  cloud key *before* its poll loop, so with the shipped all-local
  `ai.enrichment_routing` the unit exits at startup and restarts every 10 s.
  The installer warns when no task class is cloud-routed.
- **BUG (High)**: the operator instructions tell the operator to edit
  `configs/app_config.yaml` — which breaks the merge gate. Setting
  `ai.enrichment_routing.{visual,sentiment,deal_verdict}: gemma` in that
  committed file fails `src/tests/unit/test_config.py::test_enrichment_routing_default_all_local`,
  which pins story 1.1's own AC ("the default shipped config routes every task
  class to a local backend — NFR-1"). Committing it turns `validate.sh fast`
  red for every later story; leaving it uncommitted breaks `bmad-loop validate`'s
  clean-worktree check. **Fix hint:** the correct enablement is per-host env in
  `.env.local` (which the unit already reads via `EnvironmentFile=`) —
  `IMOVEIS_AI__ENRICHMENT_ROUTING__{VISUAL,SENTIMENT,DEAL_VERDICT}=gemma`.
  `_apply_env_overrides` merges these leaf-wise over the YAML map, so it stays
  total (story 1.1's validator requires that), the scalar `ai.backend` stays
  local so the live path is untouched (AD-13), and nothing enters git. Verified
  2026-08-12: backfill resolves `gemma` for the three classes, live resolves
  `ollama`, `embedding` stays local even for backfill. Update the operator docs
  (`docs/setup.md`, `docs/deployment-guide.md`, `.env.local.example`) and teach
  `routing_has_cloud_backend()` about the env override — it awk-greps the YAML
  only (`scripts/install-backfill-runner.sh:247`), so the correct configuration
  currently reports a false `[WARN]`. Ledgered as `DW-31`.
- **`runner_present` is not the unit's state.** The admin API derives it from
  Redis (lease held **or** the `backfill:gemma:supervisor:active` heartbeat), so
  a unit that is `active` but wedged still reads as absent there. `--status`
  shows the *unit's* state and prints that difference as a prose reminder — it
  does not read Redis or the lease, so it cannot tell you a unit is wedged. It
  does exit non-zero when the unit was never installed (the DW-27 state).
- **The agent could not verify the privileged path.** Installing to
  `/etc/systemd/system`, `daemon-reload`, `enable` and `restart` are operator
  actions; only rendering and the preflight branches are covered by tests.
- Related: `DW-27` (closed by this story), story `v0.13-s1.5` (the control API
  whose inline unit example this supersedes), stories 3.2–3.4 (runner internals,
  untouched here).
