# Periodic tasks are not blocked by scrapes — a third queue with its own worker, expiring housekeeping ticks and one scrape at a time per platform

> Feature branch: `feat/v0.14-s1.18-periodic-tasks-not-blocked-by-scrapes` · Story: `v0.14-s1.18` · Status: implemented; the primary is not rebuilt yet (see Operator steps)

## Problem

Every Celery task that is not AI work was routed to the queue `scrapers`, including every task the beat schedules. The worker of that queue (`worker_scraper`) has two slots. A scrape can hold a slot for hours, so two scrapes stop everything else on the queue.

Measured on the primary, read-only, on 2026-10-08 at 19:40 UTC. Every time in this document is UTC. The backlog was read several times that evening while it grew, which is why other sections quote 11,400, 11,600 and 11,716 for it:

| What | Value |
|---|---|
| Messages waiting on `scrapers` | 11,640 |
| Messages waiting on `periodic` (did not exist yet) | 0 |
| Running tasks | two `tasks.scrape_listings`, received at 16:34 and 16:36, both still running at 19:41, one on each worker process |
| What both were doing | fetching QuintoAndar price windows: the same scrape, twice at once |
| Other platforms' scrapes | finished in 38 s and 93 s |
| A task id received twice in 48 h (before the restart at 19:59) | none |

A sample of the first 400 waiting messages (DW-63) was 245 `tasks.snapshot_pipeline_metrics`, 121 `tasks.monitor_queues`, 23 `tasks.evaluate_watchlist_alerts` and 12 `tasks.scrape_listings`.

Effect: the saved-search matcher, due every 15 minutes, had not run once two hours after the Story 1.9 rebuild. The beat kept publishing every tick, none carried an expiry, so the backlog only grew.

Three separate defects produce this:

1. Short periodic work shares capacity with scrapes.
2. A missed tick of an idempotent task is kept for ever and replayed later.
3. The beat publishes a scrape of a platform while a scrape of that platform is already queued or running, so two of them run at once and do the same work.

## Approach

### 1. Three queues, one worker each

| Queue | Worker service | Slots | Tasks |
|---|---|---|---|
| `scrapers` | `worker_scraper` (also consumes the default `celery`) | 2 | `tasks.scrape_listings`, and the operator-triggered `tasks.backfill_listing_costs` |
| `ai` | `worker_ai` | 2 | `tasks.ai_enrich`, `tasks.embed_property`, behind the GPU semaphore (unchanged) |
| `periodic` | `worker_periodic` (new) | 2 | every other task |

The queue names are defined once, in `src/adapters/queue/celery_app.py` (`QUEUE_SCRAPERS`, `QUEUE_AI`, `QUEUE_PERIODIC`, `ROUTED_QUEUES`). Every other module imports them.

Tasks on `periodic` and whether a missed tick expires:

| Beat entry | Task | Interval | `expires` |
|---|---|---|---|
| `monitor-queues` | `tasks.monitor_queues` | 60 s | 60 s |
| `snapshot-pipeline-metrics` | `tasks.snapshot_pipeline_metrics` | `pipeline_metrics.snapshot_interval_sec` (30 s) | same as the interval |
| `evaluate-watchlist-alerts` | `tasks.evaluate_watchlist_alerts` | 300 s | 300 s |
| `match-saved-search-new-matches` | `tasks.match_saved_search_new_matches` | `alerts.new_match.match_interval_minutes` (15 min) | same as the interval |
| `recheck-listing-availability` | `tasks.recheck_listing_availability` | `scraping.availability_recheck.interval_minutes` (6 h) | same as the interval |
| `refresh-neighbourhood-amenities` | `tasks.refresh_neighbourhood_amenities` | `osm_amenities.interval_hours` (168 h) | same as the interval |
| `refresh-transit-proximity` | `tasks.refresh_transit_proximity` | `transit.interval_hours` (168 h) | same as the interval |
| `refresh-neighbourhood-access` | `tasks.refresh_neighbourhood_access` | `neighbourhood_access.interval_minutes` (24 h) | same as the interval |
| `refresh-listing-claim-stats` | `tasks.refresh_listing_claim_stats` | `listing_claim_stats.interval_hours` (24 h) | same as the interval |
| `send-saved-search-new-match-alerts` | `tasks.send_saved_search_new_match_alerts` | hourly | none |
| `send-daily-digest` | `tasks.send_daily_digest` | daily 08:00 | none |
| `send-top-deals-digest` | `tasks.send_top_deals_digest` | weekly | none |
| (not scheduled; published by the persist path) | `tasks.send_price_drop_alert` | — | none |
| `scrape-<platform>` (on `scrapers`) | `tasks.scrape_listings` | per platform | none |

Why a queue and not only an expiry: an expiry bounds the backlog, but the task still waits for a slot a scrape holds for hours, so the matcher would be discarded every time instead of running. Separate capacity is what makes a periodic task run within its own interval. The expiry only keeps a slow or restarted periodic worker from replaying history.

Why the sender and the digests carry no expiry: a duplicate run is harmless (the sender claims the day per search under a row lock, the digest drains a list) and a discarded run is not. Celery checks `expires` when a worker receives the message, so a worker behind by more than the interval would discard every run.

Why `backfill_listing_costs` stays on `scrapers`: it is started by the operator, walks the whole corpus and would hold a periodic slot for its whole run. `send_price_drop_alert` moves to `periodic`: it is short, and an alert should not wait for a scrape.

The three admin triggers that named a queue explicitly (`POST /admin/availability/recheck`, `/admin/neighbourhoods/access/refresh`, `/admin/neighbourhoods/listing-claims/refresh`) now name `QUEUE_PERIODIC`. An explicit `queue=` overrides `task_routes`, so leaving `"scrapers"` there would have put those tasks back behind scrapes.

Rule for a new task: route it to `periodic` unless it is a scrape or GPU work. Give its beat entry `expires` (through `_expiring(...)` in `build_beat_schedule`) when the next run covers a missed one. GPU work stays on `ai` only.

### 2. One scrape at a time per platform and scope

`src/adapters/queue/scrape_single_flight.py`. Two Redis leases per platform and scope, both `core.backfill_runner.BackfillLease` (atomic `SET NX EX`, renew and release only by the holder's token), both with the Celery task id as token:

| Lease | Key | Taken by | TTL | Released |
|---|---|---|---|---|
| queued | `scrape:single_flight:<platform>:<scope>:queued:lease` | whoever publishes the message (beat, `POST /scrape`) | 3 h | when the task starts (also when it starts as a duplicate and does not run), when the publish fails, when the task finds scrapers paused, or when its platform is unknown |
| running | `scrape:single_flight:<platform>:<scope>:running:lease` | the task, when it starts | 2 h, renewed at most once a minute from the item loop | when the task ends, success or failure |

Scope: a scheduled scrape passes no checkpoint and has the scope `default`. A manual trigger always carries a checkpoint (at least `scrape_type`), so its scope is a digest of that checkpoint. A manual scrape and the scheduled scrape of one platform do not block each other, as before this story.

What each side does:

| Situation | Behaviour |
|---|---|
| Beat tick, nothing queued or running | takes the queued lease with a new task id, looks at the running lease once more (a task that starts in between is then reported as `running` and the reservation handed back), and publishes the message with that id. If the publish fails, the lease is released. |
| Beat tick, a scrape is queued | publishes nothing, logs `scrape_enqueue_skipped` with `reason: queued`. The entry still advances to its next tick. |
| Beat tick, a scrape is running | publishes nothing, `reason: running`. |
| `POST /scrape`, same platform and scope queued or running | answers 200 with `status` `already_queued` or `already_running` and the `task_id` of the holder. Publishes nothing, logs `scrape_enqueue_skipped`. |
| Task starts and holds the reservation | takes the running lease, then releases the queued lease (in that order, so the platform is never seen free in between), scrapes, releases the running lease in `finally` (before Celery schedules a retry). |
| Task starts, another execution is running | returns `{"status": "skipped", "reason": "already_running", "platform": ...}` before a scraper is created or a database session is opened. It does not touch the other run's leases or its status key. |
| Task starts with no reservation (a message published before this story) | takes the running lease itself and runs. |
| Scrapers are paused (`workers:scrapers:paused`) | releases its own reservation, then retries in 120 s as before. |
| A run goes longer than 2 h | keeps its lease by renewing. If a renewal finds the lease gone, the task logs the warning `scrape_single_flight_lost` once and continues. A Redis error during a renewal is logged as `scrape_single_flight_renew_failed` and does not stop the scrape. |
| The process is killed | nothing releases the lease. It expires by its TTL, and the first tick after that queues a scrape. |

Two leases and not one, because "a message is waiting" and "a scrape is running" are different facts. The running lease is what stops a second delivery from scraping the same windows again. A second delivery is either a message from before this story or, under `task_acks_late`, a redelivery of the same task id after the broker's one-hour visibility timeout. For that second case the token of the duplicate equals the token of the running task, so the task object records that it took the lease itself and never releases on a token match alone.

#### What a worker restart does

| Stop | Running lease | The redelivered scrape |
|---|---|---|
| Graceful stop (`restart.sh`, `docker stop`: SIGTERM, then SIGKILL after 10 s) | Released at once by a shutdown hook: `tasks.py` listens to Celery's `worker_shutting_down` and releases the running leases of the scrapes that worker is executing (`release_running_leases_of`): the lease's recorded owner must be that worker node and its token must be the id of one of the worker's active `scrape_listings` requests. The release is the lease's token compare-and-swap; any other lease is left alone. | Starts again when the broker gives the message back: one hour after it was first delivered (the Redis visibility timeout), so at once if the scrape had already run for more than an hour. The lease is free in the meantime, so the next beat tick can queue a scrape of the platform. |
| Hard kill (out of memory, power loss, no SIGTERM) | Stays until its TTL: up to 2 h. | The message with that task id returns `skipped` when it is redelivered. The platform's scheduled scrape waits for the TTL. |

The hook exists because the task's `finally` does not run in a killed process. The owner recorded on the running lease is the worker node name (`self.request.hostname`). A node name alone is not an identity (workers started by hand without `-n` all call themselves `celery@<host>`), which is why the hook also matches the task id: a worker that runs no scrape releases nothing and does not read Redis.

Why the release happens when the stop is requested and not when the task ends: Celery sends `worker_shutting_down` from the signal handler of the main process, then waits for the running tasks (warm shutdown). Under `docker stop` the process is killed ten seconds later and the task never ends by itself, so "when the task ends" would never come; that is the case the hook is for. The cost is that the scrape holds no lease from the signal until it is killed or finishes. In that time the beat may publish a scrape of the platform, but the only consumer of `scrapers` is the worker that is stopping (one worker service per queue, pinned by `test_queue_layout.py`), so nothing starts beside it. If the stopping worker is not killed and a second worker consumes `scrapers`, a second scrape of the platform can start while the first is finishing; the first logs `scrape_single_flight_lost` at its next renewal and releases nothing. Do not add a second `scrapers` consumer without replacing the hook by a time-based heartbeat (see Notes).

After a hard kill, `POST /scrape` (Scraper Control) starts a scrape of the platform at once: a manual trigger has its own scope and does not wait for the scheduled scope's lease.

Observed on the primary: it was restarted at 19:59 UTC on 2026-10-08, and both in-flight scrape task ids were received again within a second (both had been running for more than three hours). Without the hook each would have returned `skipped` and both platforms would have waited out the TTL.

Checked with a real worker on 2026-10-08 (follow-up review): the worker image with this branch's `src/` mounted, Celery 5.6.3 prefork with two slots, in a scratch container with its own scratch Redis on a private Docker network; the real task module, hook and leases, with the scraper and the database stubbed (one item a second).

| Case | Observed |
|---|---|
| SIGTERM and no kill, 8 s into a 30 s scrape | `worker: Warm shutdown`, then `scrape_single_flight_released_on_shutdown` 0.1 s later; the running lease key was gone at the first read one second after the signal; the scrape went on for 21 more items, logged `scrape_completed`, and the worker exited 0. |
| `docker stop -t 5`, 7 s into a scrape | the lease was released at the signal, the task ran four more items, the container was killed (exit 137); afterwards the lease key was absent and the message was in the broker's `unacked` set. |
| The same worker started again, the broker's unacked entry aged past the visibility timeout | the task with the same id was received and ran from its first item, holding the running lease again. It was not skipped. |

Not checked on a real worker: a second scrape starting beside one that outlives the signal (it needs a second `scrapers` consumer), and the primary itself.

| Surface | Change |
|---|---|

No third queue column is stored. It would need a migration, a change to `src/api/schemas.py` and to the Dashboard chart, and the migration cannot be applied while a backfill holds the guard. The live value is in `GET /system/pipeline`, in the snapshot task result and in the monitor log.

### 4. A test run cannot reach a real Redis or broker

The config default is `redis://localhost:6379/0`. On a development host that is the Redis of the primary stack, and it is the Celery broker too. During this story a raw `pytest` run of the contract suite published one real `tasks.scrape_listings` message there (see Notes).

`src/tests/conftest.py` now installs a guard at import, in every session and every xdist worker (`install_redis_connection_guard` in `src/tests/redis_isolation.py`). It wraps redis-py's `connect_check_health`, the one method every connection goes through, for the sync and the asyncio client. Kombu (the Celery publish and the result backend) and the rate limiter connect through redis-py, so they are covered.

| Session | What it can reach |
|---|---|
| `REDIS_URL` names a logical DB other than 0 (what `validate.py` exports for its ephemeral stack: `redis://127.0.0.1:<port>/15`) | exactly that host, port and DB |
| `REDIS_URL` unset, empty, or DB 0 (a raw `pytest`, and the gate's unit tier) | no Redis at all |

A refused connection raises a `redis.exceptions.ConnectionError` subclass before a socket is opened, with a message that starts `Test session blocked a Redis connection to <host>:<port>/<db>`. Code that already treats Redis as unreachable behaves as it does on a host without Redis. The endpoint is fixed when the session starts: a test that changes `REDIS_URL` later does not widen it. `IMOVEIS_ALLOW_PRIMARY_REDIS_WIPE=1` is the existing emergency override and lifts the DB 0 rule here as well.

Limits: the guard lives in the pytest process. A script that a test starts as a subprocess is not covered, and neither is a raw run of anything other than pytest. The database has its own guard (`tests/db_isolation.py`, wipe fixtures only).

### The scrape-duration finding

Not changed by this story, recorded because it is the reason a scrape holds a slot for hours.

In the three hours read on the primary there were 4,777 QuintoAndar price-window fetches. 3,341 URLs were fetched by both worker processes and none was fetched twice by the same process: the two concurrent runs were doing the same work. Windows per city for `alugar`: São Paulo 1,589, Belo Horizonte 1,556, Campinas 1,510. Price windows were split down to R$ 13 wide.

Verdict: the duration of one QuintoAndar run is expected from the design, not a defect. A run is a rate-limited walk over price windows in three cities, at about 4.5 s per request, and in dense cities the windows are split down to R$ 13 wide, which gives about 1,500 windows per city. One run therefore cannot finish inside the 60-minute scrape interval.

The defect was the second concurrent run of the same platform: it doubled the requests without adding listings. This story removes it. It does not shorten one run: how a scrape fetches, paginates and rate-limits is unchanged (out of scope).

Deferred finding: whether three cities belong in the QuintoAndar schedule is a product decision. It is recorded here and not decided by this story.

### Operator steps (primary stack)

No database migration. The steps can be run by an agent operator. Stopping after any step is safe.

1. Rebuild and restart the stack so that `worker_periodic` exists and the API, the workers and beat run the new routing:
   ```bash
   ./scripts/restart.sh --build
   ```
   A new service starts with the stack: no script lists services by name.
2. Know what the messages already on `scrapers` do. They are not moved to `periodic` and they are not lost. `worker_scraper` still consumes `scrapers` and loads the same task module, so it runs them:
   - Housekeeping messages (about 97% of the DW-63 sample) were published without `expires`, so every one runs. Each `tasks.snapshot_pipeline_metrics` writes one snapshot row stamped with the time it runs, not the time it was due.
   - Sender, digest, recheck and refresh messages run once each. A repeated sender or digest run does nothing after the first.
   - `tasks.scrape_listings` messages run one at a time per platform. One that starts while a scrape of its platform is running returns `skipped` and is consumed. One that starts while none is running scrapes. Counted read-only on 2026-10-08, late evening: 193 `tasks.scrape_listings` messages among 11,716 on `scrapers`. They are not purgeable. After the deploy `worker_scraper` works through them: while one slot holds a long scrape, the other slot consumes the queue behind it and skips the messages of that platform. How long the whole backlog takes was not measured.
   - New periodic work does not wait for any of this: it is published to `periodic`.
3. Drain or purge. Recommended: purge the four housekeeping types. Their work is repeated by the next scheduled run on `periodic`, and draining them through `worker_scraper` writes thousands of snapshot rows with nearly the same timestamp and delays the scrapes queued behind them. Dry run first, from the primary checkout:
   ```bash
   .venv/Scripts/python.exe scripts/ops/purge_stale_periodic.py
   ```
   The first output line names the Redis it is aimed at (`redis <host>:<port>/<db>`, no password) and is printed before anything is read or removed, in the dry run and with `--apply`: check it is the primary before going on. Then it prints the count per task type, marks which are removable and removes nothing. `--dry-run` says the same explicitly and is refused together with `--apply`. Then:
   ```bash
   .venv/Scripts/python.exe scripts/ops/purge_stale_periodic.py --apply
   ```
   It removes only `tasks.snapshot_pipeline_metrics`, `tasks.monitor_queues`, `tasks.evaluate_watchlist_alerts` and `tasks.match_saved_search_new_matches`, and only from `scrapers`. Any other queue or task is refused with exit 2. `--redis-url` defaults to `redis://localhost:6379/0`; pass the host port of the primary Redis when `REDIS_PORT` is not 6379. `--task <name>` (repeatable) narrows the removal to some of the four.

   The alternative is to do nothing: the backlog drains by itself, with the costs above.

## Notes / Follow-ups

- Resolves DW-63 in code. The primary deploy (steps above) is an operator step.
- **Capacity of `worker_periodic`.** It has two slots. The availability recheck can hold one for up to about 17 minutes (50 URLs × 20 s timeout) every six hours. The weekly refresh jobs are off by default. Two long jobs at once delay the short ones until one ends; their stale ticks expire instead of piling up.
- **A hard-killed scrape blocks its platform's scheduled scope for up to two hours** (the running TTL; a graceful stop releases the lease, see "What a worker restart does"), and a message that is lost after it was reserved blocks it for up to three (the queued TTL). Both end by themselves. To end one sooner the operator deletes the lease key; nothing does that automatically.
- **The renewal runs from the item loop only.** A scrape that yields no item for more than two hours loses its lease (it logs `scrape_single_flight_lost` at the next item and continues). A second scrape of the platform can then start beside it. On 2026-10-08 the fetches of one run were seconds apart, far from this limit.
- **After a pause-retry or a failure-retry the retried message has no reservation**, so a tick can queue a second message of the same platform. Whichever starts while the other is running is skipped; one that starts after the other ended runs. They never run together.
- **The queued reservation is not renewed.** A message that waits more than 3 h (possible while the legacy backlog drains) loses its reservation, and the beat may then publish one more message per platform every 3 h. They never run together either.
- **Legacy `scrape_listings` messages on `scrapers` are not purgeable** (by rule: the purge tool never removes a scrape). After the deploy they run one at a time per platform, and one that starts while a scrape of its platform is running is skipped and consumed: 193 of them on 2026-10-08. Before this story the same messages would have run too, and two at once.
- **One of those 193 messages and one lease were left on the primary Redis by this story's development, by mistake.** A raw `pytest` run of `src/tests/contract/test_api_contract.py` on 2026-10-08, after `POST /scrape` was changed and before its test was given an in-memory broker, published one manual OLX scrape (`scrape_type: both`, task id `fd1f4df9-1898-4d68-91c1-88daa7ad62bd`) to `scrapers` and took `scrape:single_flight:olx:2fe9313c54db7883:queued:lease` (expires by itself within three hours; its `:meta` hash within twelve). Nothing was removed afterwards: removing it is a write to the primary and the operator's call. Left alone, the message runs one ordinary OLX scrape when it reaches a worker. The test now patches the broker and Redis, and the suite-wide guard of section 4 refuses the connection for every test.
- **The shutdown release assumes one consumer of `scrapers`.** It frees the lease when the stop is requested; a scrape that outlives the request (a warm shutdown that is not followed by a kill) runs on without a lease. With a second `scrapers` consumer a duplicate could start beside it. A time-based heartbeat with a short TTL would replace both the hook and the two-hour wait after a hard kill.
- **The `queue_monitor_periodic_backlog` warning cannot fire while `worker_periodic` is down**: the task that emits it runs on `periodic` itself. The signal for a missing periodic worker is `GET /system/status` (`workers.unconsumed_queues`).
- **The Dashboard does not show the new detail.** Its Celery card shows "offline" for any `workers.status` other than `ok`, including an unconsumed queue, and does not show `detail`; Scraper Control still shows two queue lengths. The manual trigger does tell the truth: Scraper Control shows a warning toast and log line for `already_queued` and `already_running` instead of "enqueued" (added in the follow-up review; the only frontend change of this story).
- **`GET /system/status` waits about one second for worker replies, as it did with `ping()`, and about two while a routed queue has no consumer** (it asks once more before reporting the queue). The Dashboard polls it every 8 s. A worker that answers late in one round is not reported: the two rounds are added together.
- **A skipped duplicate of the same task id stores its `skipped` result under that id** in the result backend, over the state of the run it duplicates. Nothing reads scrape results.
- **If `worker_periodic` is persistently later than an entry's interval, every tick of that entry is discarded until it catches up.** That is the coalescing: the entry runs again as soon as a tick is received inside its interval.
- **`expires` is checked when a worker receives the message.** A message already in a worker's hands is not discarded.
- **One scrape still takes hours on QuintoAndar** (see the scrape-duration finding). Not addressed here.
- The Dashboard history has no `periodic` series (no stored column, by decision above). The pipeline view receives one more key in `queues` and does not render it.
