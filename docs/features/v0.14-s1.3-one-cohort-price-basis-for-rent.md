# One cohort price basis for rent — rent price/m² cohorts compare the fee-exclusive rent, and each score records which price produced it

> Feature branch: `feat/v0.14-s1.3-one-cohort-price-basis-for-rent` (bmad-loop: `bmad-loop/<run>/1-3-one-cohort-price-basis-for-rent`) · Story: `v0.14-s1.3` · Status: done (primary migrated, rebuilt and rescored on 2026-10-08)

## Problem

`adapters/metrics/scoring.py` computed rent price/m² from the Listing headline `price`. That figure includes condo fee and IPTU on QuintoAndar and OLX and excludes them on ZapImóveis, so one rent cohort's mean, z-score, stat score and percentile rank mixed two different prices (AD-3). The same flat at the same rent scored 38 R$/m² on QuintoAndar and 30 R$/m² on ZapImóveis.

## Approach

- **One definition, in `src/core/price_basis.py`.** Pure (standard library only, AD-1) and built test-first. It holds the vocabulary, one SQL relation and one Python mirror of the same rule. `scoring.py` no longer selects a Listing price itself.
- **Per Listing, then the lowest.** Each Listing contributes its own best-known rent figure and the Property keeps the "cheapest offer" rule it already had. Preferring `rent_monthly` outright would let a dearer itemized Listing hide a cheaper one that lacks the column.
- **One stamp per scored row.** `metrics_scoring.price_basis` records which price produced the row's rent price/m². Only the rent figure can vary by basis; sale is always the published sale price.
- **Nothing excluded, nothing imputed.** A cohort may hold both bases; every member stays in the same statistics with its own stamp.
- **Characterization lock first.** `test_scoring_characterization_lock.py` landed in its own commit before any production change and is not edited afterwards. Its fixtures carry no `rent_monthly`, so they keep the headline basis and the same numbers.
- **Total Monthly Cost is not the basis.** Scoring never reads `total_monthly_cost`, `condo_fee*` or `iptu*`.

### The rule

| Step | Behaviour |
|---|---|
| Which Listings count | Active, `price > 0`, type `rent` or `sale` (unchanged). |
| Price of a rent Listing | `rent_monthly` when it is not NULL and above zero (basis `rent_monthly`); otherwise the headline `price` (basis `headline`). A zero or negative `rent_monthly` is treated as absent. |
| Price of a sale Listing | The headline `price`, always. |
| Price of a Property, per listing type | The lowest price among its Listings (as `MIN(price)` before). |
| Stamp | The basis of the Listing that supplied the rent price. On an exact tie `rent_monthly` wins. |
| Row with no rent price/m² (sale-only) | `headline`. |
| Row scored from the legacy `properties.price` fallback (no Listings) | `headline`. |
| Row written before this story | `headline` until the next recalculation, which is true of it. |

### What `core/price_basis.py` exports

| Name | Use |
|---|---|
| `PRICE_BASIS_RENT_MONTHLY`, `PRICE_BASIS_HEADLINE`, `PRICE_BASES` | The vocabulary of `metrics_scoring.price_basis`. |
| `COHORT_PRICE_SQL` | Relation `(property_id, listing_type, price, price_basis)`, one row per Property × listing type. The bulk path uses it as a CTE body. |
| `COHORT_PRICE_FOR_TYPE_SQL` | The same relation for one listing type, bound as `:lt`. The cached cohort stats use it. |
| `property_cohort_prices(listings)` | Python mirror for one Property's Listings. The single-property path uses it. |
| `listing_cohort_price(...)` | The per-Listing step of the mirror. |
| `row_price_basis(rent_basis)` | The stamp for a scored row (`None` becomes `headline`). |

Story 1.6 (percentiles) imports the relation instead of writing `pl.price`.

The query:

```sql
WITH listing AS (
    -- per active priced rent Listing: the price it contributes under each basis
    SELECT pl.property_id,
           pl.platform,
           pl.price AS headline_price,
           CASE WHEN pl.rent_monthly IS NOT NULL AND pl.rent_monthly > 0
                THEN pl.rent_monthly ELSE pl.price END AS basis_price,
           (pl.rent_monthly IS NOT NULL AND pl.rent_monthly > 0) AS uses_rent
    FROM property_listings pl
    WHERE pl.active = true AND pl.price > 0 AND pl.listing_type = 'rent'
),
per_property AS (
    SELECT property_id,
           MIN(headline_price) AS headline_price,
           MIN(basis_price) AS basis_price,
           CASE WHEN MIN(basis_price) FILTER (WHERE uses_rent) = MIN(basis_price)
                THEN 'rent_monthly' ELSE 'headline' END AS price_basis
    FROM listing
    GROUP BY property_id
),
typed AS (
    -- every active Property with area, cohort key as scoring.py builds it
    SELECT p.id,
           p.props_json->>'city' AS city,
           COALESCE(n.name, p.props_json->>'neighborhood', 'Unknown') AS n_key,
           pp.headline_price / p.area_m2 AS ppm_headline,
           pp.basis_price / p.area_m2 AS ppm_basis,
           pp.price_basis
    FROM properties p
    JOIN per_property pp ON pp.property_id = p.id
    LEFT JOIN neighborhoods n ON n.id = p.neighborhood_id
    WHERE p.active = true AND p.area_m2 > 0
),
scored AS (
    SELECT t.*,
           COALESCE((ppm_headline - AVG(ppm_headline) OVER w)
                    / NULLIF(STDDEV(ppm_headline) OVER w, 0), 0) AS z_headline,
           COALESCE((ppm_basis - AVG(ppm_basis) OVER w)
                    / NULLIF(STDDEV(ppm_basis) OVER w, 0), 0) AS z_basis
    FROM typed t
    WINDOW w AS (PARTITION BY n_key)
),
bh AS (
    SELECT s.*,
           CASE WHEN z_headline < -1.0 THEN '1 highly_undervalued'
                WHEN z_headline < -0.2 THEN '2 slightly_undervalued'
                WHEN z_headline < 0.2 THEN '3 average'
                WHEN z_headline < 1.0 THEN '4 slightly_overvalued'
                ELSE '5 highly_overvalued' END AS band_headline,
           CASE WHEN z_basis < -1.0 THEN '1 highly_undervalued'
                WHEN z_basis < -0.2 THEN '2 slightly_undervalued'
                WHEN z_basis < 0.2 THEN '3 average'
                WHEN z_basis < 1.0 THEN '4 slightly_overvalued'
                ELSE '5 highly_overvalued' END AS band_basis
    FROM scored s
    WHERE s.city = 'Belo Horizonte'
)
SELECT '1 properties' AS report, 'all' AS k1, '' AS k2, count(*) AS n,
       NULL::numeric AS q1, NULL::numeric AS median, NULL::numeric AS q3, NULL::numeric AS mean
FROM bh
UNION ALL
SELECT '2 stamp per property', price_basis, '', count(*), NULL, NULL, NULL, NULL
FROM bh GROUP BY price_basis
UNION ALL
SELECT '3 basis per listing', l.platform, CASE WHEN l.uses_rent THEN 'rent_monthly' ELSE 'headline' END,
       count(*), NULL, NULL, NULL, NULL
FROM listing l JOIN bh ON bh.id = l.property_id
GROUP BY 2, 3
UNION ALL
SELECT '4 price/m2', 'headline', '', count(*),
       round((percentile_cont(0.25) WITHIN GROUP (ORDER BY ppm_headline))::numeric, 2),
       round((percentile_cont(0.50) WITHIN GROUP (ORDER BY ppm_headline))::numeric, 2),
       round((percentile_cont(0.75) WITHIN GROUP (ORDER BY ppm_headline))::numeric, 2),
       round(avg(ppm_headline)::numeric, 2)
FROM bh
UNION ALL
SELECT '4 price/m2', 'new basis', '', count(*),
       round((percentile_cont(0.25) WITHIN GROUP (ORDER BY ppm_basis))::numeric, 2),
       round((percentile_cont(0.50) WITHIN GROUP (ORDER BY ppm_basis))::numeric, 2),
       round((percentile_cont(0.75) WITHIN GROUP (ORDER BY ppm_basis))::numeric, 2),
       round(avg(ppm_basis)::numeric, 2)
FROM bh
UNION ALL
SELECT '5 stat band', 'headline', band_headline, count(*), NULL, NULL, NULL, NULL
FROM bh GROUP BY band_headline
UNION ALL
SELECT '5 stat band', 'new basis', band_basis, count(*), NULL, NULL, NULL, NULL
FROM bh GROUP BY band_basis
UNION ALL
SELECT '6 moved', 'price/m2 changed', '', count(*) FILTER (WHERE ppm_basis <> ppm_headline), NULL, NULL, NULL, NULL
FROM bh
UNION ALL
SELECT '6 moved', 'stat band changed', '', count(*) FILTER (WHERE band_basis <> band_headline), NULL, NULL, NULL, NULL
FROM bh
ORDER BY 1, 2, 3;
```

### Operator steps (primary stack)

Deploy order matters: the new code writes `price_basis`, so the primary is migrated before the rebuild. The old code tolerates the new column (it has a default), so stopping after step 1 is safe.

1. Migrate the primary database, from the primary checkout, in Git Bash:
   ```bash
   bash scripts/agent/migrate-primary.sh
   ```
   Expected: `alembic_version` becomes `d5e6f7a8b9c0` and every existing `metrics_scoring` row reads `price_basis = 'headline'`. The script refuses while a cloud backfill runner is alive (`backfill:gemma:active`); wait for it or pause the runner, never delete the key.
2. Rebuild and restart the API and workers so they run the new scoring code:
   ```bash
   ./scripts/restart.sh --build
   ```
   If the rebuild fails, the previous images keep working against the migrated schema. Do not downgrade the schema while any container runs the new code.
3. Recalculate the stored scores, right after step 2. No beat task runs the bulk stage; this endpoint is the only trigger:
   ```bash
   curl --max-time 3600 -X POST http://localhost:8000/admin/scoring/recalculate -H "X-API-Key: $API_KEY"
   ```
   It returns `stat_rows_updated` and `combined_rows_updated`. The whole recalculation is one request and one transaction: if it fails or the request is cut, nothing is written and it can be run again. Its run time on the primary is not measured (see the note on row count below), hence the long `--max-time`.
4. Check that every rent Property was rescored (read-only, whole database):
   ```sql
   SELECT count(*) FILTER (WHERE ms.price_basis = 'rent_monthly') AS rent_monthly,
          count(*) FILTER (WHERE ms.price_basis = 'headline')     AS headline,
          count(*) FILTER (WHERE ms.id IS NULL)                   AS not_scored
   FROM properties p
   JOIN (SELECT DISTINCT property_id FROM property_listings
         WHERE active AND price > 0 AND listing_type = 'rent') r ON r.property_id = p.id
   LEFT JOIN metrics_scoring ms ON ms.property_id = p.id
   WHERE p.active AND p.area_m2 > 0;
   ```
   Expected: `not_scored` 0 and `headline` a small remainder (on 2026-10-08 only 300 of 128,382 active rent Listings had no `rent_monthly`). A large `headline` count means step 3 did not run on the new code.
5. Record the stored result for Belo Horizonte under the band table above (read-only). The "after" column there is a projection computed from the Listings; this is what the stage actually stored:
   ```sql
   SELECT ms.meta->'stat_analysis'->>'category' AS band, count(*)
   FROM metrics_scoring ms
   JOIN properties p ON p.id = ms.property_id
   WHERE p.active AND p.props_json->>'city' = 'Belo Horizonte'
     AND ms.price_per_m2_rent IS NOT NULL
   GROUP BY 1 ORDER BY 1;
   ```
   Expected: close to the "New basis (after)" column; it differs only by Listings that changed since the measurement.

## Notes / Follow-ups

- **Stored scores move only on recalculation.** Between step 2 and step 3 the single-property path (run after each enrichment) already scores with the new basis and stamps its row, while rows it has not touched keep their headline-based values and read `headline`. Both are true of the rows they sit on; the cohort is only consistent after step 3, so run step 3 straight after step 2. Cohort statistics cached in Redis by the old code (`n_stats:*`, 60 s) can also serve the single-property path for the first minute after the restart.
- **The card shows a headline price next to a fee-exclusive R$/m².** `price_per_m2` and `price_per_m2_rent` already reach the API, the export and the UI. After step 3 a QuintoAndar or OLX card shows its fee-inclusive `price` beside a price/m² computed from the rent alone, and nothing on the wire says which basis produced it. Story 2.8 states `price_basis` in the cohort summary; no story yet shows it on the card.
- **A schema downgrade loses the stamps.** Dropping the column discards them while `price_per_m2_rent` keeps its value; after a re-upgrade every row reads `headline` until step 3 is run again.
- **The recalculation writes a row for every scored Property.** `compute_neighborhood_stats` inserts a `metrics_scoring` row (with `ai_score` 0) for each active Property that has an area and a price and no row yet. On 2026-10-08 the primary held 28,210 rows for about 200,000 such Properties, so step 3 would add roughly 170,000 rows. This is the endpoint's behaviour before this story; it took 62 minutes on that volume on 2026-10-08.
- **Cohorts are keyed by neighbourhood label only.** The primary has no `neighborhood_id` set, so the cohort key is `props_json->>'neighborhood'`, and a label shared by two cities is one cohort. The measurement above follows that key, as scoring does. Changing the key belongs to Story 1.6.
- **A rent figure above the headline is still the rent.** 67 QuintoAndar Listings on the primary publish a `rent_monthly` above `price`. The rule uses `rent_monthly` when it is known; it does not pick the lower of the two.
- **`price_basis` is not on the wire.** `src/api/` and the frontend are untouched in this story.
- **No percentiles, no minimum cohort size.** `percentile_rank*` is still the SQL `PERCENT_RANK` the stage already wrote; Story 1.6 computes the cohort percentiles from `COHORT_PRICE_SQL`.
- Related: Story 1.1 (`rent_monthly` on the persist path), Story 1.6 (cohort percentiles), Epic 2 (the `aluguel-2027` profile).
