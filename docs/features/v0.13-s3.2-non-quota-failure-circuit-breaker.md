# Non-quota AI failures must not fabricate a score — typed marker + circuit breaker

> Feature branch: `feat/v0.13-s3.2-non-quota-failure-circuit-breaker` · Story: `v0.13-s3.2` · Status: implemented

## Problem

Every AI-client exception that was **not** a quota refusal got swallowed into a
fabricated result — `VisualResult(condition_score=0.5, analysis="Error")` /
`SentimentResult(sentiment_score=0.5, …)`. `run_enrichment` blended that into
`ai_score = 0.5`, persisted it and committed; and because `mode_is_missing_ai`
is `not score`, `0.5` is truthy, so the row left the `mode=missing` candidate set
**permanently**.

A revoked or expired `GEMINI_API_KEY` (401), a retired model id (404) and a
DNS/proxy outage are none of `_RETRY_STATUS` or `_QUOTA_BODY_MARKERS`, so none of
them re-raised. An unattended `--continuous` run therefore stamped ~4,600
properties a day with a fake score behind a healthy-looking progress banner, and
no later pass would ever revisit them. Filed as **DW-17**; explicitly fenced by
story 1.3, which closed the same corruption for quota only.

Epic 3 gates Epic 2 for exactly this reason: percentile work computes over this
corpus, so fabricated scores had to stop accruing first.

## Approach

- **A typed marker on the result, not a raise from the client.** The three result
  models gained `degraded: bool = False`, set only on the seven non-quota
  exception fallbacks. Making `analyze_visuals`/`analyze_text` raise would have
  been the smaller diff, but it deletes the local resilience contract story 1.3
  deliberately fenced — one bad response must not abort a whole enrichment. The
  client's behaviour is byte-identical; what changed is what the *consumer* does
  with the result.
- **The refusal lives in `run_enrichment`** — the single write authority (AD-10)
  — and raises `AIResultDegradedError` **before** `SessionLocal()`. Nothing is
  written, nothing is committed, `_worker` skips the `else:` that advances the
  checkpoint, and the row stays a `mode=missing` candidate. A check in the
  backfill's `_enrich_one` would have been too late (the commit already happened)
  and would have left the live Celery path fabricating under a second policy.
- **A consecutive-fallback circuit breaker in `run_backfill`.** A degraded row is
  ambiguous — a dead key (systemic) or one property's unparseable response (per
  row) — so it *is* charged an error and a ledger attempt, and the ledger's
  quarantine keeps owning the per-row case. `max_consecutive_ai_failures`
  completions in a row with no success between them set
  `BackfillResult.ai_circuit_open` and stop launching. Any success resets the
  count; an ordinary row error neither counts nor clears it.
- **Tripping rolls the charge back.** The unbroken run is the proof those rows
  were never at fault, so their ledger attempts are returned — the same
  reasoning `rollback_attempt` was written for on the quota branch. Without it
  the charge outlives a pass whose checkpoint does not: the next start re-fetches
  exactly the same oldest-first rows, and `max_attempts` restarts against a key
  nobody has fixed yet would quarantine three innocent properties while the
  banner promises they are still candidates. Degradation *below* the threshold
  keeps its charge — a row nobody can ever enrich must still march to
  quarantine, or `--continuous` pays for it every cycle forever.
- **Duck-typed across the boundary.** `core.backfill_runner.is_degraded_result`
  reads `exc.is_degraded_result`, exactly like `is_quota_exhausted` reads its
  flag — `src/core` still imports nothing from `adapters`/`api` (AD-1). Unlike
  the quota predicate it carries **no** message-matching safety net: this marker
  is set by our own gate, never by an untagged transport error.
- **No new `BackfillState`.** `BACKING_OFF` is defined as "the provider refused on
  quota" and would send an operator to the Gemini dashboard for a revoked key; a
  new value would need a pt-BR label and a frontend change this epic forbids. A
  tripped run publishes what a finished pass publishes (`idle`) and speaks
  through `BackfillResult.ai_circuit_open`, a distinct WARNING log line and CLI
  exit code **9**.
- **The quota path is untouched.** `_reraise_if_quota` still fires first, so a
  quota error can never become a degraded result; the quota branch keeps its
  rollback + `BACKING_OFF` publish, and a quota refusal never feeds the breaker.
- **A degraded *verdict* is recorded, not refused.** `template_deal_verdict()`'s
  text and `confidence=0.0` are unchanged and `_llm_verdict` still swallows its
  exception; `meta["deal_verdict"]` simply gains `"degraded": true`. The verdict
  never touches `ai_score`, so it cannot retire a row.


The regression test is written to fail on the pre-fix tree: with the
`run_enrichment` gate removed, `test_run_enrichment_degraded.py` fails with
*"run_enrichment opened a DB session for a degraded result"* — the session
factory it injects raises if it is called at all, which is what makes "nothing
was persisted, nothing was committed" provable rather than argued.

### The operator knob

`backfill.max_consecutive_ai_failures` (default **3**) is how many consecutive
degraded rows end a pass. `<= 0` disables the **breaker only** — the refusal to
persist a fabricated score is unconditional and cannot be turned off. Be aware of
the trade: a disabled breaker also never reaches the attempt rollback, so a
broken backend charges every candidate an attempt per pass and `max_attempts`
passes later the whole queue is quarantined and needs `--reset-quarantine`.

### What an operator sees when it trips

```
════════════════════════════════════════════════════════════════════
  BACKFILL STOPPED — the AI backend kept returning fabricated results
  Likely causes: a revoked/expired API key, a retired model id, or blocked network egress.
  Nothing was persisted for those rows, the checkpoint is intact and their attempts were rolled back — they are still candidates.
  The cause is in the AI client, not the queue: check GEMINI_API_KEY, the configured model id and egress (journalctl -u imoveis-backfill-serve).
  Re-run the same command once it is fixed; backfill.max_consecutive_ai_failures sets the threshold.
════════════════════════════════════════════════════════════════════
```

plus exit code **9** (`EXIT_AI_CIRCUIT_OPEN`), a `backfill_ai_circuit_open`
WARNING, and one `backfill_ai_result_degraded` WARNING per affected row carrying
its running `consecutive` count. `--serve` survives the non-zero child and keeps
supervising, so a fixed key needs only a new start request.

## Notes / Follow-ups

- **Blast radius is deliberate, not scope creep.** The gate sits in the shared
  write authority, so the live `ai_enrich` path stops fabricating too — bounded
  by that task's existing `max_retries=5` retry policy, which is unchanged. Note
  the cost that bound implies: a *sustained* local outage now runs six attempts
  per property where it previously fabricated one score and moved on, and that
  path has no breaker of its own (deferred, see below).
- **Consecutive under concurrency** means consecutive *completions* with no
  success between them. With `concurrency > 1`, up to `concurrency - 1` extra
  rows may already be in flight when the breaker trips; they drain (never
  cancelled mid-enrichment) and, being degraded, persist nothing.
- Closes **DW-17**. Untouched by design and still open: **DW-18** (story 3.3, the
  budget counts properties not requests), **DW-19** (`--continuous` never exits on
  a permanently refusing *quota* account — a different terminal condition from
  this one), **DW-20**.
- The breaker reports itself through `BackfillResult` and the exit code only. If
  the Operações card should ever show it, that needs a wire-vocabulary decision
  (a new `BackfillState` value + pt-BR label + frontend map) that this epic
  explicitly forbids.
- Review pass (2026-08-12) deferred five findings to the ledger, all outside this
  story's intent contract: a 200 response whose JSON merely *omits* the score key
  still yields an **undegraded** fabricated 0.5 (`data.get("condition_score",
  0.5)` — a model-quality failure, not a client failure); rows poisoned **before**
  this fix are unreachable and no repair path exists, which is the missing half of
  the Epic 3 → Epic 2 gate; the live `ai_enrich` path has no breaker; a tripped
  breaker is invisible on the Operações card; and the live *verdict-only* task
  writes a degraded template verdict with a fresh `enriched_at`.
