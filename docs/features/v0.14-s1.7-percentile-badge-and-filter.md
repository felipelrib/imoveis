# Percentile badge and filter — cards say `entre os N% mais baratos` and the grid filters by it

> Feature branch: `feat/v0.14-s1.7-percentile-badge-and-filter` · Story: `v0.14-s1.7` · Status: implemented; the primary stack is not rebuilt yet (see Operator steps)

## Problem

Story 1.6 stores, per Property and listing type, how cheap it is inside its neighbourhood cohort (`metrics_scoring.price_per_m2_percentile_rent` / `_sale`). Nothing read those columns:

- the API did not serve them;
- the grid did not show them;
- they could not be filtered.

The only "percentile" on the wire was the legacy `percentile_rank*`, which is a different number (SQL `PERCENT_RANK`, cheapest = 0, no minimum cohort size, a fabricated `0.5` on the single-property path).

## Approach

- **One projection, stored values.** The two columns are added to the AD-12 serializer (`core/property_projection.py`), so list, batch, export and detail carry them from one place. The API computes nothing per Property.
- **Unrounded on the wire.** The legacy fields are rounded to three places in the list. A share such as 501/2000 rounded to three places reads `0.25` while the truth is 25.05%, so a rounded value would let the badge say 25% for a Property the 25% filter rejects. The new fields are served as stored; "the badge says N ≤ 25" and "passes the 25% filter" are one test.
- **Ceil, not round.** `entre os N% mais baratos` is true for N ≥ value × 100 and false below it. N is the smallest whole percent that keeps it true: `0.25` → 25, `0.2001` → 21, at least 1. The ceiling is guarded against floating-point noise (`0.07 × 100` is `7.000000000000001`; it reads 7).
- **Badge only up to 50%.** DESIGN.md reserves the green ink for good price news. The cutoff equals the widest option of the filter, so every card a percentile filter returns carries a badge for the filtered type. Values above the cutoff stay on the wire for Story 1.8's sentence.
- **`both` means either.** Without a listing type the card shows one price line per type, each with its own badge, and a Property passes the filter when one of the lines does. With a type selected only that type's column is read.
- **A column counts only while its Listing is live.** The stored percentile outlives a deactivated Listing until the next scoring run. The filter therefore also requires an active Listing of the type whose column it reads; otherwise it would return a Property whose card has no price line, and so no badge, for that type.
- **A general parameter, three UI choices.** The API accepts any value in (0, 1]; the UI offers `qualquer preço`, 25% and 50%.
- **NULL never matches and never renders.** A suppressed cohort, a Property that is not a cohort member and a Property without a scoring row all read `null`: no badge element, no placeholder, and the SQL comparison is NULL, which is not a match.
- **The legacy fields are untouched.** `percentile_rank*` stays on the wire, in the export and in the modal (Story 1.8 owns the modal).
- **No migration, no index.** The filter is a predicate on `metrics_scoring` rows the list query already joins. Whether an index would help was not measured on the primary.

### What the API serves

| Where | What |
|---|---|
| `GET /properties`, `/properties/by-ids`, `/properties/export`, `/properties/{id}` | `price_per_m2_percentile_rent`, `price_per_m2_percentile_sale`: number in (0, 1] or `null` |
| `GET /properties`, `/properties/export` | `max_price_per_m2_percentile`: number, > 0 and ≤ 1; anything else is a `422` |
| CSV export | The two fields are the last two columns; `null` is an empty cell |
| `POST /saved-searches`, `PATCH /saved-searches/{id}` | `filters.max_price_per_m2_percentile` (camelCase `maxPricePerM2Percentile` accepted), same range, `422` outside it |

How the filter reads the columns:

| `listing_type` | Keeps a Property when |
|---|---|
| `rent` | `price_per_m2_percentile_rent <= value` and the Property has an active rent Listing |
| `sale` | `price_per_m2_percentile_sale <= value` and the Property has an active sale Listing |
| `both` or absent | either of the two rows above |

The SQL is static text; the value is a bound parameter (BIN-135).

### Product decisions taken in this story

The epics and the UX contract left these open. Each is one constant or one rule and can be changed without touching the rest.

| Decision | Chosen | Where |
|---|---|---|
| Rounding of N in the badge | Up to the next whole percent (`0.2001` reads 21), at least 1 | `cheapestPercent` in `frontend/src/utils/percentile.ts` |
| Which values get a badge | Stored value ≤ 0.5 only. Above it the card shows nothing, like a suppressed one; the value is still on the wire | `PRICE_PERCENTILE_BADGE_MAX` |
| Badge tint | One tint for every badge (DESIGN.md has one `percentile-badge` component); no stronger tint for cheaper values | `.percentile-badge` in `index.css` |
| Filter default | `qualquer preço` (no parameter sent) | `DEFAULT_FILTERS` |
| Suppressed Properties under an active filter | Left out: a null percentile never matches. With `qualquer preço` they are listed, without a badge | `_PRICE_PERCENTILE_CAP_*` in `src/api/properties.py` |
| No Transação selected (`Aluguel e venda`) | A Property passes when its rent line or its sale line qualifies | same |
| Dual Property | One badge per price line, each from its own cohort | `PropertyCard.tsx` |
| Chip | Only this filter renders a chip; the other filters stay as they are until Story 6.3 | `PropertiesFilterBar.tsx` |
| Favoritos | The view ignores every filter, so it shows no chip; its endpoint does not serve the two fields, so its cards show no badge | `filtersApplied` |
| Card price typeface | Serif family and tabular numerals on the existing price; size, weight and gradient unchanged | `.property-price` |

### What the grid shows

| Element | Rule |
|---|---|
| Badge | On each price line, for that line's listing type, when the stored value is ≤ 0.5. Text `entre os {n}% mais baratos` (en: `among the {n}% cheapest`). |
| Badge visual (UX-DR9) | Ink `#74bd82`, background `#74bd821f`, border `1px solid #74bd8259`, radius 7px, 11.5px / 600, `margin-left: auto` on the price line. |
| Price | `.property-price` uses the DESIGN.md `display-price` family (Georgia stack) with tabular numerals. |
| Filter | Select `Preço no bairro` in the advanced-filters panel: `qualquer preço`, `entre os 25% mais baratos`, `entre os 50% mais baratos`. |
| Chip | One chip with the option's text under the toolbar while the filter is active, visible with the panel closed. `×` clears the filter. Not shown in Favoritos, where no filter is applied. |
| Chip strip | `max-height` of two chip lines (2 × 30px + 6px gap = 66px), overflow hidden. |

The filter value takes part in the grid fetch, the map fetch, the export, saved searches, `Limpar tudo`, `Limpar filtros` and `hasActiveFilters`. Changing Transaction refetches with the new `listing_type` and the same value.

New `:root` tokens, under their DESIGN.md names: `--price-drop`, `--price-drop-tint-12`, `--price-drop-tint-35`, `--font-display-price`, `--radius-meia-sm`. The chip strip carries the `.meia` class so `--accent` resolves to the Meia-noite blue inside it only.

## Notes / Follow-ups

- **On today's cards the badge sits under the price, not beside it.** The grid card is about 356px wide at a 1280px viewport, and the price line already holds the price, the listing-type tag, the platform and the favourite / watchlist icons. The badge (about 170px) does not fit beside them, so it wraps inside its price line and stays right-aligned. On a line wide enough it sits beside the price, as in the Painel mock. Putting it beside the price at this card width means moving the icons or the tags, which is the card restyle this story must not do (the mock has the icons on the photo).
- **The price keeps its weight and gradient.** Only the family and the numerals changed on `.property-price`; DESIGN.md's 26px / 400 / plain ink is part of the card restyle, not of this story.
- **The stored values drift between full recalculations.** The single-property path updates the scored Property's own percentile, not its cohort peers (Story 1.6 notes). The badge and the filter show what is stored; no beat task runs the bulk stage and this story does not schedule one.
- **No index for the filter.** Not measured on the primary. At 25% to 50% selectivity a b-tree on the percentile columns would likely not be chosen; measure before adding one.
- **Applying a saved search does not clear filters it does not hold.** `applyFilters` sets only the keys present in the saved search. Applying a search saved without a percentile leaves an active `Preço no bairro` value in place. This is how every filter behaves today; not changed here.
- **The select lists a non-standard value when one is active.** A saved search written through the API can hold any share in (0, 1] (for example `0.305`). The select then shows `entre os 30.5% mais baratos` as an extra option and the chip reads the same: the cap as it is applied, not rounded. The decimal separator is not localized. A stored value outside (0, 1] is dropped when the search is applied. A cap above 0.5 returns cards without a badge (the badge stops at 50%).
- **Favoritos shows no badge and no chip.** `src/api/favourites.py` has its own projection without the two fields, and the view sends no filters. Story 5.10 owns the Favoritos columns.
- **A price line without a price can still carry a badge.** If an active Listing has a null price and the stored percentile of its type is ≤ 0.5, the line reads a dash and the badge. Not guarded: a cohort member has a price when it is scored.
- **The legacy `percentile_rank*` is still served** (list, batch, detail, export) and the modal still labels it `Percentil` in pt-BR. Two numbers called percentile are on the wire until Story 1.8 replaces the modal; ledger entry DW-47.
- **The map e2e test loads map tiles from the network**, as `compare-map-select.spec.js` already does.
- Related: Story 1.6 (the stored percentiles), Story 1.8 (panel sentence, cohort size, retirement of the legacy fields in the modal), Story 6.3 (chip collapse and `Filtros (N)`).
