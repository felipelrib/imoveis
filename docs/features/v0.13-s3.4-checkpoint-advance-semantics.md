# Checkpoint advance semantics under lease loss — the shared resume marker is lease-gated

> Feature branch: `feat/v0.13-s3.4-checkpoint-advance-semantics` · Story: `v0.13-s3.4` · Status: implemented

## Problem

`<prefix>:checkpoint` is a single Redis hash that **every** backfill runner
writes: `last_property_id`, `last_run_date` and the all-time `processed_total`.
`Checkpoint.advance()` wrote it unconditionally — an `hset` plus an `hincrby`,
called from `_worker`'s success branch with no reference to who holds the
backfill lease.

That collides with a deliberate constraint: **in-flight rows always drain**.
Cancelling a row mid-enrichment leaves a half-written property, so when a runner
discovers it has lost its lease it stops *launching* but lets everything already
in flight finish. Each of those late completions then wrote the shared hash:

- `last_property_id` / `last_run_date` were stamped with the **displaced**
  runner's rows, overwriting the successor's marker (a rewind, in the sense that
  the marker now names an older row than the one the live runner just recorded);
- `processed_total` counted rows **twice** — the successor had re-fetched those
  same properties as `mode=missing` candidates, so both runners' copies landed in
  the all-time counter.

v0.13-fu7 closed exactly this overwrite class for the *state* key (`_publish` is
guarded on `result.lease_lost`) and deliberately left the checkpoint alone: the
same call also records genuinely completed work, and deciding what to do with
that was a semantics change rather than a review patch (ledger item **DW-11**).

The window is not theoretical. At the shipped `lease_ttl_seconds: 900` the
background renewer only observes a takeover every `ttl/3` = 300 s, so a guard
based purely on an in-process flag would still leave up to five minutes of
drained rows writing on a lease somebody else already owns.

## Approach

**Lease-gate the advance at the write, not in the caller.**

- `Checkpoint` takes an optional `lease` handle (duck-typed on `.key` / `.token`
  — `core` gains no adapter import, AD-1) and `advance()` returns `bool`.
- With a lease wired it is an owner-token compare-and-set:
  `_CHECKPOINT_ADVANCE_LUA` (KEYS: checkpoint + lease; ARGV: token, property id,
  Python-computed run date) when the client exposes a callable `eval`, and the
  codebase's standard token-guarded `get`-then-write fallback otherwise — which
  announces itself once through `_warn_non_atomic_fallback(self, "checkpoint
  advance")`. The reply goes through `_reply_is_true`, because `bool(b"0")` is
  `True` and a refusal read as success is the whole bug back again.
- Without a lease it keeps today's unconditional write and returns `True`. That
  is what `--status`, `--dry-run`, the admin API's read-only `Checkpoint` and
  every pre-existing test build, and gating a read-only object on a token it
  never holds would refuse forever.
- `run_backfill` now has **one** ownership predicate, `_owns_shared_state()`
  (`not result.lease_lost`), used by both `_publish` and the new
  `_record_completion(property_id)`. A CAS refusal is a *detector*, not a second
  policy: it feeds `_note_lease_lost(reason)`, the same latch a refused renew
  uses, so the state-key guard and the checkpoint rule can never drift apart.
- Only an explicit `False` counts as a refusal. The suite's duck-typed
  checkpoint doubles return `None`, and reading falsiness as a refusal would have
  every one of them fabricate a lease loss.
- The guarantee lives on the *caller's* wiring, so a run that holds a lease and
  was handed an ungated `Checkpoint` (the pre-fix shape, and one refactor away at
  any time) logs `backfill_checkpoint_ungated` naming DW-11. `Checkpoint.lease_gated`
  is public for exactly that check.
- A raising `eval` (scripting disabled, a rejected script body, a `CROSSSLOT` on a
  clustered client) degrades **once** to the token-guarded fallback rather than
  raising per finished row — which would surface as an anonymous row error and
  leave the checkpoint frozen for the whole run. Both keys are `<prefix>:`-derived
  and co-located on the single Redis this stack runs; a cluster would need a shared
  hash tag, and without one every advance takes that fallback.

**Why not a monotonic compare-and-set on the id ordering?** The epic left both
options open; monotonic ordering turns out not to be expressible over what is
actually stored, and it would protect nothing:

- `Property.id` is a **random UUID** (`src/adapters/db/models.py:113-122`);
  `public_id` is the monotonic one and it is not what the checkpoint stores. So
  "forward" has no definition over `last_property_id`.
- Launch order is `first_seen` (`scripts/dev/backfill_gemma.py:761-763`), and
  rows land in *completion* order from up to `concurrency` workers, so even a
  well-ordered id would not arrive monotonically.
- Nothing reads `last_property_id` back to drive resume. Resume is `mode=missing`
  set subtraction (`src/core/enrichment_rerun.py:249-290`);
  `fetch_candidate_rows` never receives the checkpoint at all.

That last point also means DW-11's "the next resume rewinds and re-enriches the
gap" overstated the harm: the real damage is a **lying resume marker** and an
**inflated all-time counter** on the two operator surfaces that read them
(`--status` and `GET /admin/backfill/status`). Lease-gating is the mechanism that
matches the actual failure.

**The trade-off, stated.** A drained row's work is real, and this drops its
bookkeeping: `processed_total` will not count it and `last_property_id` will not
name it. The counter's semantics is therefore **at most once** per property, not
exactly once: a row the successor also re-fetched is counted once (by the
successor), and a row it never re-fetched — because the drain finished first, so
the row was no longer a `mode=missing` candidate — is counted zero times. That is
the deliberate price of counting each *property* once — the
successor re-fetched those same rows as candidates, so counting the loser's copy
double-counts the property, while declining it merely under-reports an all-time
counter nobody resumes from. Nothing that matters is lost: the enrichment is
committed to Postgres by `run_enrichment`, the row leaves the candidate set, and
the run still reports the work in `result.processed`, in `backfill_done`, and now
in `result.unrecorded_completions`, a `backfill_checkpoint_declined` log line and
the CLI's exit-7 banner.

## How to Test

```bash
bash scripts/agent/validate.sh fast      # lint + unit, incl. the new handover suite
bash scripts/agent/validate.sh backend   # + the real-Redis CAS tests
bash scripts/agent/validate.sh all       # full gate
```

The regression that proves the fix is
`src/tests/unit/test_backfill_checkpoint_handover.py::test_a_displaced_runners_drain_neither_rewinds_nor_double_counts`,
with `…::test_rows_recorded_before_the_loss_survive_it` as its other half (rows
recorded under our own lease *and* rows declined after the steal, in one run — a
fix that simply stopped writing altogether passes only the first).

To watch them fail, revert the **body** of `Checkpoint.advance` to the
unconditional `hset` + `hincrby` and keep the `lease=` constructor argument
(dropping the argument makes the whole module fail at construction with a
`TypeError` instead, which proves nothing). The rewind then shows up directly:
`assert 'prop-2' == 'successor-row'` — a drained row of the displaced runner
sitting in `last_property_id` where the successor's marker belongs.

**What an operator sees after a handover.** A run that loses its lease still
exits `7` with the `BACKFILL LEASE LOST` banner; when rows drained after the
loss, the banner now leads with them:

```
════════════════════════════════════════════════════════
  BACKFILL LEASE LOST — another runner may have taken over; exiting to avoid two writers
  3 row(s) finished after the lease was lost in this pass: enriched and
  committed, but NOT counted on the shared checkpoint (it is the lease
  holder's). They are simply no longer candidates.
  The checkpoint is intact: whoever holds the lease continues from it.
  Check `--status` before starting another run.
════════════════════════════════════════════════════════
```

So `enriched N` in the summary and a `--status` `processed_total` that did not
move by `N` are explained on the spot instead of looking like lost work. "in this
pass" is literal: under `--continuous` the summary's `enriched this run` is
cumulative across cycles while this count is the final pass's. The structured log
carries the same figure (`backfill_checkpoint_declined`, once per pass, at the
end, with the whole count) and `BackfillResult.to_dict()` exposes
`unrecorded_completions` — which also counts a row whose checkpoint write *raised*
(a Redis blip), since that row is committed and equally unrecorded.

## Notes / Follow-ups

- Closes ledger item **DW-11**.
- The `:active` heartbeat policy is unchanged on purpose: a draining runner is
  genuinely writing rows, so beating it stays honest and `migrate-primary.sh`
  keeps its exclusion.
- `src/api/admin.py`'s `_backfill_primitives()` builds a `BackfillLease` whose
  owner string (`admin-api`) exists only to *name* a holder in refusal messages.
  Its `Checkpoint` is deliberately left lease-less — it never advances, and
  wiring that token in would gate a read on a lease the API does not hold.
- `unrecorded_completions` is a per-run counter and is not persisted anywhere. If
  an operator ever needs the all-time figure reconciled, that is a separate
  decision about what `processed_total` is supposed to mean.
- It also stays off the wire (the story's contract forbade schema changes), so the
  Operações card shows a `processed_total` that quietly stops moving during a
  handover with the explanation only in the host's CLI/journal. Logged as deferred
  work.
- The success branch's `consecutive_degraded` / `degraded_run_ids` resets now run
  *before* `_record_completion`, which talks to Redis and propagates by design: a
  blip after them would have left a genuinely successful row counted as
  consecutive degradation and walked the s3.2 AI breaker towards a trip with no
  evidence behind it.
