# Admin backfill control API — start/pause/resume/status under the shared lease

> Feature branch: `bmad-loop/20260806-010958-6ecb/1-5-admin-backfill-control-api` · Story: `v0.13-s1.5` · Status: implemented

## Problem

Story 1.3 turned the cloud enrichment backfill into a lease-governed, pausable,
resumable runner with a published control state — but the only way to drive it
was `scripts/dev/backfill_gemma.py` in the operator's shell. FR-28 asks for the
backfill to graduate from `scripts/dev` to an operator-facing operation, and
story 1.6's *Operações* card has no API to talk to. A live run was equally
invisible to anything outside that terminal: nothing in `src/api/` exposed the
lease holder, the published state, today's budget consumption or the checkpoint.

## Approach

- **A control plane, never a second runner.** `/admin/backfill/{status,start,pause,resume}`
  construct the *same* story-1.3 primitives (`BackfillLease`, `BackfillControl`,
  `DailyBudget`, `Checkpoint`, `Heartbeat`, `MigrationGate`, `AttemptLedger`)
  against the *same* Redis keys. The API only reads and *requests*: it never
  enriches, never queries the domain database, never spawns a process, and never
  beats the runner's `:active` heartbeat (a beating heartbeat blocks
  `migrate-primary.sh`). The one database write it makes is the AD-6 audit row
  each mutation records via `log_audit_action` — which opens a session and
  commits, and swallows its own failure, so a mutation can land with no audit row
  behind it.
- **Start is a request, not an execution.** The runner needs `GEMINI_API_KEY`,
  which by design lives only in the operator's host shell (NFR-3), and driving a
  multi-day pass from a request-serving thread would contradict AD-4/AD-10. So
  `POST /admin/backfill/start` writes a short-lived `…:control:start` level key
  and a new host-side `--serve` supervisor consumes it and launches the ordinary
  `--continuous` run. `runner_present` (lease held **or** supervisor heartbeat)
  is reported so story 1.6 can say "nothing is listening" instead of showing a
  button that silently queues into the void.
- **One hour, not seven days.** Pause/stop are 7-day levels because a runner must
  observe them whenever it wakes. A start is an intent to begin *now*: a
  week-old start request firing a multi-day cloud spend unattended is the worse
  hazard, so the start key expires in an hour while `start_requested_at` keeps it
  visible meanwhile.
- **Liveness is the lease, not the state key** (DW-20 workaround, not a fix). A
  single row slower than the 120s state TTL makes a live run read back `idle`.
  The status contract therefore carries `state` (what the runner published) and
  `active` (does anyone hold the lease) as separate fields.
- **One aggregator.** `build_status_snapshot()` in `src/core/backfill_runner.py`
  is the single pure function that turns the primitives into the wire shape, so
  Redis key layout never leaks into `src/api/` (AD-13). It backs the API only:
  the CLI's `--status` still formats its own print-out (it interleaves DB-derived
  census/ETA figures the wire shape deliberately excludes), so the two can still
  differ in what they show — only the pending-request vocabulary is shared
  outright, via `pending_control_requests()`. Adopting the aggregator in
  `--status` is the open follow-up that would close that gap.
- Alternative rejected: running `run_backfill` (or a Celery task) from the
  request thread. It would put the cloud key in the API container, create a
  second driver inside a request-serving process, and make the API a second
  quota consumer.

## How to Test

1. Automated (the gate this story is verified by — the API schema changed, so
   the contract suite must run):
   ```bash
   bash scripts/agent/validate.sh backend
   ```
2. Manually, against the primary stack (`X-API-Key` = the configured admin key):
   ```bash
   # Nothing running: state idle, active false, runner_present false
   curl -s -H "X-API-Key: $API_KEY" localhost:8000/admin/backfill/status | jq

   # Host side — the consumer that makes "start" real (needs the cloud key):
   GEMINI_API_KEY=... PYTHONPATH=src python scripts/dev/backfill_gemma.py --serve

   # Ask for a run: 202 + requested=true, runner_present=true once --serve is up
   curl -s -X POST -H "X-API-Key: $API_KEY" localhost:8000/admin/backfill/start | jq

   # While it runs: pause / resume, and a second start is refused with 409
   curl -s -X POST -H "X-API-Key: $API_KEY" localhost:8000/admin/backfill/pause | jq
   curl -s -X POST -H "X-API-Key: $API_KEY" localhost:8000/admin/backfill/resume | jq

   # The CLI sees exactly the same keys, including the start request/supervisor:
   PYTHONPATH=src python scripts/dev/backfill_gemma.py --status
   ```

### Supervision (`--serve` in production)

**With no supervisor running, the Start button only queues a request.** The API
accepts it (202) and nothing consumes it; the status body says so with
`runner_present: false`, and the request expires after an hour. Keep one
supervisor up on the host that has `GEMINI_API_KEY`:

```ini
# /etc/systemd/system/imoveis-backfill-serve.service
[Unit]
Description=Imoveis cloud backfill supervisor (consumes /admin/backfill/start)
After=network-online.target

[Service]
User=felipe
WorkingDirectory=/home/felipe/workfolder/imoveis
Environment=PYTHONPATH=src
EnvironmentFile=/home/felipe/workfolder/imoveis/.env.local   # GEMINI_API_KEY
ExecStart=/home/felipe/workfolder/imoveis/.venv/bin/python \
    scripts/dev/backfill_gemma.py --serve
Restart=always
RestartSec=10
KillSignal=SIGTERM

[Install]
WantedBy=multi-user.target
```

`Restart=always` matters: the supervisor survives a failing run on its own (a
refused or crashing run is logged and the loop keeps serving) and a Redis blip
on a poll costs one cycle rather than the process — but not a host reboot or an
OOM kill.

`systemctl stop` works at both levels. An idle supervisor clears its heartbeat
and exits, so `runner_present` goes false immediately instead of lying until the
key's TTL. A SIGTERM that arrives *during* a live run is first that run's
clean-stop signal — in-flight rows drain, the checkpoint stays intact — and the
supervisor then exits rather than going back to waiting, so the unit stops
within its own drain time instead of being SIGKILLed at `TimeoutStopSec`.

A pending start request is never spent on a run that cannot happen: while
another run holds the lease, or while `migrate-primary.sh` holds the primary
database, the supervisor leaves the request pending and says so — and says so
again if it expires (one hour) before the blocker clears.

Flags refused at parse time under `--serve`:

- `--force` — it would be carried into every API-requested run and re-enrich
  already-scored rows, spending the whole daily cloud budget on work already
  paid for.
- `--continuous` — reads as "run now", which is exactly what `--serve` does not
  do until the API asks.
- `--daily-budget`, `--concurrency`, `--tpm-limit`, `--min-interval` — the
  status endpoint reports these from `AppConfig` and cannot see the supervisor's
  argv, so an override would make the dashboard describe a run that is not the
  one executing. Set them in `configs/app_config.yaml` instead.

## Notes / Follow-ups

- **Operator-visible workflow change:** the start endpoint only records a
  request. A host-side `scripts/dev/backfill_gemma.py --serve` supervisor must be
  running (tmux/nohup/systemd, with `GEMINI_API_KEY` exported) for a start to
  actually launch a run. `runner_present=false` in the status body is how the API
  says nothing is listening; story 1.6 renders that.
- **Deliberate exclusions.** No stop endpoint — the epic's surface and UX-DR5's
  card are start/pause/resume, and CLI `--stop` stays the way to end a run. No
  coverage / throughput / ETA figure: that is story 1.4 and it is DB-derived, and
  the runner's Redis state must never become a second progress metric (FR-29). No
  UI (story 1.6).
- The wire state vocabulary stays English (`idle|running|paused|backing-off|blocked`);
  pt-BR rendering belongs to story 1.6.
- **A requested run that fails reports nothing the API can read (DW-28).** Once
  the supervisor consumes a request, `start_requested_at` goes null; a run that is
  then refused or crashes is logged host-side only, so the dashboard sees the
  request vanish and `active` never become true. The cases where the request would
  be *burned* are closed (a held lease and a live primary migration defer instead
  of consuming, and an expired deferred request is announced) — what remains needs
  a published `last_run` surface, designed together with story 1.6.
- **The audit trail has no actor (DW-29).** `log_audit_action` takes an action and
  a payload and nothing else, so the AD-6 trail cannot answer "who started this
  multi-day cloud run". Pre-existing and shared by every admin mutation in the
  file; fixing it is a schema change, not a story-1.5 patch.
- `consume_start()` uses `GETDEL` on any real client and falls back to
  get-then-delete (announced via the existing non-atomic warning) on doubles that
  lack it. Two supervisors on the fallback path could both consume one request;
  the single-instance lease still refuses the second run.
- Open ledger items are untouched by design — in particular **DW-20** (state
  decays to `idle` under one slow row) is *worked around* here by reporting the
  lease separately, not fixed.

### Review pass (patches applied after the first landing)

- **Budget pair is arithmetic, not two reads.** `build_status_snapshot` derived
  `remaining` from a second `budget.remaining()` round trip, so a live run
  reserving between the two reads put `consumed + remaining != limit` on the
  wire (and a rolling window in between produced a nonsense pair). It is now
  `max(0, limit - consumed)` off the single `consumed` read.
- **The polled status surface no longer scans the attempt ledger.**
  `quarantined_count()` is an `HGETALL` over one field per property ever
  attempted (~26k on a full pass) plus a sort — on an endpoint story 1.6 polls
  every few seconds with no rate limit. `build_status_snapshot(ledger=...)` is
  now optional, the API passes `ledger=None`, and `quarantined` is `null` on the
  wire. The CLI's one-shot `--status` still counts it; coverage telemetry is
  story 1.4's.
- **One derivation of the pending-request vocabulary.** New public
  `core.backfill_runner.pending_control_requests()`; the snapshot, the admin API
  and the CLI's `_pending_requests` all delegate to it (there were three copies).
- **`request_start`'s fallback keeps its stamp guarantee.** The "expired in the
  window" recovery write was a plain `SET`, so two callers racing that branch
  both took the honor-the-caller path and the second clobbered the first's
  `requested_at`. It is `SET NX` too now, and a lost race returns the existing
  request (`already_requested: true`).
- **A start that 500s leaves nothing queued.** The route now reads the pending
  pause/stop list, records the start, *then* clears the stale levels; anything
  failing after `request_start` triggers a best-effort `clear_start()` (guarded,
  never masking the original error, and never withdrawing a request that was
  already pending) before the 500.
- **An applied pause/resume is never reported as a 500.** The post-mutation
  snapshot is ~10 further Redis reads; a blip there used to turn an applied pause
  into "Internal server error" and the operator concluded it had not taken.
  `BackfillControlResponse.status` is now optional: a null status means the
  request *was* applied and only the status read failed — poll
  `GET /admin/backfill/status`.
- **Pause can cancel a pending start.** "Start, then Pause" (no supervisor
  running yet) left a pause the launching run discards at start-up via
  `clear_requests()`, so the run proceeded unpaused and the second command was
  silently void — and nothing could withdraw a start request. With a start
  pending and no lease held, pause now calls `clear_start()` as well and reports
  `cleared_start: true` (audited).
- **The 409 advises what the refused state allows.** Paused → "resume it
  (`POST /admin/backfill/resume`)", stale holder (last seen longer ago than two
  renewal intervals — see the follow-up pass below) → "it may be dead, or its
  provenance write may be failing", otherwise the original pause/stop advice.
  Every variant still names the owner and how long it has held the lease.
- **Liveness contract documented for story 1.6.** `BackfillStatusResponse` now
  documents `active` (the liveness signal), `state` (published, decays),
  `heartbeat_active` ("rows are being enriched right now" — deliberately false
  for a healthy paused run, which must not block `migrate-primary.sh`) and
  `runner_present` ("a lease holder or a waiting supervisor exists").
- **Supervisor hardening.** `--serve` now: survives a run that raises or exits
  (`SystemExit` code becomes the reported rc; the loop keeps serving, since the
  start request it consumed is already gone); validates scope + backend at
  start-up instead of beating a "ready" heartbeat it cannot honor; checks the
  lease *before* the destructive `consume_start()`, leaving a request pending
  (logged once, not per poll) while another run holds it; refuses `--serve
  --force`; and handles SIGTERM through the same clean path as Ctrl-C, re-armed
  after every supervised run so a `docker stop` never leaves the heartbeat set.
- **BUG (Low)**: `log_audit_action` swallows its own failure, so any admin
  mutation here can be applied with no audit row behind it — inherited from the
  existing helper, unchanged by this story. Fix hint: let it raise, or surface a
  counter, when AD-6 needs to be an actual guarantee.

### Follow-up review pass (bookkeeping must never overrule an applied mutation)

- **An unreachable audit database no longer fails a decided outcome.**
  `log_audit_action` guards only its *commit*; `SessionLocal()` itself raises when
  the database is down, and that call sat after the pause level was already in
  Redis and before the 409 was raised. A DB outage therefore told the operator
  their pause had failed while the runner was quietly halting, and swallowed the
  conflict that names the live run. Refusals and applied pause/resume now audit
  best-effort (`_audit_applied`, logged on loss); the state read that only picks
  the 409's wording is guarded the same way. A `start` is deliberately *not*
  best-effort — it queues a multi-day cloud spend AD-6 says must be recorded, so
  an unauditable start is rolled back rather than fired unrecorded.
- **A single dropped provenance write no longer reads as a dead run.** The lease
  renewer runs at `ttl/3` and its `last_seen` write swallows its own failure, so
  one lost write ages the stamp to `2*ttl/3` under a perfectly healthy run — and
  the old `ttl/2` threshold then told that operator to wait out an expiry the
  live renewer keeps pushing out. The threshold is now two renewal intervals and
  the wording keeps both readings open ("it may be dead, or running with a
  failing provenance write — check the host before waiting it out").
- **The supervisor stopped blaming expiry for a cancellation.** `pause` withdraws
  a pending start whenever no run holds the lease, so a deferred request can
  disappear because the operator cancelled it; the loop announced "expired —
  press Start again", prescribing exactly what they had just undone. It now names
  the request as gone (expired *or* cancelled) and prescribes nothing. The same
  announcement also fires when the blocker clears in the same poll the request
  vanishes — previously that case fell between the two branches and said nothing.
- **`requested_at` is coerced like `source`.** The start payload decoder tolerates
  anything it did not write, but published the raw `requested_at`; on a response
  model typed `Optional[str]` a foreign value (a number, an object) would fail
  response validation and turn every status poll into a 500.
- **Honest aggregator claims.** `build_status_snapshot` is the API's aggregator
  only — the CLI's `--status` still formats its own print-out, so the docstring's
  "`--status` and the API read the same function / can never drift apart" was
  false, as was "the CLI keeps passing its ledger" (no caller passes one). The
  prose now says what is true and names adopting the aggregator in `--status` as
  the open follow-up; the shared derivation that does exist is
  `pending_control_requests()`.
- **`docs/api.md` documents the wire contract story 1.6 codes against** — the
  nullable `status` (null means *applied*, poll `/status`), `cleared_start`,
  `cleared_stop`, `already_requested`, `discarded_requests` — and states the
  audit guarantee accurately rather than a blanket "audited".
- **Test-strength.** The auth-gate test asserted only that `router.dependencies`
  was non-empty, so swapping the gate for any other dependency kept it green; it
  now names `verify_admin_access`. The stale-holder test's single-value
  `parametrize` became a real boundary pair either side of the new threshold.
