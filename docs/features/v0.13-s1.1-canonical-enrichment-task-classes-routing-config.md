# Canonical enrichment task classes + per-task-class routing config — one enrichment vocabulary, validated at startup

> Feature branch: `feat/v0.13-s1.1-canonical-enrichment-task-classes-routing-config` · Story: `v0.13-s1.1` · Status: implemented

## Problem

Enrichment had no shared vocabulary of signal types — they lived as scattered `metrics_scoring.meta` keys (`"visual"`, `"sentiment"`, `"deal_verdict"`), columns (`embedding`, `stat_score`), and `enrichment_rerun.STAGES_*` constants — so routing, backfill scope, and coverage each risked inventing their own words. Backend selection was a single unconstrained scalar `ai.backend` (`str`, no validation) that, if set to `gemini`/`gemma`, would silently make **unmetered cloud calls on the live path** — the exact hazard AD-13 forbids. Misconfiguration failed mid-pipeline, not at startup.

## Approach

- **One canonical vocabulary in `core`.** New `src/core/enrichment.py` defines `EnrichmentTaskClass` (`visual`, `sentiment`, `deal_verdict`, `valuation`, `embedding`) and `EnrichmentBackend` (`ollama`, `lmstudio`, `gemini`, `gemma`) as `str` enums, plus `LOCAL_BACKENDS`/`CLOUD_BACKENDS` and the `is_cloud_backend`/`is_valid_backend`/`is_valid_task_class` helpers. Framework-free, no `adapters`/`api` imports (AD-1) — the correct dependency direction is everything → `core`.
- **`AppConfig` owns the routing map.** `AIConfig.enrichment_routing` (task class → backend) is the single source of truth that live routing (story 1.2), backfill scope (story 1.3) and coverage (story 1.4) will consume; it supersedes the scalar `ai.backend`. Default (and shipped YAML) route every task class to local Ollama.
- **Fail-fast at config load.** The file's first `@model_validator(mode="after")` rejects: an unknown/`cloud` scalar `ai.backend` (cloud is backfill-only — AD-13), an unknown routing task class or backend, and a **partial** routing map (it must cover every task class, so a missing entry is a clear config error rather than a downstream `KeyError`). `ValueError`s are wrapped by `load_config` into `ConfigError`, preserving the existing fail-fast path. Cloud backends stay legal as routing *values* (backfill-eligibility), illegal as the live-path scalar.
- **Scope held tight:** live-path client routing, backfill scope, and coverage adoption of the enum are their own stories (1.2/1.3/1.4). `src/adapters/ai/client.py` is intentionally untouched here — the existing BIN-248 gemma backfill builds its client directly (`_build_client`), independent of `ai.backend`, so the new scalar rejection does not affect it.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh fast    # lint + unit (test_enrichment.py + test_config.py branches)
   ```
2. Manual sanity:
   - `PYTHONPATH=src python -c "from infra.config import get_config; print(get_config().ai.enrichment_routing)"` → all task classes → `ollama`.
   - Set `ai.backend: gemini` in a config and load → `ConfigError` naming `ai.backend` (cloud is backfill-only).
   - Set a partial `ai.enrichment_routing` (one task class) → `ConfigError` naming the missing task classes.
