# Migration ↔ backfill mutual exclusion — no new writer starts against a migrating primary DB

> Feature branch: `bmad-loop/20260810-193244-9de6/dw-migration-backfill-mutual-exclusion` · Story: `v0.13-fu6` · Status: implemented

## Problem

The guard that keeps `scripts/agent/migrate-primary.sh` and the Gemma backfill
runner off the primary database at the same time was check-then-act, and leaked
in both directions:

- **DW-3** — the script read the advisory heartbeat `backfill:gemma:active`
  once, reported "safe to migrate", and then ran `alembic upgrade head` with
  nothing holding the window. A runner that started anywhere inside that gap
  enriched rows against a schema mid-upgrade.
- **DW-4** — `_go`'s `finally` clears the heartbeat before `_sleep_for_reset`,
  so a runner sleeping out its RPD window reads as *idle* to the guard while
  still holding its Redis lease. The migration is waved through, the window
  resets, and the runner wakes up writing into the upgrade.

Same root cause: there was no key the runner could honor, only a signal the
script sampled.

## Approach

- Add a **migration-held** key, `backfill:gemma:migrating`. `migrate-primary.sh`
  takes it with `SET NX EX` and a per-invocation token, and releases it from an
  `EXIT` trap by token compare-and-swap.
- **Set-then-check on both sides** is the whole correctness story. The script
  acquires `:migrating` *before* it probes `:active`; the runner beats `:active`
  *before* it reads `:migrating`. If the runner does not see `:migrating`, its
  read happened before the script's write, so its heartbeat was already written
  when the script probed — and the script refuses. Symmetric in the other
  direction. Both may refuse in a narrow interleaving; that is safe, and
  `--continuous` recovers by waiting.
- **Pass entry is the wake-up gate.** Every `--continuous` cycle funnels through
  `_run` → `_go`, so checking there (right after `heartbeat.beat()`) is exactly
  "at wake-up from `_sleep_for_reset`, before it resumes launching rows".
  `_sleep_for_reset` is deliberately unchanged — a sleeping runner writes
  nothing, so only the resume needs gating.
- The core half stays framework-free and injectable (AD-1): `MigrationGate` is a
  Redis-duck-typed read-only class beside `Heartbeat`/`BackfillLease`, and
  `run_backfill` takes a plain `Callable[[], bool]` exactly like
  `is_quota_error`. It reads with `get`, not `exists` — the key always carries a
  non-empty token, so the refusal can name the holder.
- The runner **never** deletes or expires the key: it belongs to the migration
  and self-clears on its own TTL, the same contract as `:active` and `:lease`.
- A blocked pass is reported as `migration_blocked`, never `stopped` and never a
  stall — nothing was launched and the checkpoint is untouched. `--continuous`
  waits up to `backfill.migration_wait_seconds` for the key to clear and resumes
  with a fresh pass; past that it exits 8 for the operator. A stop request or a
  lost lease during that wait is reported as itself (exit 6 / exit 7), never as a
  migration. The bound covers one **stretch of consecutive blocked cycles** —
  they share the budget, so a key that never clears cannot be waited on forever —
  and any cycle that actually runs starts it over. A single lifetime budget looks
  tighter but breaks the mode it exists for: a runner up for days would spend it
  on its first migration and then refuse to wait a single second for the next.
- While it waits, the runner publishes control state `blocked` — a member added
  for this, because `backing-off` means "the provider refused on quota" in this
  vocabulary and would send an operator (and stories 1.5/1.6) to the Gemini
  dashboard over a migration running in their own terminal. It publishes from the
  first poll, not one refresh interval in, so `--status` never shows a live,
  lease-holding runner as `idle`; and a run that exits 8 does not stamp
  `backing-off` on its way out. `--status` also reports the migration key itself
  ("primary migration: IN PROGRESS — &lt;token&gt;"), which is the operator's direct
  answer to "why is the runner launching nothing?".
- **Scope of "one writer": launching, not draining.** The gate stops the runner
  from *starting* new rows — at pass entry, at the launch-loop head and again
  right after `sem.acquire()` (that wait can be minutes long). Rows already
  in flight when the migration is detected deliberately finish and keep
  writing, exactly like the lease-lost path: cancelling them mid-enrichment
  would leave half-written scores, which is worse than a few seconds of overlap.
  So the guarantee is "no *new* writer starts against a schema mid-upgrade",
  not "zero writes during the upgrade". `migrate-primary.sh` refusing on a live
  `:active` heartbeat is what keeps that overlap from ever being the normal case.
- The script **renews** the key while `alembic upgrade head` runs: a background
  watchdog re-`EXPIRE`s it by owner-token CAS every `MIGRATE_LOCK_TTL_SECONDS/3`
  and is killed from the same `EXIT` trap that releases the key. Without it, an
  upgrade longer than the TTL silently lost mutual exclusion halfway through and
  kept writing DDL — DW-3 again, on a clock. A failed CAS warns loudly on stderr
  and never kills alembic: a half-applied migration is worse than an unguarded
  one. The script re-checks ownership once alembic returns — **on the failure
  path too**, since a half-applied upgrade is exactly when "was this guarded?"
  matters — and warns if the key was not still ours.
- The watchdog checks that the script it renews for is still alive, every second.
  A SIGKILLed migration runs no `EXIT` trap, so an orphaned watchdog would keep
  re-`EXPIRE`ing `:migrating` **forever**: the key documented to self-clear on its
  TTL would block every backfill until somebody found and killed a stray
  background shell — and the contract says never to delete it by hand.
- Dry runs are not gated *and take nothing*: `--dry-run` on the runner writes
  nothing, and `migrate-primary.sh --dry-run` only **probes** both keys (is
  `:migrating` free, is `:active` alive) and exits 0. Taking the lock for the
  second or two a dry run costs would bounce a runner starting in that window
  to exit 8 for a command that by contract changes nothing.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh backend
   ```
2. Against the live primary stack — the runner must refuse while the key is held:
   ```bash
   redis-cli -p "$REDIS_PORT" set backfill:gemma:migrating tok ex 60
   PYTHONPATH=src python scripts/dev/backfill_gemma.py --limit 1   # exit 8, nothing enriched
   redis-cli -p "$REDIS_PORT" del backfill:gemma:migrating
   ```
3. From the primary checkout, the dry run *probes* the guard and writes nothing
   at all:
   ```bash
   bash scripts/agent/migrate-primary.sh --dry-run
   redis-cli -p "$REDIS_PORT" get backfill:gemma:migrating   # (nil) — never set
   ```

## Notes / Follow-ups

- A migration killed hard (SIGKILL, so the `EXIT` trap never runs) leaves
  `backfill:gemma:migrating` behind; it self-clears within
  `MIGRATE_LOCK_TTL_SECONDS` (default 1800s, overridable in the environment for
  an upgrade expected to run longer — the watchdog renews on `TTL/3`). Never
  delete it manually — same contract as `backfill:gemma:active` and
  `backfill:gemma:lease`.
- Raising `MIGRATE_LOCK_TTL_SECONDS` above `backfill.migration_wait_seconds`
  (default 1800) is safe: the exclusion still holds, a blocked `--continuous`
  runner simply exits 8 instead of resuming, and an operator restarts it.
- `migrate-primary.sh` still hardcodes `localhost`, `db=0` and the literal
  `backfill:gemma:*` key names, while the runner resolves its Redis from
  `REDIS_URL` and its prefix from `backfill.redis_prefix`. A parity test fails if
  the *prefix* default drifts, but an operator who points `REDIS_URL` at another
  host or database — or changes the prefix — silently disables **both** halves of
  the exclusion with every test still green. Pre-existing for `:active`; the new
  key inherits it.
- **BUG (Medium)**: the runner-first half of the exclusion proof assumes `:active`
  is still visible when the script probes it, but the heartbeat has a 300s TTL and
  is beaten only when a row *finishes* — nothing ticks it while a row is in
  flight. A single enrichment slower than 300s (three cloud calls with client-side
  429 retries) lets `:active` lapse under a live writer, so the script reads
  "idle" and migrates alongside it. Pre-existing cadence, not introduced here, but
  it caps what this change can guarantee — fix hint: tick the heartbeat on a timer
  (or from `_tick_lease`, which already runs on every worker `finally`) rather
  than only per completed row.
- **BUG (Medium)** — **ungated writer:** `scripts/dev/backfill_listing_descriptions.py:213` runs its
  own, unrelated `run_backfill` and commits descriptions to the primary DB
  (`session.commit()` per row). It honors neither `backfill:gemma:active` nor
  `backfill:gemma:migrating`, so running it during a migration writes into the
  upgrade. Wire the gate (or at least the heartbeat) in if it ever becomes more
  than an occasional manual command. `core.backfill_runner.run_backfill` itself
  has exactly one caller today — this runner; story 1.5's admin API does not
  exist yet, and whoever builds it must pass `is_migrating`.
- Resolves deferred-work entries DW-3 and DW-4.
