# Corpus repair applied and verified — the fabricated-score repair is confirmed on the primary corpus

> Feature branch: `feat/v0.14-s1.5-corpus-repair-verified` · Story: `v0.14-s1.5` · Status: implemented

## Problem

v0.13 story 2-7 shipped a one-off migration (`f3a7c81d5e42`) that nulls `ai_score` on `metrics_scoring` rows poisoned with fabricated scores, but shipped it un-applied: applying it to the primary `realestate` database is an operator step. Until someone confirmed it had landed, Story 1.6 (cohort price-per-m2 percentiles) could not start, because percentiles would be computed over scores known to be fabricated. The old key sat at `awaiting-operator` from 2026-08-13 and was carried into v0.14 as this story.

## Approach

- Verification only. No code, no migration and no schema change ship with this story.
- The check is read-only: the recovery query from `docs/features/v0.13-s2.7-corpus-repair-fabricated-scores.md` (the migration's own predicate run as a `SELECT`), plus the primary's `alembic_version`, both read in a read-only session.
- `migrate-primary.sh` was probed with `--dry-run` and not run for real, because the primary was already at head.
- The forensic predicate stays in the v0.13 repair artifact and its feature doc. Nothing in `src/` references it.

## Evidence (2026-10-07, primary `realestate`)

| Check | Result |
|---|---|
| `alembic_version` on the primary | `f3a7c81d5e42` — the repair migration, which is also the current head |
| `marker_rows` (rows carrying the fabrication signature in `meta`) | 1193 |
| `still_poisoned` (marker rows with a non-null `ai_score`) | **0** |
| `repaired_or_never_scored` (marker rows with a null `ai_score`) | 1193 |
| `migrate-primary.sh --dry-run` | `backfill:gemma:migrating` free, no `backfill:gemma:active` heartbeat |
| `backfill_gemma.py --status` | enriched 26,947 of 196,237 enrichable; remaining 169,290; quarantined 0; runner idle, lease free, last run 2026-08-13 |

**Count the repair touched.** The repair writes no per-row record, and it was not applied through `migrate-primary.sh`, so the migration's own log line (`nulled N fabricated ai_score metrics rows (M of them …)`) was never captured. The exact `N` and `M` are therefore not recoverable. What the corpus shows is an upper bound: at most 1193 `metrics_scoring` rows were nulled, since all 1193 marker rows now carry a null `ai_score` and a marker row that was never scored is indistinguishable from a repaired one.

**How it got applied.** Most likely through `scripts/start.sh`, which runs `alembic upgrade head` against the primary without the migration lock and prints migration output only on failure. This is DW-32, predicted in the v0.13 feature doc and closed by Story 1.4.
