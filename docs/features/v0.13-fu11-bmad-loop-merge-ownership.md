# bmad-loop merge ownership — explicit finish-feature refusal + gate-binding carve-out

> Feature branch: `feat/v0-13-fu11-bmad-loop-merge-ownership` · Story: `v0.13-fu11` · Status: implemented

## Problem

`_bmad/custom/bmad-dev-auto.toml` told every loop-driven dev session that
"finishing is ONLY `finish-feature.sh`", but the bmad-loop orchestrator owns
merge-back for its `bmad-loop/<run>/<story>` worktree branches — it
squash-merges into `main` itself after its review pass (`.bmad-loop/policy.toml
[scm]`). `finish-feature.sh` correctly refused those branches, but only with
the generic "not a valid conventional type prefix" error. Every Epic 3 dev
session hit the contradiction, burned time re-deriving "the orchestrator merges
this, by design" from the script source (one session spent ~35 min on it), and
parked the conclusion in per-story operator notes instead of a durable rule.
Letting the gate proceed would be worse: it would bypass the orchestrator's
review pass, tear down a worktree the orchestrator owns, and delete the branch
out from under its merge step, desyncing the run.

## Approach

- Keep the refusal (the two merge machineries must never race on one branch)
  but make it self-explanatory: a dedicated check in `finish-feature.sh` names
  the orchestrator and states what finishing means on such a branch.
- Fix the instruction at its source: the dev-auto gate binding now carries the
  carve-out, so loop sessions stop rediscovering it.
- Record the rule in every place a future session looks: CLAUDE.md, the Cursor
  mirror (sync rule), and `docs/harness-troubleshooting.md`.
- Lock both sides with a regression test: the refusal fires with the explicit
  message, and `bmad-loop` never appears in `VALID_BRANCH_TYPES` (the
  explicitly wrong "fix").

## Notes / Follow-ups

- Deliberately NOT done: adding `bmad-loop` to `VALID_BRANCH_TYPES` (would let
  the gate race the orchestrator), and any change to bmad-loop itself — the
  orchestrator's merge machinery is upstream tooling, not project code.
- Optional hardening left open: `.bmad-loop/policy.toml [verify] commands` is
  empty, so the orchestrator's merge relies on session discipline (the skill
  running `validate.sh all`) rather than a deterministic gate. Setting
  `commands = ["bash scripts/agent/validate.sh all"]` would close that at the
  cost of minutes per story.
- The same session that shipped this also cleared the operator debt this issue
  created on stories 3-2/3-3/3-4 (validate re-run + stranded-merge push +
  `bmad-loop confirm`).
