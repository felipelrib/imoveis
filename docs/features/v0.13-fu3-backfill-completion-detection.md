# Backfill completion detection and non-enrichable accounting — the Gemma backfill can now tell when it is actually done

> Feature branch: `feat/v0.13-fu3-backfill-completion-detection` · Story: `v0.13-fu3` · Status: implemented

## Problem

The resumable Gemma backfill runner (BIN-248 / BIN-267 / BIN-269 / v0.13-fu2) could not
recognise its own completion, and had no way to stop chasing rows it can never score.

**1. Completion detection was dead code.** `_run_continuous()` measured progress with
`_remaining()` = `total properties − enriched (ai_score > 0)`. But the runner only ever
fetches **active** rows (`fetch_candidate_rows(mode=missing, active_only=True)`). Measured
on the primary DB, 2026-08-05:

| Bucket | Count |
|---|---|
| total properties | 26,226 |
| enriched (`ai_score > 0`) | 7,626 |
| **active** + un-enriched (the real work queue) | **18,106** |
| **inactive** + un-enriched (never fetched) | **494** |

Those 494 inactive rows keep `total − enriched` permanently ≥ 494, so:

- `if remaining == 0: print("Backfill complete")` could **never fire** — dead code.
- A finished run instead fell through the safety valve and printed
  `Stopping: 494 remaining but no progress this cycle`, **exit 0** — a success code
  carrying a message that implies work remains.
- If the last productive cycle also exhausted the daily budget, the loop reached the
  sleep branch first and slept **~24h** before discovering an empty queue.
- `--status` reported `remaining 18,600` instead of 18,106, inflating the ETA.

**2. Nothing retired unworkable rows.** `run_backfill` counts an error and deliberately does
*not* checkpoint the row, so `--continuous` re-fetches and re-attempts the same failing rows
every cycle, burning RPD/TPM indefinitely. A row can also *succeed* and still come back:
`mode_is_missing_ai` treats a falsy `ai_score` as un-enriched, so an enrichment landing on
`0.0` re-queues itself forever.

**3. The photo gate was never applied.** The runner called `fetch_candidate_rows` directly and
skipped `evaluate_candidate`, so a gallery-less listing would be "enriched" from zero images.
(No row is currently affected — all 18,106 queued rows have 8+ images — but the gate is the
thing that stops it, and it was absent.)

## Approach

**Measure the queue, not the table.** A new `QueueCensus` value object holds the honest
accounting, with `candidates` = what `fetch_candidate_rows` would actually return:

```
remaining      = candidates − blocked_no_photos − quarantined
enrichable     = enriched + remaining          ← the denominator to quote a human
non_enrichable = total_properties − enrichable ← inactive + gate-blocked + retired
is_complete    = remaining == 0
```

On today's data: `enriched 7,648 / enrichable 25,732 (29.7%)`, `remaining 18,084`,
`non_enrichable 494`. The 26k total is still reported, but as context — never as the
denominator, because ~1.6k of it is delisted stock the pipeline is not trying to score.

`_census()` computes this in one SQL pass mirroring the candidate query; its `photos`
expression counts non-blank strings exactly like `core.photo_gate.count_photos`, so the SQL
census and the in-process partition agree on which rows are gate-blocked.

**Retire rows that never leave the queue.** `AttemptLedger` is a Redis-backed per-property
counter (`backfill:gemma:attempts` + `:last_error`, 30-day TTL refreshed on write). It counts
**attempts, not just errors** — that is what catches the "enriched to 0.0 and re-queued" shape
as well as the deterministic-failure shape. At `max_attempts` (default 3, `backfill.max_attempts`
/ `--max-attempts`) the row is quarantined: skipped for free, listed in the closing banner with
its last error, and excluded from `remaining`. `--reset-quarantine` releases them all.

A row that enriches normally leaves the candidate set and never reaches the ceiling, so the
ledger costs nothing in the healthy path.

**Filter before spending.** `partition_candidates()` splits fetched rows into `workable` /
`blocked_no_photos` / `quarantined` — applying the photo gate the runner had been skipping —
and only `workable` rows reach `run_backfill`. Each row lands in exactly one bucket, so the
counts sum back to the input and nothing is double-counted.

**Make the ending impossible to miss.** `--continuous` closes with a banner and a distinct
exit code:

| Code | Meaning |
|---|---|
| `0` | complete — candidate queue drained, nothing retired |
| `3` | **stalled** — work remains but a full cycle made no progress |
| `4` | complete, but N rows were quarantined un-enriched |

```
════════════════════════════════════════════════════════════════════
  BACKFILL COMPLETE
  enriched 25,732 / enrichable 25,732 (100.0%)
  remaining 0 · non-enrichable 494 of 26,226 total
    (inactive/unfetched 494 · photo-blocked 0 · quarantined 0)
  cycles 7 · elapsed 5d 22h · enriched this run 18,106 · errors 12
════════════════════════════════════════════════════════════════════
```

The loop now checks `census.is_complete` **before** the budget branch, which is what stops a
run that spent its last budget on the last row from sleeping out the remaining ~24h. The
budget-exhausted-with-zero-progress case still sleeps (a spent window is not a stall) — that
distinction is pinned by a test, since collapsing the two conditions silently breaks resume.

### Alternatives considered

- **`notify-send` desktop alert** — not installed on this WSL2 box.
- **Sentinel file / `--on-complete <cmd>` hook** — deferred. Exit code + banner covers the
  tmux-attached workflow in use; the launcher can add a hook later without touching Python.
- **Deleting the ledger entry on success** — rejected: it would reset the counter for a row
  that succeeds but stays a candidate, restoring the infinite loop.

## How to Test

1. `bash scripts/agent/validate.sh all`
2. Honest denominator against the live DB (read-only; safe during a running backfill):
   ```
   DATABASE_URL="postgresql://imoveis:imoveis_local_dev@localhost:5433/realestate" \
     PYTHONPATH=src .venv/bin/python scripts/dev/backfill_gemma.py --status
   ```
   Expect `enriched / enrichable` against ~25.7k (not 26,226) and `remaining` ≈ 18.1k
   (not 18.6k), with `non-enrichable 494` broken out.
3. Completion path without a live run — the unit suite drives it:
   `.venv/bin/python -m pytest src/tests/unit/ -k backfill -q`
4. Quarantine round-trip: after a run with failures, `--status` lists the retired rows and
   their last error; `--reset-quarantine` releases them.

## Notes / Follow-ups

- The live run in `/home/felipe/backfill-run` is pinned to an older commit and **keeps the old
  behaviour until restarted**. It is mid-pass and losing it costs only the current property
  (the checkpoint is in Redis), but there is no urgency: the old code's failure mode only
  bites at the very end of the ~7-day pass. Update with
  `git -C /home/felipe/backfill-run fetch origin && git -C /home/felipe/backfill-run checkout --detach origin/main`.
- 5,820 active rows carry `visual`/`sentiment` meta but a NULL `ai_score` (written
  2026-07-27, before the runner existed). They are legitimately re-queued and the backfill
  will score them properly — no action needed, but they are the exact shape the attempt
  ledger exists to catch if a future pipeline change starts leaving them at 0.
- The quarantine banner truncates its listing at 20 rows; the full set is in the Redis hash
  `backfill:gemma:attempts`.
- `_census` runs two extra aggregate queries per cycle (~200ms on 26k rows). Negligible against
  a cycle that takes hours, but it is per-cycle work, not per-property.
