# Transport-storm quota classification — a throttle that arrives as connection resets no longer burns a row's attempts

> Feature branch: `bmad-loop/20260810-193244-9de6/dw-gemini-transport-quota-classification` · Story: `v0.13-fu8-gemini-transport-quota-classification` · Status: implemented

## Problem

`GeminiClient.chat_completions` classified quota on exactly one path: the HTTP
one. When the provider answered — 429, or any status with a quota-shaped body —
`_is_quota_response` tagged the failure as `AIQuotaExhaustedError`, and
`core.backfill_runner.is_quota_exhausted` recognised it, so `run_backfill` rolled
the row's attempt back and paused instead of charging it.

The transport arm did not. `except (aiohttp.ClientError, asyncio.TimeoutError)`
re-raised the raw exception untagged on the final attempt, so:

- `is_quota_exhausted` did not match (no flag, no class name, and "connection
  reset by peer" hits none of `_QUOTA_MARKERS`),
- `_worker` took the hard-error branch,
- and the `AttemptLedger.record_attempt` charged *before* launch stood.

A throttled free-tier project does not always answer 429. Past the ceiling the
endpoint can simply stop responding, and the refusal reaches us as connection
resets or timeouts. The row is charged its `AttemptLedger.record_attempt` before
launch either way, so every row attempted inside that window burned one of its
`backfill.max_attempts` — three of them and the row is quarantined, retired
unenriched until an operator runs `--reset-quarantine`. Perfectly good rows,
retired by a condition that had nothing to do with them. That is deferred-work
entry **DW-7**.

The visual and sentiment stages have a second, worse shape of the same bug.
`analyze_visuals` / `analyze_text` catch `Exception`, call `_reraise_if_quota`
— which only lets a *flagged* quota error through — and otherwise return a
fabricated `0.5`. An untagged transport storm on those stages therefore did not
surface as a row error at all: the 0.5 was persisted, the row counted as
processed, and `mode=missing` would never re-queue it. Tagging the storm is what
routes it to the runner's back-off instead.

## Approach

- **Two independent conditions, both over-strict.** A throttle and an outage
  look identical at the socket, so the inference fires only when (a) *every*
  attempt of the call died in transport with the *same* `(type, truncated
  message)` signature, and (b) the provider itself stated a 429/quota refusal
  within `ai.gemini_transport_quota_window_seconds`. Anything else re-raises the
  original exception and the runner charges the row, exactly as before.
- **Why "identical" and "every attempt".** Condition (a) excludes the two
  commonest non-throttle shapes: a connect error decaying into a timeout (mixed
  signatures), and a call that saw a real HTTP response before the sockets died
  (caught by the `saw_http_response` flag; the `len(signatures) == max_retries`
  condition is defence-in-depth against a future change to the retry loop, and
  is redundant with that flag as the loop stands today).
  A mixed sequence *during* a genuine throttle is therefore misclassified as an
  outage. That is accepted: it is the status quo, costing one wasted attempt,
  whereas the opposite error masks a real provider outage across every row of a
  multi-day run.
- **Why a ≥2 floor.** With `max_retries=1`, "all attempts failed identically" is
  vacuously true for a single blip. `_MIN_TRANSPORT_FAILURES_FOR_QUOTA = 2` keeps
  the word *repeated* honest; production builds the client with the default
  `max_retries=5`, so the floor costs nothing.
- **Recency is monotonic, cancellable, and cross-task by design.**
  `_note_rate_limit_hit()` stamps `time.monotonic()` at both existing 429 sites
  (the retry hit and the terminal one). A wall clock was rejected: an NTP step
  must not license or revoke the inference. A **successful response clears the
  stamp** — a paced free-tier run collects retried 429s routinely and recovers
  from them, and without this each one would license the inference for a full
  window, so an unrelated local network drop would read as quota. The stamp is
  per-client, and one long-lived client serves every backfill row of a pass
  (`scripts/dev/backfill_gemma.py`), so a 429 seen by row A licenses the
  inference for row B's storm — the quota is per-project, not per-call. Note the
  shipped default is `backfill.concurrency: 1`, so "cross-row" normally means
  *successive* rows on one client; rows are only genuinely parallel when an
  operator raises `--concurrency`.
- **Recency is judged at the first failure of the call, not at its end.** Five
  attempts at `ai.timeout` (120 s) each, plus backoff, can outlive the whole
  300 s window. Judging at the end would mean a *timeout* storm — half of what
  DW-7 describes — could never qualify, however obviously throttled the account.
- **"No attempt reached the endpoint" is tracked explicitly.** A body read
  (`response.json()` / `.text()`) can raise `ContentTypeError` or
  `ClientPayloadError`, and both are `aiohttp.ClientError` subclasses, so a fully
  answered request lands in the transport arm and leaves no gap in the signature
  list. A separate `saw_http_response` flag is what actually keeps an HTML
  throttle page or a truncated body out of the inference.
- **The window is config, not a constant.** `AIConfig.gemini_transport_quota_
  window_seconds` (`Field(default=300.0, ge=0.0, le=3600.0, allow_inf_nan=False)`)
  is threaded to the client at all three construction sites (`create_ai_client`,
  the backfill CLI's `_build_client`, the A/B harness). The hour ceiling matters:
  a day-wide window would let one 429 license the inference for the rest of the
  day, so a dead key or a firewall change would stop producing row errors
  entirely. `0` disables the inference entirely and
  every transport failure is a hard row error again — the escape hatch if this
  heuristic ever misreads a real outage. The client floors a negative value
  rather than rejecting it: the bound belongs to the config schema, and a
  hand-built client must not become a second gate.
- **`rate_limit_hits` still means "the provider said 429".** The A/B harness and
  the CLI progress hook report it as observed evidence of the ceiling, so an
  inferred throttle must not inflate it. Inferences are counted separately in
  `transport_quota_inferences`.
- **Auditable, because masking an outage is the real risk.** The inference bumps
  its own counter, writes a `last_error` that cannot be mistaken for a plain
  `connection:` failure, and logs `gemini_transport_quota_inferred` at WARNING
  naming the repeated signature, the attempt count and the window it was judged
  against. The backfill CLI's progress hook reports
  `transport_quota_inferences` beside `rate_limit_hits`, so a pass that backs off
  "on quota" with a flat `rate_limit_hits` explains itself instead of looking
  contradictory. A window the constructor had to correct — floored from a
  negative value, capped at the 3600 s ceiling, or resolved to "off" from
  `inf`/`NaN` — is logged as `gemini_transport_quota_window_clamped`; silently
  disabling *or* silently unbounding a safety feature is not acceptable.
- **The cross-layer contract is unchanged.** `src/core/backfill_runner.py` is
  untouched: `AIQuotaExhaustedError` (duck-typed via `is_quota_exhausted`, AD-1 —
  core never imports adapters) stays the only signal core reads, and the raised
  message keeps a `_QUOTA_MARKERS`-matching phrase ("quota exhausted") so the
  runner's text net still backstops the flag.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh backend
   bash scripts/agent/validate-ai.sh   # merge-blocking gate for an AI-client change
   ```
   (From WSL, `validate-ai.sh` needs
   `OLLAMA_HOST=http://$(ip route show default | awk '/default/{print $3}'):11434`.)
   The classifier branches are pinned in
   `src/tests/unit/test_ai_quota_propagation.py`; each direction was verified to
   fail with its condition removed (see Notes).
2. Against the live primary stack — during a `python scripts/dev/backfill_gemma.py`
   pass that reaches the free-tier ceiling, a throttle that surfaces as resets
   logs the inference, and the affected properties must **not** show up in the
   quarantine report afterwards:
   ```bash
   grep gemini_transport_quota_inferred <backfill log>
   python scripts/dev/backfill_gemma.py --status
   ```
3. To turn the inference off (every transport failure becomes a hard row error
   again), set `ai.gemini_transport_quota_window_seconds: 0` in
   `configs/app_config.yaml`.

## Notes / Follow-ups

- Resolves deferred-work entry **DW-7**. The review passes opened **DW-12** (the
  in-call `429`-then-silence transition is still declined), **DW-13** (once
  the provider answers nothing at all, no new 429 refreshes the licence, so a
  sustained silent throttle charges rows again after the window lapses),
  **DW-14** (the licence cannot survive a `--continuous` cycle boundary — see
  the per-pass note below) and **DW-15** (the recency comparison is one-sided, so
  a 429 observed *after* a storm began licenses it however much later it lands).
  Together DW-12/DW-13/DW-14 bound how much of DW-7 this change actually closes:
  the classifier is correct and pinned, but the licence it needs is established
  far less often than the classifier alone suggests.
- Each condition was mutation-checked against the new tests: restoring the bare
  `raise` in the transport arm fails the five inferred-quota tests; dropping the
  recency check fails the outage / stale-throttle / zero-window / negative-window
  tests (and the pre-existing
  `test_connection_error_exhausted_raises_and_records`); dropping the identical-
  signature condition fails the mixed-shape tests; dropping the ≥2 floor fails
  the single-attempt test; counting a 429 without stamping the clock fails the two
  recency tests; dropping the `saw_http_response` guard fails the unreadable-body
  test; judging recency at call end instead of the first failure fails the slow-
  storm test; not clearing the stamp on a 200 fails the cancelled-throttle test;
  and truncating the signature before comparison fails the long-shared-prefix
  test. Three of the four review-added guards are isolated by exactly one test;
  the fourth, `len(signatures) == max_retries`, is **not** — deleting it keeps
  the suite green, because `saw_http_response` already short-circuits the
  post-HTTP-retry storm. It is kept as defence-in-depth against a future retry
  loop that could leave a gap without an HTTP response, not as a live guard.
  The follow-up pass added six more, each mutation-checked the same way:
  clamping only the low end of the window fails the over-wide/non-finite test;
  logging the traceback before classifying fails the "no hard-error traceback"
  test; gating the progress tick on the 25-row milestone alone fails the
  before-the-first-milestone test; and dropping the `_build_client` kwarg fails
  the routing-map test (whose expected window is deliberately *not* the client's
  own default, or the fallback would satisfy the assertion); and beating the
  lease inside the same `try` as the progress log fails the failed-beat test.
- **Accepted false negative:** a real throttle whose storm has mixed exception
  shapes — a connect reset that becomes a timeout — is still read as a hard
  error. On the deal-verdict stage that charges the row one attempt; on the
  visual and sentiment stages it persists a fabricated `0.5` (see Problem), which
  is the more expensive miss. Widening the signature test (comparing only
  exception *types*, or accepting a majority) would also widen the
  false-positive surface, which is the failure mode that matters: masking a
  genuine outage silently suppresses errors for every row of a multi-day run.
  Deliberately left narrow.
- **Accepted false positive, and its real blast radius:** a provider outage that
  begins within `transport_quota_window_seconds` of a real 429 — plausible during
  a throttled run — is read as quota. This is *not* a one-row event.
  `run_backfill` sets both `quota_exhausted` and `budget_exhausted`, breaks the
  launch loop and publishes `BACKING_OFF`, so the whole pass stops; and because
  `budget_exhausted` is set, the CLI's `processed == 0 → exit non-zero` stall
  detector does not fire, turning a loud outage into repeated silent
  `quota_backoff_seconds` sleeps. What bounds it is the 300 s stamp expiry (and
  now the clear-on-success rule): once the stamp lapses the next storm is a hard
  error again. The WARNING and `transport_quota_inferences` are what make it
  visible; `0` disables the inference outright.
- **The stamp is per-*pass*, not merely per-process — so the inference is much
  narrower in practice than the classifier alone suggests.** `_build_client` runs
  inside `_run` (`scripts/dev/backfill_gemma.py`), and `--continuous` calls `_run`
  once per cycle, so `last_rate_limit_at` starts `None` on **every cycle**, not
  just after an operator restart. Worse, `backfill.quota_backoff_seconds` (900 s)
  is three times the 300 s window, so the pass that follows any quota back-off
  can never inherit a live licence even in principle. For the inference to fire,
  a single pass must observe a *retried* 429 (a terminal one stops the pass), not
  see a 200 afterwards (which clears the stamp), and then hit a full identical
  storm within 300 s. The headline DW-7 shape — an endpoint that simply stops
  answering from the start of a pass — produces no 429 at all and therefore still
  burns attempts. Tracked as **DW-14**; persisting the stamp (in the backfill
  pacer's Redis namespace) was rejected as a second consumer of quota state.
- `_is_quota_response`, `_QUOTA_BODY_MARKERS`, `_sleep_backoff`, `AttemptLedger`,
  and `src/core/backfill_runner.py` are untouched. The HTTP retry ladder is
  touched in three places, all bookkeeping rather than control flow: the two
  `rate_limit_hits += 1` sites became `_note_rate_limit_hit()` (sanctioned by the
  spec's Code Map), and the 200 branch gained `_clear_rate_limit_recency()` (a
  review patch, recorded in the spec's Change Log). No status, retry decision or
  backoff in the ladder changed.
- The A/B harness's report table shows `rate_limit_hits` and `last_error` but not
  `transport_quota_inferences`; an inference is visible there only through the
  distinguishable `last_error` and the WARNING. Adding the counter to the report
  is cosmetic and out of scope here. Note also that `_run_arm` gathers its samples
  without `return_exceptions`, so an inferred quota error now aborts that arm
  where an untagged storm used to degrade to a `0.5` — the same thing an
  HTTP-path quota refusal has done since v0.13-s1.3, and the correct outcome for
  an arm whose provider is refusing it.
- `create_ai_client`'s `backend in ("gemini", "gemma")` branch is unreachable in a
  valid configuration — `AIConfig._validate_backends` rejects a cloud scalar
  backend outright ("cloud is backfill-only") — so the live Celery enrichment path
  cannot see this change. The backfill CLI, which resolves its cloud client from
  `ai.enrichment_routing`, is the only production consumer.
