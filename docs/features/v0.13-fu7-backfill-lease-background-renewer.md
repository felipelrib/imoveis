# Background lease renewer — the backfill lease survives a row slower than its TTL

> Feature branch: `bmad-loop/20260810-193244-9de6/dw-backfill-lease-background-renewer` · Story: `v0.13-fu7-backfill-lease-background-renewer` · Status: implemented

## Problem

`run_backfill` held its single-instance lease (`backfill:gemma:lease`) but renewed
it only from **event** sites:

- once per launch-loop iteration (`_lease_held()`),
- once per pause poll,
- once per finished row (`_tick_lease()` in the worker's `finally`).

Nothing renewed it *while a row was in flight*. One property whose enrichment
(≈3 cloud calls plus image downloads, each with client-side 429 retries) outlives
`backfill.lease_ttl_seconds` therefore let the lease lapse **under a live
writer** — and a second runner could acquire it and start working the same queue.

The same hole covers every long await in the loop that is not a row: the
launch-interval (RPM) sleep, the TPM wait, `await sem.acquire()`, and the closing
`asyncio.gather` drain when a single slow row is all that is left. That is
deferred-work entry **DW-6**.

## Approach

- **A timer, not another event.** `run_backfill` starts one asyncio task for the
  whole body of the run that renews the lease every `lease_renew_interval`
  seconds — default `lease.ttl_seconds / 3`, the same cadence
  `migrate-primary.sh`'s watchdog and the CLI's sync sleep loops already use, so
  two consecutive misses still leave a margin. Because it is a timer, it is
  independent of what the launch loop or the workers happen to be doing.
- **The renewer gets its own sleep seam.** The new `lease_sleep_fn` defaults to
  `asyncio.sleep` and is deliberately *not* the existing `sleep_fn`: `sleep_fn`
  is the launch loop's pacing seam, and a dozen unit tests inject counting
  closures there that mutate control/Redis state on the *n*-th poll. A renewer
  sharing that seam would fire those side effects on its own schedule and
  silently change what those tests exercise.
- **It yields even when its sleep does not.** An injected
  `async def sleep(_): return None` never suspends, so `while True: await
  lease_sleep_fn(i)` would spin without handing control back and hang the run it
  is protecting. The body therefore also awaits `asyncio.sleep(0)` once per
  tick — a real yield point regardless of what was injected. For the same
  reason the renewer never calls `clock()` or `_refresh_state()`: the tests
  inject finite `iter([...])` clocks that a timer loop would exhaust, and the
  published state belongs to the loop's own cadence.
- **Loss is observed, not raised.** The renewer calls the same `_lease_held()`
  the loop uses — the single place that flags `BackfillResult.lease_lost` and
  logs the loss — and then simply returns. The launch loop stops at its next
  observation point: a new `result.lease_lost` check at the loop head and
  another right after `await sem.acquire()`, beside the existing
  `quota_exhausted` / migration re-checks (that wait can be minutes long, and a
  row launched after it would be a second writer). `lease_lost` stays distinct
  from `stopped` — nobody asked this run to end.
- **Renewal stays owner-token CAS.** Nothing about `BackfillLease` changed, so a
  runner whose lease was taken over can never extend or steal back its
  successor's key.
- **A Redis blip is bookkeeping, not a lost lease.** A `renew()` that *raises*
  inside the renewer is logged (`backfill_lease_renewer_failed`) and the timer
  keeps ticking; it never sets `lease_lost` and never propagates into the launch
  loop, which would abandon rows that are still enriching.
- **Cancellation order: after the drain.** The task is created only when a
  `lease` was supplied, as the first statement of the `try` wrapping the launch
  loop, and cancelled in a nested `finally` that runs *after* the existing
  `await asyncio.gather(...)` drain — a drain of one slow row is precisely a
  window the timer must cover. The cancelled task is then observed through
  `asyncio.wait({renewer})` rather than `await renewer`: `await` would raise the
  renewer's own `CancelledError`, which is indistinguishable from a cancellation
  delivered to `run_backfill` itself (Ctrl-C, a supervising `wait_for`) landing
  on the same line — so catching it there swallowed the caller's cancellation.
  `wait` never re-raises what the awaited task raised; whatever the renewer
  ended with is read off the task and logged, so it can never replace or
  suppress the exception the caller is about to see.
- **All three existing renewal sites stay.** The launch-loop and pause-poll
  calls double as the loop's *stop* decision, and the per-row `_tick_lease()`
  also refreshes the published control state, which has a tighter TTL than the
  lease. The timer is an addition, not a replacement; renewing more often than
  strictly necessary costs one CAS per tick.
- `src/core/backfill_runner.py` stays framework-free and injectable (AD-1): no
  config import, no adapters — the cadence derives from the injected
  `lease.ttl_seconds` and the sleep is a parameter.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh backend
   ```
2. Against the live primary stack — during a `python scripts/dev/backfill_gemma.py`
   pass, the lease TTL must never decay below roughly two thirds of
   `backfill.lease_ttl_seconds`, including while a single slow property is being
   enriched:
   ```bash
   watch -n 5 'redis-cli -p "$REDIS_PORT" ttl backfill:gemma:lease'
   ```

## Notes / Follow-ups

- Resolves deferred-work entry **DW-6**.
- The advisory heartbeat `backfill:gemma:active` still ticks only per finished
  row and is deliberately untouched here — its own liveness gap is **DW-9**, a
  separate ledger entry with different consequences (a *paused* runner
  deliberately stops beating `:active` so `migrate-primary.sh` can proceed, so it
  cannot simply move onto this timer).
- `scripts/dev/backfill_gemma.py`'s sync `_sleep_for_reset` / `_wait_out_migration`
  loops are unchanged: they already renew at TTL/3 outside the event loop, and
  they run when `run_backfill` is not.
- The timer is a coroutine on the run's own event loop: it is not driven by the
  launch loop, but it is not preemptive either. A blocking section inside
  `enrich_fn` (the live `run_enrichment` does synchronous SQLAlchemy work) or a
  slow Redis round-trip delays the tick exactly as it delays everything else —
  the TTL/3 cadence is the margin that absorbs that.
- Losing the lease stops *launching*, not the rows already launched: up to
  `concurrency` in-flight enrichments keep running and writing while the
  successor works the same queue, for the length of the drain. In-flight rows
  always draining is a deliberate constraint (cancelling mid-enrichment means
  half-written properties), so the overlap is bounded by one row, not removed.
- The tick's own `lease.renew()` is a *synchronous* client call, so every tick
  briefly blocks the loop — including the rows it protects — for one Redis
  round trip.
- The TTL refresh is asserted against the suite's `EvalRedis` fake, which
  records expirations but never decays them; the CAS itself is covered against
  real Redis by `src/tests/integration/test_backfill_lua_scripts.py`. A timer
  ticking against a live server remains the operator check above.
- A run that is cancelled from the outside (`asyncio.wait_for`, Ctrl-C) while a
  row can never complete still blocks in the in-flight drain — the drain
  deliberately does not cancel workers mid-enrichment. Pre-existing behaviour,
  unchanged here; only visible under a deliberately broken build.
