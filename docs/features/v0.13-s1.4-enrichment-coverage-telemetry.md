# Enrichment coverage telemetry — DB-derived per-signal coverage, throughput and ETA

> Feature branch: `bmad-loop/20260806-010958-6ecb/1-6-operacoes-backfill-card-coverage-visibility` · Story: `v0.13-s1.4` · Status: implemented (delivered inside the `v0.13-s1.6` branch)

## Problem

Nothing in the product answered "how much of the DB is actually enriched". The only progress signal for a six-day cloud backfill was the runner's own log output and its Redis checkpoints — and a checkpoint is a resume marker, not a progress metric: it is wrong the moment a run is started outside the API, restarted, or crashes mid-pass, and it says nothing at all when no runner is running. FR-29 requires the figures to come from the database so they survive restarts and are correct with the runner absent, and NFR-6 requires them mid-run without reading logs.

This story escalated on 2026-08-06 inside the same bmad-loop run, on a branch-state blocker (an unmerged story-1.3 follow-up branch) that has since been resolved and merged. It was left at `backlog` while the loop advanced. Story 1.6's UI consumes this endpoint directly and was undeliverable without it, so the scope was absorbed into 1.6's branch and built to *this* story's acceptance criteria in `epics.md`.

## Approach

- **`GET /admin/enrichment/coverage`, purely DB-derived.** Every number comes from SQL over `properties`, `metrics_scoring` and `pipeline_metric_snapshots`. Redis contributes exactly one thing: the runner's lease, answering "is a pass live right now" and bounding the throughput window. No checkpoint, budget or state read may influence a figure (FR-29), and no second telemetry bus is introduced.
- **Signal identity is `EnrichmentTaskClass`** (story 1.1's vocabulary) — English on the wire, all five members returned. The column aliases in the SQL *are* the enum values, so a member added without a query column fails a unit test rather than a polled route.
- **Absence over zero.** `total == 0` yields `fraction: null`, not `0.0`; a run whose snapshot history cannot support a rate yields `throughput_per_day: null`. `null` means "not measurable" and is never to be rendered as zero — the contract every consumer codes against.
- **Active properties only** as the denominator. Delisted rows are never enriched, and counting them would permanently depress coverage and stall the ETA — the dead-completion-branch failure `v0.13-fu3` fixed in the runner.
- **The ETA is guarded on every side that could fabricate one.** The throughput window is the trailing 24h of snapshots, clamped forward to the live run's lease acquisition (a fixed window divides a 30-minute-old run across 23.5 idle hours); fewer than two points, a flat or negative delta, or a window shorter than fifteen minutes all report no rate at all. `estimate_eta_days` is reused, and `inf` never reaches the wire.
- **The remaining-candidate count mirrors the runner's own predicate**, photo gate included, so a photo-blocked row cannot inflate the ETA with work the runner will never pick up. A drift-lock unit test compares both against the runner's originals across six config shapes.
- **Pure math in `src/core/`, SQL in an adapter, a thin route.** `src/core/enrichment_coverage.py` imports nothing from `adapters`/`api` and is TDD'd against the story's edge-case matrix.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh backend
   ```
2. Manually, against a credentialed API:
   ```bash
   curl -s -H "X-API-Key: $API_KEY" localhost:8000/api/admin/enrichment/coverage | jq
   ```
   With no runner running, every figure is still correct and repeated calls are identical; `backfill.active` is `false` and `throughput_per_day` / `eta_days` / `projected_completion_date` are all `null`. Without the header the router refuses before any query runs.
