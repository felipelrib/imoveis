# The daily budget counts requests, not properties — reserve, then reconcile

> Feature branch: `feat/v0.13-s3.3-budget-counts-requests` · Story: `v0.13-s3.3` · Status: implemented

## Problem

The backfill's daily budget was charged a flat `requests_per_property` (3) per
row — `budget.try_consume(requests_per_property)` in the launch loop — and never
reconciled. But one property is 3 stages × up to 3 JSON-retry attempts
(`_run_json_retry_loop`) × up to 5 HTTP attempts (`GeminiClient.max_retries`) =
up to **45** real requests, and as few as **2** (a row with no description skips
the sentiment call).

`429` is in the client's `_RETRY_STATUS`, so every throttled call is retried and
counted by the provider — which means the undercount was worst exactly when the
account was already being throttled. Story 1.3 made the reservation atomic (Lua
reserve + rollback, locked under real contention by
`src/tests/integration/test_backfill_lua_scripts.py`), so AC-1's never-exceed
guarantee was correct — about a quantity that was not the provider's RPD. Filed
as **DW-18**.

Concretely: a pass that retried its way through 40 properties could report `120`
requests against a 14,000 cap while the provider had counted well over a
thousand, keep launching rows into an account it had already exhausted, and burn
the rest of the day on 429s.

## Approach

- **Keep the flat charge as a forecast; add reconciliation.** The launch loop
  still reserves `requests_per_property` *before* a row runs — it has to, since
  nothing is known about the row's cost yet, and the reservation is what makes
  the cap atomic. What is new is that every finished row settles the difference
  between what the provider really counted and what this run has charged.
- **A second Lua script, not a mode flag on the reserve.** `_BUDGET_SETTLE_LUA`
  is 12 lines beside `_BUDGET_RESERVE_LUA`, which is untouched. A settle must be
  able to do what a reserve must never do (push `count` past `daily_limit`) and
  must never do what a reserve must always do (open or roll a window). Branching
  one script on a flag would put both policies one `if` apart in the file where a
  mistake overspends a real account — and would put the reserve's never-exceed
  proof back in question.
- **`DailyBudget.settle(delta)` adjusts the live window only.** No live window ⇒
  no-op returning `False`, writing nothing: those requests belong to a window
  that has already reset, and opening one here would restart the 24h clock from a
  *reconciliation* rather than a reservation. Refunds floor at 0; `delta == 0`
  costs no round trip. Both branches ship, atomic (`eval`) and the documented
  multi-op fallback, exactly as `try_consume` does.
- **The aggregate is reconciled, never the row.** One `GeminiClient` is shared by
  all `concurrency` tasks and `request_count` is a single monotonic int, so
  `after - before` around one row attributes other rows' retries to whichever row
  finished first. Instead each finished row computes
  `target = observed + inflight × requests_per_property` and settles
  `target - charged`: attribution-free, never *below* reality while rows are in
  flight, and exact once the last row drains. With the shipped `concurrency: 1`
  the in-flight term is always 0, so it is exact at every settle.
- **The counter arrives as an injected callable.** `request_counter:
  Callable[[], int]` alongside `is_quota_error` / `is_degraded_error` — `src/core`
  still imports nothing from `adapters`/`api` (AD-1). `request_count` alone is
  the right quantity: it is incremented once per attempt at the top of the
  client's retry loop, so retries are already inside it (`retry_count` is a
  diagnostic *subset* and adding it would double-count).
- **`None` reproduces the old behaviour byte-for-byte.** It is the default, and
  it is what every local backend gets: `OllamaClient` / `LMStudioClient` /
  `RoutingAIClient` expose no such counter, and a `--dry-run` builds no client at
  all. Flat charge, zero settles.
- **An overshoot is recorded, not capped.** The provider has already counted
  those requests; a counter that stopped at the cap would under-report exactly
  the condition this story exists to expose. It grants nothing: `try_consume`
  still refuses on `count > limit`, `remaining()` still floors at 0, and
  `BackfillCard.tsx` already clamps its percentage with a comment naming retries
  as the cause.
- **No migration for existing budget hashes.** `count`'s *unit* did not change —
  it was always nominally "requests"; the old writer simply wrote a wrong number.
  Carrying it forward can only under-state, never grant, and leaving
  `_migrate_start_epoch` and the window rule untouched is what keeps an upgrade
  mid-window from opening a second day (the hazard v0.13-fu6/1.3 wrote that
  helper for).
- **`--continuous` re-verified against the new quantity.**
  `rpd_spent = headroom < requests_per_property` still asks the right question —
  "can another property be reserved?" — now against a truthful `headroom`. A run
  whose last row overshoots ends normally; the next cycle is refused at its first
  reservation, giving `processed == 0` **with** `budget_exhausted`, which routes
  to the sleep-to-reset branch, never to the stall exit.

budget exhaustion, in-flight forecast, window roll, legacy-hash continuation).

### What an operator sees when a retry storm spends the day early

`--status` reports the requests really sent, so the budget line drains faster
than properties complete:

```
  budget today         : 14002 / 14000 requests sent (retries included)
  ETA (~days)          : 5.7 (best case at 3 req/property; not running)
```

`consumed` can read slightly **above** the cap — that is the recorded overshoot,
not a bug: the last row's retries were already counted by the provider.
`remaining` floors at 0, the next reservation is refused, and `--continuous`
sleeps to the window reset (`Daily budget spent; sleeping 21.4h …`) rather than
exiting as a stall. The `backfill_progress` log line carries both numbers —
`requests_consumed` (real) and `requests_reserved` (3 × rows) — and a persistent
gap between them is the signal that retries, not properties, are eating the
quota. A window that resets mid-pass logs `backfill_budget_window_rolled` once; a
Redis blip during a settle logs `backfill_budget_settle_failed` and the row
completes regardless.

## Notes / Follow-ups

- Closes **DW-18**.
- **The reported properties-per-day figure is now explicitly a best case.** The
  ~4,600 props/day planning basis assumes every property costs exactly 3
  requests. It is unchanged as a *planning* number (and the `~6-day whole-DB
  pass` basis with it), but a pass with heavy retries buys fewer properties for
  the same budget — which the ETA line now says out loud.
- **The RPM pacer still paces on the forecast.** `launch_interval_for_rpm` and
  the dry-run projection both divide by `requests_per_property`, so a retrying
  pass can exceed the nominal 30 RPM between launches. Out of scope here (this
  story owns the *daily* counter); the client's own back-off remains the
  per-minute defence.
- **A settle failure is swallowed** (logged as `backfill_budget_settle_failed`,
  the row completes). The *window* keeps that row's flat forecast as its charge,
  so the Redis counter under-reports until the next successful settle catches up
  — the conservative direction, since the next reconciliation targets the
  aggregate rather than a delta. `BackfillResult.requests_consumed` is
  unaffected: it is assigned from the client's counter *before* the settle is
  attempted, so a Redis blip never costs the pass its reported request count.
- **A settle that finds no live window carries its spend forward.** The 24h
  window can roll mid-run; the settle writes nothing (it must never open or roll
  one), and the run re-anchors only what it has *charged*, leaving the spend
  pending so the next window absorbs it. That over-charges the new window by up
  to one row's worth rather than dropping those requests — under-charging is the
  only direction that can push a real account past its RPD.
- Untouched by design and still open: **DW-19** (`--continuous` never exits on a
  permanently refusing account), **DW-20**, **DW-21**. Story 3.4 (checkpoint
  advance under lease loss) edits the same runner core and follows this one.
