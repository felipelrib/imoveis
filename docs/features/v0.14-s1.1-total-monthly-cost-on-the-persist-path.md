# Total Monthly Cost on the persist path — every Listing carries rent, condo fee and IPTU as comparable monthly components

> Feature branch: `feat/v0.14-s1.1-total-monthly-cost-on-the-persist-path` (bmad-loop: `bmad-loop/<run>/1-1-total-monthly-cost-on-the-persist-path`) · Story: `v0.14-s1.1` · Status: implemented, awaiting operator (primary migration, worker rebuild, backfill run)

## Problem

A Listing's `price` means something different on each platform, so nothing comparable existed for the `aluguel-2027` total-cost cap (FR-31):

- QuintoAndar and OLX fold condo fee and IPTU into the headline price; ZapImóveis does not.
- OLX sums a fee the advertiser did not fill in as zero, so a "complete" looking headline can be missing a component.
- ZapImóveis stores IPTU as published, and it is often the annual figure.

## Approach

- **Typed columns on `property_listings` (AD-3):** `rent_monthly`, `condo_fee_monthly`, `iptu_monthly`, `iptu_periodicity_source` (`monthly` / `annual` / `unknown`), `fees_bundled`, `total_monthly_cost`, `cost_complete`, plus `updated_at` (AD-19).
- **One rule module, `src/core/listing_cost.py`**, pure (standard library only) and built test-first. `compute_listing_cost(...)` maps published figures to the columns; `listing_cost_columns(listing)` is what the persist path calls.
- **One writer.** Only `core/dedupe.py` writes the cost columns: `_upsert_listings` on the scrape path and `repopulate_listing_costs` for rows already stored. The second is the same mapping re-applied to stored rows, not a second writer.
- **Stamp plus fallback.** Scrapers stamp the platform's raw figures into the listing's stored `raw_json["cost_source"]` (`rent`, `condo_fee`, `iptu`, `fees_combined`, `iptu_periodicity`), so the mapping never reads a headline column for a fresh rent Listing. Rows stored before this story have no stamp; the fallback rebuilds the identical inputs from the legacy fields, and a test pins fresh == stored.
- **Legacy values are untouched.** `price`, `base_price`, `condo_fee`, `iptu` and the `raw_json.fees_bundled` key the projection reads keep their values and their meaning.

### Rules

| Rule | Behaviour |
|---|---|
| Unknown component | A missing, zero or negative published figure is `NULL`, never `0`. Nothing is imputed, defaulted or estimated. |
| `rent_monthly` | The platform's unbundled rent: QuintoAndar `rentPrice`, OLX `rent_base`, ZapImóveis rental `value`. `NULL` on sale Listings. |
| Bundled | QuintoAndar `condoIptu` with no separately published fee: the combined figure goes in `condo_fee_monthly`, `iptu_monthly` stays `NULL`, `fees_bundled` is true and the total is complete. |
| QuintoAndar remainder | `totalCost − rentPrice` is never a fee for the new columns (it includes other charges). It still feeds the legacy `condo_fee`. |
| IPTU periodicity | Declared `monthly` by QuintoAndar (it itemizes monthly). Otherwise classified by magnitude against the Listing's own reference: rent for rent, sale price for sale. |
| Annual IPTU | Divided by 12 and rounded to cents (half up). |
| Ambiguous IPTU | Periodicity `unknown`, no division, `iptu_monthly` `NULL`. |
| `total_monthly_cost` | `rent_monthly + condo_fee_monthly + iptu_monthly`, rent Listings only. `NULL` whenever a component is unknown and not bundled. |
| `cost_complete` | True exactly when the total is not `NULL`. Always false on sale Listings. |
| `iptu_periodicity_source` | `unknown` whenever there is no usable IPTU figure (missing, bundled or ambiguous). |
| `updated_at` | Set on insert; moves only when a cost column changes or the Listing is reactivated. |

### Periodicity thresholds

No platform labels IPTU periodicity. A read-only live probe on 2026-10-08 over 60 Belo Horizonte ZapImóveis listings showed two clean clusters:

| Listing type | Observed monthly | Observed annual | Monthly at or below | Annual at or above |
|---|---|---|---|---|
| Rent (IPTU ÷ rent) | 3–14% | 51–105% | 15% | 40% |
| Sale (IPTU ÷ sale price) | 0.01–0.06% | 0.33–0.41% | 0.10% | 0.25% |

The gap between the clusters is the ambiguity band. The thresholds are the named constants `RENT_IPTU_MONTHLY_MAX_RATIO`, `RENT_IPTU_ANNUAL_MIN_RATIO`, `SALE_IPTU_MONTHLY_MAX_RATIO` and `SALE_IPTU_ANNUAL_MIN_RATIO` in `core/listing_cost.py`; changing one is a one-line edit followed by a backfill run. The same probe showed QuintoAndar search rows carry `rentPrice`, `totalCost` and `condoIptu`, with `totalCost − rentPrice` exceeding `condoIptu` by about 35.

### Rows stored before this story

| Platform | Rent | Fees |
|---|---|---|
| QuintoAndar | `raw_json.partial_price`, else `base_price` | Itemized `condo_fee` / `iptu` as stored. When `raw_json.fees_bundled` is true, the stored `condo_fee` is a combined figure only if `fees_note` is the published-`condoIptu` note; with the derived-remainder note (or no note) both fees are unknown. |
| OLX | `base_price` | `condo_fee` / `iptu` as stored (`0` reads as unknown). |
| ZapImóveis | `price` | `condo_fee` / `iptu` as stored. |

Malformed `raw_json` is treated as `{}`. An unknown platform never has its headline read as rent.

### Operator steps (primary stack)

Deploy order matters: the new code INSERTs the new columns, so the primary must be migrated before the workers are rebuilt. The old code tolerates the new columns (they all have defaults), so stopping after step 1 is safe.

1. Migrate the primary database, from the primary checkout, in Git Bash:
   ```bash
   bash scripts/agent/migrate-primary.sh
   ```
   Expected: `alembic_version` becomes `c4d5e6f7a8b9`. Existing rows start with `NULL` components, `iptu_periodicity_source = 'unknown'` and `cost_complete = false`. The script refuses while a cloud backfill runner is alive (`backfill:gemma:active`); wait for it or pause the runner, never delete the key.
2. Rebuild and restart the API and workers so they run the new persist path:
   ```bash
   ./scripts/restart.sh --build
   ```
   If the rebuild fails, the previous images keep working against the migrated schema; fix and retry. Do not downgrade the schema while any container runs the new code.
3. Populate the Listings already stored (idempotent; safe to re-run, and safe while scrapes run because each batch is row-locked until it commits):
   ```bash
   docker compose --env-file .env.local exec worker_scraper celery -A adapters.queue.tasks call tasks.backfill_listing_costs
   docker compose --env-file .env.local logs --since 30m worker_scraper | grep listing_cost_backfill
   ```
   `celery call` prints only a task id. The log line `listing_cost_backfill_complete` reports `scanned`, `updated` and `batches`; `listing_cost_backfill_failed` means it stopped part-way (committed batches are kept; run it again). A second run must report `updated=0`.
4. Measure the result (read-only). This is the SM-3 view: active rent Listings per platform, split into complete, bundled and incomplete, plus the two reasons a row stays incomplete that the rules cannot fix:
   ```sql
   SELECT platform,
          count(*)                                                        AS active_rent,
          count(*) FILTER (WHERE cost_complete AND NOT fees_bundled)      AS complete_itemized,
          count(*) FILTER (WHERE cost_complete AND fees_bundled)          AS complete_bundled,
          count(*) FILTER (WHERE NOT cost_complete)                       AS incomplete,
          count(*) FILTER (WHERE rent_monthly IS NULL)                    AS rent_unknown,
          count(*) FILTER (WHERE iptu > 0 AND iptu_monthly IS NULL
                             AND NOT fees_bundled)                        AS iptu_ambiguous,
          count(*) FILTER (WHERE iptu_periodicity_source = 'annual')      AS iptu_annual
   FROM property_listings
   WHERE active AND listing_type = 'rent'
   GROUP BY 1 ORDER BY 1;
   ```
   Record the numbers in this doc. A large `rent_unknown` on OLX means rows stored before `base_price` existed (see Notes); a large `iptu_ambiguous` means the thresholds deserve a second look.

   **Recorded on the primary, 2026-10-08** (migration `c4d5e6f7a8b9` applied, stack rebuilt, backfill run twice: first run `scanned 288372, updated 269464`, second run `updated 0`):

   | platform | active_rent | complete_itemized | complete_bundled | incomplete | rent_unknown | iptu_ambiguous | iptu_annual |
   |---|---|---|---|---|---|---|---|
   | olx | 7293 | 3705 | 0 | 3588 | 3 | 391 | 339 |
   | quintoandar | 77888 | 0 | 72908 | 4980 | 297 | 0 | 0 |
   | zapimoveis | 43197 | 26295 | 0 | 16902 | 0 | 1926 | 1156 |

   Reading: 80% of active rent Listings carry a complete total (102,908 of 128,378). `iptu_ambiguous` is 5.4% on OLX and 4.5% on ZapImóveis, so the thresholds stand (operator confirmed both product calls on 2026-10-08: periodicity by magnitude, zero is unknown). QuintoAndar is all bundled, as its payload publishes only the combined figure.

## Notes / Follow-ups

- **Zero is unknown.** Platforms and advertisers emit `0` for "not filled in". A house with genuinely no condo fee is indistinguishable, so it stays incomplete and later reads as pending verification rather than as a false total.
- **Unchanged Properties are not rewritten by a scrape.** `_is_unchanged` still skips listing writes for a Property whose price, text and photos did not change, so such a row gets its cost columns from the backfill task, not from the next scrape. Run the backfill once after deploying; run it again after any threshold change.
- **The stamp reaches a stored row only on a real change.** For the same reason an unchanged row keeps its pre-story `raw_json` (no `cost_source`); the fallback yields the same columns, which is what the fresh == stored test pins.
- **ZapImóveis dual rent+sale ads** use the rental side's condo fee and IPTU for both Listings, as the legacy columns already do, so fresh and stored rows agree.
- **`active` and `updated_at`.** The persist path moves `updated_at` on reactivation and `deactivate_listing_and_maybe_property` (`adapters/scrapers/availability.py`) moves it on deactivation, so the AD-19 Fit sweep sees a Listing enter or leave the active set. The recheck task's `last_seen` touch does not move it.
- **Rows that stay incomplete after the backfill.** Stored rows carry only what an earlier scrape kept. An OLX rent row written before `base_price` existed (`b7c8d9e0f1a2`) and unchanged since has no unbundled rent, and a QuintoAndar row without `raw_json.partial_price` likewise; both stay `rent_monthly NULL` until the Property next changes on the platform. Nothing is reconstructed from the summed headline. The step 4 query counts them.
- **Periodicity is inferred, and the inference can be wrong.** No platform labels IPTU periodicity. An annual IPTU small enough to sit under the monthly threshold (below 15% of one month's rent) is read as monthly and overstates the total; the thresholds come from one ZapImóveis probe and are applied to OLX and to sale Listings as well. Whether a row's periodicity was declared or inferred is in `raw_json.cost_source.iptu_periodicity` (`null` = inferred).
- **QuintoAndar sale payloads with fees and no `totalCost`** make the legacy normalizer emit a rent Listing priced at condo + IPTU (pre-existing; `_prices_and_fees`). Its cost columns are honest (`rent_monthly NULL`, incomplete), the phantom Listing itself is not fixed here.
- **Sale reference.** A sale Listing's IPTU is classified against its `price`, which is the published sale price on all three platforms.
- No API exposure (Story 1.2) and no cohort basis change (Story 1.3) ship here; `src/api/`, `scoring.py` and the frontend are untouched.
