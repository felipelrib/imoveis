# Runner lifecycle ends honestly — a backfill that cannot proceed says so, on the surface it was started from

> Feature branch: `feat/v0.14-s1.13-runner-lifecycle-ends-honestly` · Story: `v0.14-s1.13` · Status: implemented

## Problem

A cloud backfill run had five ways of not proceeding without telling anyone.

| Entry | What happened | Why nobody saw it |
|---|---|---|
| DW-19 | `--continuous` against a provider that refuses permanently (a quota set to zero, a project without the free tier) slept out one daily window after another, one refused pass per window | every wait printed "safe to resume"; there was no exit and no exit code |
| DW-28 | a run requested through `POST /admin/backfill/start` was refused (no key, local routing) or died after the `--serve` supervisor had consumed the request | the supervisor printed the exit code to its own log; the API and the Operações card showed `idle`, the same as before the click |
| DW-23 | a pause expired after 7 days (the request TTL) and the run launched rows again | the pause key simply vanished; the run resumed and spent cloud quota nobody had asked it to spend |
| DW-22 | the SIGINT/SIGTERM handler called `control.request_stop()` (a Redis round trip) and `print` | a handler runs between two bytecodes of the main thread; when that thread was inside a Redis call or a `print`, the handler could block for good |
| DW-81 | since Story 1.12 a run whose main thread hung kept its lease, its published state and the supervisor key alive | the liveness thread proves the process exists, not that the run moves, so a wedged run read as alive until someone killed it |

## Approach

Each case gets an explicit end or an explicit standing state, published where the operator started the run.

- **A provider that keeps refusing ends the run (exit 10).** `_run_continuous` already counted consecutive cycles that end in a provider quota refusal with nothing enriched (`quota_zero_cycles`); until now the count only made the wait longer. When it reaches `backfill.max_no_progress_cycles` (default 6) the run prints a banner naming the count and returns `EXIT_PROVIDER_REFUSED` before the next sleep. With the shipped values that is four refused passes 15 minutes apart, a wait for the rest of the local 24-hour window, a fifth refused pass, a whole window and a sixth refused pass. The fifth and the sixth are a full day apart because a refused pass reserved budget before it was refused, which opens a local window of its own; a quota that resets daily has reset between them, so a healthy provider that merely ran out for the day cannot reach six. Any cycle that enriches a row resets the count, whatever that cycle ended on. `0` disables the limit. The final published state is `idle`, not `backing-off`: the run is not waiting for anything.
- **The supervisor records how each run ended.** `--serve` writes `<prefix>:last_run` (JSON, kept 30 days) when it launches a run and again when the run returns, raises a refusal or raises an exception. `GET /admin/backfill/status` serves it as `last_run`, and the Operações card shows a line for it. A refusal carries the runner's own message (it names config keys). A crash carries the exception **type only**: its text can hold a URL with a key in it and this record goes out on an HTTP response. Recording is guarded: a Redis error is logged and the supervisor keeps serving.
- **`interrupted` is derived, never written.** The supervisor and the run it drives are one process, and the supervisor beats its key with its `host:pid`. A record that still says `started`, with the lease free and the supervisor key absent or beaten by another `host:pid`, is a run whose process is gone. While the same supervisor is alive the record stays `started` for the moment between the lease release and the end record, so the card does not flicker. The `host:pid` stays in Redis and is not on the wire.
- **A pause stays a pause until an operator resumes it.** The ledger named two options: the paused loop refreshes the key, or expiry ends the run. Ending a multi-day run because nobody resumed it costs a restart and gains nothing a pause does not already hold, so the run refreshes. `request_pause` now stores the request time (`SET NX EX`; a second pause re-arms the TTL and keeps the first stamp). While a run observes the pause it calls `hold_pause()` on every poll of the paused loop and on every state publish of the two wait loops. That is an `EXPIRE` on a key that exists: the runner extends an operator request and never creates one, and a `resume` that deletes the key between two refreshes stays a resume. The status serves `paused_since` and `pause_stale: true` once the pause is older than the 7-day request TTL, and the card says so. A pause with no run observing it still expires; the next start discards stale requests and says so, as before.
- **The signal handler sets a flag.** It sets `_STOP_SIGNAL_RECEIVED`, restores the default disposition (a second signal aborts hard) and does nothing else: no Redis, no ticker, no lock, no `print`. `_install_stop_signals` registers the flag with `BackfillControl.watch_local_stop`. `should_stop()` returns true without a Redis read when the flag is set, so the stop works with Redis down; the first time it sees the flag it writes the stop key once, guarded, so the API still shows a pending stop while the run drains. The "draining" message is printed by the main thread at that same moment. The run exits 6 as before.
- **The liveness ticker is also a watchdog on the main thread.** "Progress" means "the main thread ran": inside a pass a pulse task on the event loop calls `note_progress()` (one assignment, no lock, no I/O), and outside it the run stamps around its blocking stretches (pass start, after the candidate fetch, after the partition, cycle start, around the census, every wait-loop step). When no stamp arrives for `backfill.main_thread_stall_seconds` (default 3600, floor 900, `0` = off) the ticker stops vouching for the run: the stall is latched as a lost lease, so the lease is no longer renewed and no state is published; the callback stops the supervisor's keepalive ticker and records `hung`. The ticker cannot end a hung process. If the main thread comes back it reads `lease_lost`, launches nothing more and exits 11. `:active` keeps the lease-loss rule and is still beaten while a pass is writing, because rows in flight may write.
- **Why 3600 s.** The longest honest gap is one database statement blocked by a migration: `migration_wait_seconds` and the migration lock are both 1800 s. The default is twice that and the floor is 900 s.

### Exit codes

Every code the runner returns, and what a supervisor should do with it. Codes 0 to 9 keep the number and meaning they had.

| Code | Constant | Meaning | What a supervisor should do |
|---|---|---|---|
| 0 | `EXIT_COMPLETE` | the candidate queue drained, nothing was retired (also: a single pass or a one-shot command ended normally) | nothing; do not restart |
| 1 | `EXIT_ERROR` | an unhandled error (traceback), or a start-up refusal such as a missing `GEMINI_API_KEY` or all-local routing | read the log; restarting without fixing the cause repeats it |
| 2 | `EXIT_USAGE` | the command line was rejected | fix the command; do not restart |
| 3 | `EXIT_STALLED` | work remains but a full cycle enriched nothing while budget was left: the remaining rows are failing | look at the row errors and the quarantine list; do not restart blindly |
| 4 | `EXIT_COMPLETE_WITH_QUARANTINE` | the queue drained, but rows were quarantined unenriched | done; review the quarantined rows, `--reset-quarantine` to retry them |
| 5 | `EXIT_LEASE_HELD` | refused: another runner holds the lease | nothing; one runner is already working |
| 6 | `EXIT_STOPPED` | an operator asked it to stop (`--stop`, SIGINT, SIGTERM); in-flight rows drained | do not restart; the next start resumes from the checkpoint |
| 7 | `EXIT_LEASE_LOST` | the lease was lost mid-run; another runner may have taken over | check `--status` before starting another run |
| 8 | `EXIT_MIGRATION_ACTIVE` | `migrate-primary.sh` held the database for longer than `backfill.migration_wait_seconds` | restart once the migration has finished |
| 9 | `EXIT_AI_CIRCUIT_OPEN` | the AI backend kept returning results the write authority refused (revoked key, retired model id, blocked egress) | fix the key, model id or egress; do not restart until then |
| 10 | `EXIT_PROVIDER_REFUSED` | `max_no_progress_cycles` consecutive cycles ended in a provider quota refusal with nothing enriched | check the provider quota for the key and project; do not restart until it is fixed |
| 11 | `EXIT_MAIN_THREAD_STALLED` | no progress stamp for `main_thread_stall_seconds`; the watchdog gave the lease up and the run, once it came back, launched nothing more | find what blocked the process (a call without a timeout, Redis not answering); check `--status` before starting another run |

The `--serve` supervisor never relaunches a run on its own: a run needs a new start request, so for it "act on the code" means recording the outcome and saying so. An operator who runs `--continuous` under a supervisor of their own uses the code; for systemd: `RestartPreventExitStatus=9 10 11`. `--serve` itself still exits 0, so the shipped unit and the Windows host are unchanged.

### Outcome vocabulary

`last_run.outcome` on `GET /admin/backfill/status` and in `<prefix>:last_run`. Canonical English words; pt-BR exists only as the card's label. A client renders a word it does not know verbatim.

| `outcome` | Written when | `exit_code` | Card line |
|---|---|---|---|
| `started` | the supervisor launched the run | null | none (the run is in progress) |
| `complete` | exit 0 | 0 | plain |
| `complete_with_quarantine` | exit 4 | 4 | plain |
| `stopped` | exit 6 | 6 | plain |
| `lease_held` | exit 5 | 5 | plain |
| `stalled` | exit 3 | 3 | failure |
| `lease_lost` | exit 7 | 7 | failure |
| `migration_blocked` | exit 8 | 8 | failure |
| `ai_circuit_open` | exit 9 | 9 | failure |
| `provider_refused` | exit 10 | 10 | failure |
| `hung` | the watchdog found the main thread silent (`finished_at` is that moment, not the end of the process); written again with the code if the run came back | null, then 11 | failure, shown even while that run still holds the lease (not over a later run: the card compares `finished_at` with the lease's `acquired_at`) |
| `refused` | `main` raised `SystemExit` with a message; `reason` is the runner's message | 1 | failure |
| `crashed` | `main` raised an exception; `reason` is the exception type and a pointer to the supervisor log, never the exception text | 1 | failure |
| `failed`, `usage` | the run returned, or exited with, 1 or 2 | 1, 2 | failure |
| `interrupted` | never written: derived when the record says `started`, the lease is free and the supervisor that drove the run is gone | null | failure |

## Notes / Follow-ups

- **Deploy.** The runner and the supervisor are host processes: the change takes effect when the `--serve` supervisor is restarted, with no run holding the lease. The API image has to be rebuilt for `last_run`, `paused_since` and `pause_stale` to be served (`src/api/` and `src/core/` changed). No migration and no config change is required; the two new keys have defaults.
- **Mixed versions.** A supervisor still running the old code writes no `last_run`, so the field stays null. A pause requested by old code holds `1`: it is still a pause, `paused_since` is null and it is never reported stale. An old runner reading a pause written by new code sees a non-empty value, which is a pause.
- **The watchdog does not end the process.** It stops renewing, publishing and beating. A process that stays hung has to be ended by an operator; `last_run` reads `hung` and, after one lease TTL (900 s), the lease is free and a new run can start. If the hung thread wakes while a successor runs, it launches nothing: every launch-loop check reads `lease_lost`.
- **A run hung inside a pass keeps `:active` beaten.** Rows in flight may still write, so the ticker goes on beating the key, as after any lost lease. `migrate-primary.sh` therefore refuses until the hung process is ended; the `hung` reason on the status surface says so.
- **What the watchdog sees.** A blocked main thread. A row that awaits for ever while the event loop keeps turning still gets its pulse and is not a stall; nothing in this story bounds a single row.
- **"The provider refused" is the existing classification.** Exit 10 counts cycles whose pass ended with `BackfillResult.quota_exhausted`, which comes from the adapter's flag and from the string markers in `is_quota_exhausted`. Story 1.14 owns making that classification more exact.
- **The count resets only on an enriched row.** A zero-progress cycle that ended on the local budget neither counts nor clears it, so "in a row" in the banner means "with no row enriched in between". The same count decides when the 15-minute back-off gives way to the daily-window wait (`_MAX_QUOTA_BACKOFF_CYCLES`), so that ladder follows the same rule: before this story a zero-progress cycle on the local budget restarted it.
- **ADR 0006 and the pause.** `docs/adr/0006-backfill-runner-hosting.md` was read for the pause decision. It says nothing about pauses; its relevant rule is that recovery is unattended, which is why a pause nobody resumed does not end the run and need a restart.
- **`pause_stale` does not say a run is holding the pause.** It says the pause is older than the request TTL and still set. A second pause request re-arms the TTL, and a pause a dead run held lives on for up to 7 days, so it can be stale with no run behind it; the card shows the stale line only while a run holds the lease.
- **A host that was suspended for longer than the stall limit.** The clock the ticker uses keeps counting through a suspend on Windows, so after an hour asleep the first tick could find the limit passed before the main thread had stamped, and a run that never blocked was recorded as `hung`. The ticker thread now notices that its own wait returned 60 s or more late (`_FROZEN_WAIT_SECONDS`): nothing in the process ran in that stretch, so it is taken off the silence, and silence from before the freeze still counts. The run does not resume after such a suspend: the lease TTL (900 s) passed too, so it ends 7 (`lease_lost`), as it did before this story. Under `--serve` that needs a new start request.
- **A stop from a signal after a lost lease.** The first stop check that sees the flag writes the stop key, as the handler did before. A run that has already lost its lease reads `lease_lost` before the stop in the wait loops and in the launch loop, so in those paths the key is not written; the single-pass exit does not read the stop once the lease is lost.
- **`reason` is English.** It is the runner's sentence and names config keys; the card shows it as written, the same way it shows a 409 detail. Only the outcome word has a pt-BR label.
- **A hand-started run that hangs** also records `hung` (source `cli`), because the callback is the run's, and closes that record itself with exit code 11 if it comes back. Nothing else writes `last_run` for a run started by hand, so its normal endings are in its own terminal only.
- **How long a hung process keeps a successor out.** Up to the stall limit, plus a quarter of it (the watchdog is looked at on that cadence at the latest), plus the lease TTL: about 90 minutes at the defaults.
- **The Windows host stop.** `test_native_process_stop_drains_and_clears_real_heartbeat` (`src/tests/unit/test_windows_backfill_host.py`, three modes, `harness`-marked) drives `_install_stop_signals` through `_thread.interrupt_main` in a real child process and polls `control.should_stop()`, which is exactly the path this story changed. It builds its own checkout with a `.git` directory, so it runs in a linked worktree too and is part of the gate for this diff; the eight cases of that file that are skipped in a worktree (DW-42) are other tests.
- **A second signal.** The handler restores the default disposition, so a second SIGINT or SIGTERM ends the process at once, with no clean-up. Nothing is left that needs a hand: the lease, `:active` and the supervisor key lapse on their TTLs (at most 900 s for the lease), and a supervised run's record then reads `interrupted`. The "draining" message appears at the run's next stop check, not at the signal: at most `control_poll_seconds` in a wait, and until the next launch inside a pass.
- **BUG (Medium), fixed in the follow-up review**: a cycle that enriched rows and ended with budget to spare did not reset the refusal count (it went to the next pass before the reset), so refusals on either side of it added up towards exit 10. The reset now runs for every cycle that enriched a row. Locked by `test_a_cycle_that_enriches_rows_with_budget_to_spare_resets_the_refusal_count`.
- **BUG (Low), fixed in the follow-up review**: a `hung` record (kept 30 days) was shown over any later active run, because a run started by hand writes no record of its own. The card now shows `hung` during an active run only when the watchdog gave up after that run took its lease.
- **BUG (Low), fixed in the follow-up review**: a host suspended for longer than the stall limit could be recorded as `hung` (see the suspend note above).
- Ledger (`_bmad-output/implementation-artifacts/deferred-work.md`): DW-19, DW-22, DW-23, DW-28 and DW-81 are marked resolved in this branch, each with what the code resolves. What DW-81 leaves (the watchdog cannot end a hung process, and `:active` stays beaten for one hung inside a pass) is carried in the spec's deferred list. DW-10 (no socket timeout on the shared Redis client) stays open: a main thread blocked in such a call is now seen by the watchdog, but it is still blocked.
- Story 1.14 (transport-quota inference) touches the Gemini client and was kept out.
