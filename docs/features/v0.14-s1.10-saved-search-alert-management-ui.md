# Saved-search alert management UI — each saved search has its own alert switch and minimum price drop, and the drop email states it

> Feature branch: `feat/v0.14-s1.10-saved-search-alert-management-ui` · Story: `v0.14-s1.10` · Status: implemented; the primary is not migrated or rebuilt yet (see Operator steps)

## Problem

Story 1.9 gave every saved search an alert switch and a stored minimum price drop. Nothing in the SPA showed or edited them: a search could only be switched on with `curl`. No rule read `min_price_drop`, so the drop email that must state its threshold (FR-32, UX-DR13) did not exist.

## Approach

Two parts: the row in the Painel sidebar, and the rule behind its threshold field.

### The row

Each entry under Buscas salvas is now the saved-search row of the UX contract.

| Part | What it shows | What it writes |
|---|---|---|
| Name | The search name. A button: clicking it applies the search, as before. | nothing |
| Filter summary | What the search filters on, e.g. `Aluguel · até R$ 4.000/mês · 2+ quartos · Savassi`. `Sem filtros` for a search with none. | nothing |
| Alert switch (`Avisos por e-mail`) | `notify_new_matches` as stored. | `PATCH /saved-searches/{id}` with `{"notify_new_matches": true|false}`, at once |
| Minimum drop (`Queda mínima`, `R$`) | `min_price_drop` as stored; empty with the placeholder `sem aviso` when there is none. | `PATCH` with `{"min_price_drop": 240}` on Enter or blur; an empty field sends `null` |
| State line | `Avisos desligados` · `Avisa imóveis novos` · `Avisa imóveis novos e quedas a partir de R$ 100` · `Avisa imóveis novos e qualquer queda de preço` | nothing |

- **Nothing is on by default.** A new or existing search is off. The save dialog has no alert option and `saveSearch` still sends a name and filters only. There is no global setting and no "enable all".
- **Optimistic, with revert.** The switch and the field show the new value while the request is in flight. A failed request puts the stored value back and shows the bottom toast `Não foi possível atualizar os avisos desta busca`. The toast does not block the row.
- **One request at a time per control.** A second click on the switch while its request is in flight is ignored. The field is read-only for those milliseconds.
- **Only a value is sent.** The field accepts `240`, `1.500`, `1500,50`, `R$ 240` (and the English grouping `1,500.50`). A negative number or letters mark the field invalid (`aria-invalid`, a line under it) and send nothing. `Escape` puts the stored value back. Typing the stored value again sends nothing.
- **Honest muted state.** A search with `new_match_alerts_supported: false` shows no switch and no field. It shows one line instead: `Busca por texto não gera avisos por e-mail.` when its filters carry a text query, `Esta busca não gera avisos por e-mail.` otherwise. If such a search is still switched on, the switch stays next to the line so it can be switched off; once off it disappears.
- **Where the rows are.** In the Painel sidebar section Buscas salvas, where they were. No new route.
- **Sidebar width.** 272px at the design frame (1440px), was 220px. Below about 1320px of viewport it narrows, down to 232px at 1280px (`clamp(232px, calc(100vw - 1048px), 272px)`). The controls take two lines: the switch, then the minimum drop. See the decision table for why the width is not a fixed 272px.
- **Tokens.** The list carries `.meia`: `surface-card` rows, hairline separators, name in body type (14px / 1.55), summary and state line in meta type (12.5px, 0.03em), accent only on the switch and the threshold value, tabular numerals. No gradient, glow or pill badge.

### The drop rule

Once a day the hourly saved-search sender emails, per search, the Listings of matching decidable Properties whose own price fell by at least the search's threshold since drop alerts were switched on.

| Term | Rule |
|---|---|
| Drop alerts active | `notify_new_matches` is true and `min_price_drop` is not null. Both are needed. |
| Floor | `saved_searches.price_drop_enabled_at`: the moment drop alerts became active for the search. Stamped by the API. |
| Threshold | `min_price_drop`, absolute reais on the Listing's headline price. `0` means any drop of at least one centavo. Empty means no drop alerts. |
| Drop | One Listing's current price against that Listing's own reference price. A cheaper Listing appearing on another platform is not a drop. |
| Reference price | The first that exists: the price of this search's last drop email for the Listing (sent at or after the floor); the price in force at the floor; the Listing's first recorded price after the floor. |
| Covered | The Property is active, passes the grid's own `WHERE` (`build_property_where`) for the search and is decidable (`DECIDABLE_SQL`, as in Story 1.9). The Listing is active and priced. The Listing itself also satisfies the search's Listing-level filters: its type when the search has one, the price cap (`max_price` with its `price_type`) and the platform. A search `aluguel até R$ 3.000` never announces a Listing above R$ 3.000. One exception: a search for one type capped on the other (`venda`, with a rent cap) announces Listings of its own type; the cap is about the other Listing and stays a condition on the Property. |
| Local day, window | `alerts.new_match.window_hour` and `window_timezone`, as for new matches. The drop email has its own stored date (`price_drop_last_window_on`). |

- **Detected at send time.** A drop is a comparison of two stored prices, so nothing is recorded when it happens. This gives the hold for free: a Property that does not match or is not decidable yet is looked at again the next day, and alerted then if the drop still holds. A drop that was undone before the window is never emailed.
- **One implementation of the rule.** `core.saved_search_price_drops.drop_amount` decides. The candidate statement only bounds what is examined; the threshold is never in SQL.
- **Candidates are bounded by changes.** Only Listings with a `price_history` interval that closed after the floor are examined, so a search without filters does not probe the history of every Property.
- **Recording the alerted price is the memory.** `saved_search_price_drop_alerts` gets one row per alerted Listing. Its `new_price` is the reference of the next comparison, so the next alert for that Listing needs a further drop of at least the threshold. There is no pending state.
- **One block per Property, every fallen Listing recorded.** The email shows the Listing with the largest drop. Another Listing of the same Property that also fell by the threshold is recorded with it (`drops_to_record`), so the Property is not emailed again the next day for the smaller drop.
- **The reference only moves down.** After an alert at R$ 3.000, a Listing that goes up to R$ 3.500 and back to R$ 2.950 is measured from R$ 3.000: a drop of R$ 50. An alert always announces a price lower, by at least the threshold, than the last one this search announced for the Listing.
- **Switching off and on starts over.** It moves the floor; alert rows from before the floor are not read.
- **Independent of the watchlist alert.** The watchlist is not read. A Property that is watched and also covered by a search with drop alerts can be announced by both: the watchlist email when the price changes, the search's email at the next window. See the decision below.
- **Email only.** `get_notifiers_for_channel("email")`, like Story 1.9. Claim the day under the search's row lock, commit, send with no lock or transaction open, then record. A failed send gives the day back.
- **Inside the existing hourly task.** `tasks.send_saved_search_new_match_alerts` runs the new-match part as before and then the drop pass. No new beat entry. The Story 1.9 sender body moved into a helper unchanged.

### I/O matrix as implemented

| Scenario | Result |
|---|---|
| Threshold 100, Listing 3.240 at the floor, now 3.000 | One email; line `queda de R$ 240 — seu mínimo: R$ 100`; one alert row (3240, 3000, 100); day stamped |
| Same, now 3.200 | Nothing; the day stays open |
| 3.240 → 3.190 → 3.130, threshold 100 | One email, drop 110 |
| Alerted at 3.000; still 3.000 next day; then 2.950; then 2.890 | Nothing; nothing; alert with drop 110 |
| No threshold, or switch off | No drop email |
| Threshold 0, 3.240 → 3.239 | Alert, `seu mínimo: R$ 0` |
| The price fell before the floor | Nothing |
| A second platform lists the Property lower, no Listing fell | Nothing |
| Property not matching, inactive or not decidable | Nothing now; alerted on a later day once it is, if the drop still holds |
| The Property is on the watchlist, whatever `watchlist.last_notified_price` holds | Announced like any other |
| Filters carry `q` | Counted `unsupported`; nothing sent |
| 25 drops, limit 20 | The 20 largest in the email, `+5 nesta busca chegam no próximo aviso.`, only those 20 recorded; the other 5 leave the next day |
| The notifier raises | No row, the day is given back, `errors` counted, the task does not raise; the next hourly run retries |
| Alerts disabled or no `email` channel | Nothing sent, status `no_email_channel` |
| A typed search (`rent`) and a drop on the Property's sale Listing | Nothing; a `both` search alerts it |
| Two Listings of one Property fell | One block, the larger drop |
| The search is deleted while its email is being sent | The email leaves; nothing is recorded; no error |

### What the task returns

`tasks.send_saved_search_new_match_alerts` returns its Story 1.9 keys plus `price_drops`:

| Key | Meaning |
|---|---|
| `status` | `ok`, `skipped` (pass disabled, `alerts.price_drop` absent, or the master switch off), `no_email_channel`, or `error` (the pass failed outside one search, for example loading the searches; `errors` is 1) |
| `searches_due` | Searches with drop alerts active whose window was due on this run |
| `emails_sent`, `properties_alerted` | What left |
| `unsupported` | Due searches that are not a membership test |
| `errors` | Failed sends, failed searches, failed releases |

The pass logs `saved_search_price_drop_alerts_run` with that dict. If the new-match part raises, the drop pass still runs and the task then raises the original error. If the drop pass raises, the task logs `saved_search_price_drop_alerts_failed` and still returns the new-match result.

### The email

Plain text, `pt-BR` or `en` from `ui.locale`. Subject: `2 quedas de preço na busca “Savassi 2q”` (the name on one line).

```
Busca salva: Savassi 2q
1 imóvel desta busca baixou de preço.

1. Apartamento Savassi
   Savassi, Belo Horizonte
   R$ 3.240/mês → R$ 3.000/mês · QuintoAndar
   queda de R$ 240 — seu mínimo: R$ 100
   http://localhost:5173/properties/42

Você recebe este e-mail porque os avisos estão ligados para esta busca, com queda mínima de R$ 100. Para mudar, abra Buscas salvas.
```

| Line | Shown when |
|---|---|
| Title, else the stored type capitalised, else `Imóvel` | always |
| Neighbourhood, city | stored |
| Old price → new price, `/mês` on both for a rent Listing, ` · <platform>` | always; the platform when stored |
| `queda de R$ <drop> — seu mínimo: R$ <threshold>` | always. The threshold is the one stored for the search when the email is sent; the same value goes on the alert row |
| `<app_base_url>/properties/<public_id>` | `alerts.new_match.app_base_url` is set |
| `+N nesta busca chegam no próximo aviso.` | more drops than `max_items_per_email` |

Money is whole reais without decimals, otherwise two decimals (`1.234,50` in pt-BR, `1,234.50` in en). The first line (`Busca salva: …`) is the one the new-match email also opens with.

### API

`SavedSearchItem` gains two read-only fields.

| Field | Type | Meaning |
|---|---|---|
| `price_drop_enabled_at` | string (naive UTC) or null | The floor |
| `last_price_drop_alert_on` | date string or null | Local date of the last drop email |

- `POST` that creates a search with the switch on and a threshold stamps the floor.
- `PATCH` after which drop alerts are active when they were not before stamps it: the switch turned on with a threshold stored, a threshold set while on, or both in one write.
- Any other write leaves it: changing the threshold while active, switching off, clearing the threshold, renaming.
- The `notify_enabled_at` rule of Story 1.9 is unchanged. `src/api/schemas.py` and the filter wire are untouched.

### Schema (revision `a8b9c0d1e2f3`, after `f7a8b9c0d1e2`)

- `saved_searches`: `price_drop_enabled_at TIMESTAMP NULL`, `price_drop_last_window_on DATE NULL`.
- `saved_search_price_drop_alerts`: `id`, `saved_search_id`, `property_id`, `property_listing_id` (all three `ON DELETE CASCADE`), `owner`, `listing_type`, `platform`, `reference_price`, `new_price`, `threshold`, `sent_at`. CHECK `ck_saved_search_price_drop_alerts_drop` (`new_price < reference_price AND threshold >= 0`). Index `ix_saved_search_price_drop_alerts_lookup` on (`saved_search_id`, `property_listing_id`, `sent_at`), plus the Property index.
- Reversible. One backfill: a search that already has the switch on and a minimum stored when the migration runs gets `price_drop_enabled_at = now` (UTC), so it is active from the migration on. Such a search can only exist if both were set through the API after Story 1.9.

### Config (`alerts.price_drop`)

| Key | Default | Rule |
|---|---|---|
| `enabled` | `true` | Switch of the drop pass. The pass also needs `alerts.new_match.enabled`, the master switch of the hourly task. |
| `max_items_per_email` | `20` | ≥ 1 |

Window hour, timezone and `app_base_url` are read from `alerts.new_match`. A host overrides a key with `IMOVEIS_ALERTS__PRICE_DROP__<KEY>`.

### Decisions taken in this story

Product-visible first.

| Question | Decision | Why |
|---|---|---|
| What a per-search drop alert covers | Listings of active, decidable Properties that match the search now, whether or not the Property was ever a new match of it. The announced Listing itself is within the search's type, price cap and platform. | The UX contract scopes drops to saved searches; a home that falls into the price range is the case the user saved the search for. |
| What a drop is measured against | One Listing's own earlier price, from `price_history`: the last price this search alerted for it, else its price when drop alerts became active, else its first price after that. Never another Listing's price. | Platforms publish different headline prices for the same home; a cheaper Listing appearing is not a price change. |
| Empty threshold | No drop alerts. `0` is a threshold: any drop. | Nothing emails anyone unasked. |
| Unit and input format | Absolute reais on the headline price, for rent and sale alike. The field takes `240`, `1.500`, `1500,50`, `R$ 240`; stored as a number with at most two decimals. No percent. | UX-DR13 states the threshold in reais (`seu mínimo: R$ 100`). |
| Which threshold the email states | The one stored for the search when the email is sent; the same value is stored on the alert row. | It is the one the user can see and change in the row. |
| Unsupported search | No switch, no field, one line saying the search does not produce email alerts. A search that is still on keeps the switch so it can be switched off. Such a search sends no drop email either. | A switch that does nothing would misreport the state. |
| Daily window | Drops leave in their own email, at most one per search per local day, from the same hour and timezone as new matches. A search can therefore send two emails on one day (new matches, drops). | Two different reasons; the Story 1.9 sender was left as reviewed. |
| Relation to the watchlist drop alert | None: the two are independent, and a Property that is both watched and covered by a search with drop alerts can get both emails for one drop. The first version of this story left out a Listing whose current price equalled `watchlist.last_notified_price`; the follow-up review removed that (2026-10-08). | The stamp says a price was once handed to the watchlist path, not that this drop reached anyone. It is written when the alert is enqueued (before the one-hour debounce and before delivery, whose SMTP errors are swallowed), and it survives a later rise: a Listing stamped at R$ 3.000 that goes up and falls back to R$ 3.000 fires no watchlist alert (0% below the stamp) and would have been left out here too, so nobody would say it. Failure direction chosen: at most one extra email, never a missed drop. The primary had no watchlist row when this was decided. |
| Repeat alerts | A search alerts a Listing again only after a further drop of at least the threshold below the last alerted price. Switching the search off and on, or clearing and setting the threshold, starts over from the current prices. | The alerted price is the memory; there is no once-per-pair lock, because a later, deeper drop is news. |
| Email wording | Subject `N quedas de preço na busca “<name>”`; per home: title, place, `R$ 3.240/mês → R$ 3.000/mês · QuintoAndar`, `queda de R$ 240 — seu mínimo: R$ 100`, link when configured; footer says why and where to change it. | The quoted fragment of UX-DR13, in every block. |
| Where Buscas salvas is | The existing Painel sidebar section. No top-nav route was added. | The acceptance criteria ask for the row; a new surface is a larger change than this story. |
| Row does not show the last email date | `last_new_match_alert_on` and `last_price_drop_alert_on` are in the API only. | UX-DR13 lists name, summary, switch and threshold. |
| One switch or two | One switch per search (`Avisos por e-mail`). The threshold field is what turns drop alerts on: empty means none. | The stored model has one flag and one nullable threshold; a second switch would be a second source of truth for "no drop alerts". |
| Threshold field while the switch is off | Shown and editable; the value is stored; the state line still says `Avisos desligados`. | The user can set a search up and switch it on once. Nothing is sent until the switch is on. |
| Which drops over the limit leave first | The largest. The rest are not recorded and are found again the next day, if they still hold. | A recorded alert is one that was shown. |
| Platform in the email | The display name for the three known platforms (`QuintoAndar`, `OLX`, `ZapImóveis`), the stored slug otherwise. | A name reads better than a slug in an email. The SPA has labels for the first two only (`frontend/src/labels.ts`), so a `zapimoveis` filter still reads as the slug in the row's summary. |
| Opening line of the email | `Busca salva: <name>`, as in the new-match email. | The body names the search without relying on the subject. Not asked for by the spec; it adds a line, changes none. |
| Sidebar width | 272px at the design frame, narrowing to 232px at a 1280px viewport, instead of a fixed 272px. | With a fixed 272px the card grid loses 26px per card at 1280px, and the percentile badge of a dual-type card with the `2 plataformas` chip overflows its price line by 16px (`percentile-badge-filter.spec.js` › "a dual card carries one badge per price line" fails; measured: it passes up to 239px). The card CSS belongs to Story 1.7 and was left alone. The row was laid out to fit 232px. |
| Unused sidebar CSS | `.sidebar-list` and `.sidebar-item*` were removed with the markup that used them. | Nothing else referenced them. |

## Notes / Follow-ups

- **A search that had the switch on and a threshold before this migration is active from the migration on** (the migration stamps its floor). The primary had no saved search when Story 1.9 measured it (2026-10-08).
- **Editing the filters of an active search does not move the floor**, as in Story 1.9. Listings that match the new filters and fell at any time since the floor are alerted in the next email. The SPA has no filter editing for a stored search; only `PATCH` through the API can do this.
- **Switch and threshold written together.** The row sends two requests. The API reads the search under a row lock before deciding the stamps, and the SPA takes only the written field from each response, so neither a lost stamp nor a stale field results.
- **The drop statement, measured on the primary (2026-10-08, read-only session, the last-alert subquery left out because its table does not exist there yet).** 206,429 Properties, 288,704 Listings, 321,691 `price_history` rows of which 32,983 are closed, on 22,302 Listings. A search with no filters and a floor 30 days back: 1,575 candidate rows in 0.70 s. The worst case, a floor before all history (2.5 months): 2,756 rows (2,145 of them below their reference) in 0.46 to 0.68 s over three runs. The parallel scan of `price_history` by `end_ts` is about 35 ms of that; the rest is the join to `properties` and `metrics_scoring` for every changed Listing. No index was added: an index leading on `end_ts` would save tens of milliseconds on a statement that runs once an hour per due search. The search's row lock is held while the statement runs, so a `PATCH` of that search arriving in that moment waits for it (under a second). A search whose drops never reach its threshold stays due all day and runs the statement on every hourly run from the window hour on. Measure again if `price_history` grows by an order of magnitude or many searches are switched on.
- **A Listing needs `price_history` rows that carry its `property_listing_id`.** A row without it is not a reference. Measured on the primary (2026-10-08): no `price_history` row lacks it (0 of 321,691) and every active Listing has a listing-scoped open interval (0 of 288,164 without), so this does not occur there.
- **The threshold applied is the one stored when the email is sent**, not the one stored when the price fell. Raising it before the window suppresses a drop that would have qualified; lowering it can alert a drop from days ago, as long as it is after the floor.
- **A drop over the per-email limit is not remembered.** It is found again the next day if it still holds. If the price went back up meanwhile, it is never emailed.
- **A watched Property can get two emails for one drop**: the watchlist alert (`Property <id>: old -> new`) and, at the next window, the search's drop email. They are different subscriptions and each says which one it is. The watchlist path's own defect stays where it was: it stamps `last_notified_price` when it enqueues, so a watchlist alert that is debounced or fails to send is not retried (deferred in the spec; the fix belongs to that path).
- **An alert row is dated at the run's clock, or at the floor when the floor is later** (a search switched on while the run was already going), so it is always read as the reference of the next comparison.
- **A new Property that also dropped can be in two emails on one day**: the new-match email and the drop email. They are different reasons.
- **`searches_due` counts unmatchable searches too**; they are also counted in `unsupported`.
- **The timestamps assume a UTC database session**, as in Story 1.9: `price_history.start_ts` and the floor are compared as naive UTC. The primary's session `TimeZone` is `UTC` (checked 2026-10-08).
- **A worker killed between the claim and the send** leaves the day claimed with nothing sent. Nothing was recorded, so the drops leave the next day if they still hold.
- **The email left and recording then failed**: the day stays claimed and the same drops are emailed again the next day. A second path to a repeated Property: its drop did not fit under the per-email limit on one day (not recorded) and leaves the next day, which is a first email for that drop.
- **The row shows no date of the last email.** `last_new_match_alert_on` and `last_price_drop_alert_on` are in the API and typed in `api.ts`; nothing renders them.
- **The sidebar list scrolls** once the rows are taller than `min(62vh, 560px)`.
- **The card grid is at the edge of its width at a 1280px viewport.** Before this story the badge of a dual-type card had about 10px of slack on its price line there; the sidebar now takes 12px more at that width. Any later change that narrows the grid at 1280px will make that badge overflow its line again (the Story 1.7 e2e catches it).
- **`formatDropThreshold` relies on the browser's locale data** for grouping (`1.500` in pt-BR). The field reads both groupings back.
- **The email notifier has no TLS** and the price-drop watchlist email methods still swallow SMTP errors (both noted in Story 1.9; unchanged).
- **The gate's `alembic check` is informational** and reports the same drift as before this story (PostGIS tables, `saved_searches.filters` JSONB). The integration test `test_models_match_the_migrated_schema` compares what this story added and finds no difference.
