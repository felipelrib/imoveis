# Backfill TPM token-bucket — proactive tokens-per-minute pacing

> Feature branch: `feat/v0.13-fu2-backfill-tpm-limiter` · Story: `v0.13-fu2-backfill-tpm-limiter` · Status: implemented

## Problem

The Gemma backfill runner gated on **RPD** (daily request budget) and **RPM** (launch interval) but had
**no proactive TPM limiting** — the concurrency work deliberately relied on the client's 429 exponential
backoff to absorb the 16K tokens-per-minute ceiling. That was the wrong call:

- backoff reacts only *after* the limit is breached, so a structurally-too-fast run throttles continuously;
- every retry issues an extra request that the daily-budget counter does **not** track, silently eating RPD;
- the operator sees opaque "quota" errors rather than the runner self-pacing.

A `--concurrency 4` run hit **21.15k / 16k tokens per minute** and the API started rejecting calls.

**Measured token cost** (oracle-first, live `gemma-4-31b-it`, 8 images @768px):

| Stage | total_tokens |
|---|---|
| visual (8 images) | ~3,538 (prompt 2,859 + completion + thought) |
| sentiment | ~1,706 |
| verdict | ~1,706 |
| **per property** | **~7,000** |

At 16,000 TPM that is a hard ceiling of **~2.3 properties/min**. The failing run did ~3.3/min
(33 per 10 min) ≈ 23,100 tokens/min — matching the observed overshoot exactly.

## Approach

- **`TokenBudget`** — a sliding-60-second token limiter in `core/backfill_runner.py`. Before a property
  launches, the runner asks `seconds_until_room()`, sleeps that long if needed, then `reserve()`s the
  property's estimated tokens. Reservations age out of the trailing window, so the cap holds continuously.
  Clock and sleep are injected, so the whole thing unit-tests deterministically with no real waiting.
- **Safety margin** (`tpm_safety_margin`, default 0.9) leaves headroom for properties that tokenize above
  the estimate — the estimate is per-property average, not a guarantee.
- **Partial-expiry waiting**: it waits only long enough for the *oldest* reservations to leave the window,
  not a blanket 60s, so throughput stays as high as the cap allows.
- **No deadlock** on a property that alone exceeds the cap: the wait is bounded by the window, so an
  oversized property proceeds (and the provider's own backoff remains the last line of defence).
- **Opt-in**: `token_budget=None` preserves the previous behaviour exactly (back-compat, and dry-runs skip it).
- TPM now becomes the *effective* governor, so `--concurrency` self-regulates: asking for 4 no longer
  overshoots, it just means up to 4 in flight whenever the token window allows.

## Notes / Follow-ups

- **Realistic throughput is ~2 properties/min ≈ 2,900/day** (TPM-bound, not RPD-bound). RPD (14,400 ≈ 4,800
  properties) is no longer the binding constraint for image-heavy enrichment.
- **Lever if more speed is needed:** `ai.max_images_per_property` 8→4 roughly halves the visual stage
  (~3,538 → ~1,800 tokens), lifting the ceiling to ~4 properties/min until RPD binds instead. That trades
  visual signal for speed — BIN-242 chose 8 images, so it is deliberately left unchanged here.
- `tokens_per_property` is an **estimate**, not metered usage. A future refinement could feed the actual
  `usage.total_tokens` from each response back into the limiter for exact accounting.
- Related: `BIN-248` (runner), `BIN-268` (continuous mode), `BIN-269` (concurrency — the defect this fixes).
