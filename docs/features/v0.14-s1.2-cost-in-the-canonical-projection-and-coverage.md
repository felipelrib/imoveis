# Cost in the canonical projection and coverage — the API shows each Listing's stored cost, names the Listing that decides a Property's monthly cost, and reports cost completeness per Platform

> Feature branch: `feat/v0.14-s1.2-cost-in-the-canonical-projection-and-coverage` (bmad-loop: `bmad-loop/<run>/1-2-cost-in-the-canonical-projection-and-coverage`) · Story: `v0.14-s1.2` · Status: implemented

## Problem

Story 1.1 stored the Total Monthly Cost columns on `property_listings`, but nothing read them (FR-31, AD-12, NFR-6, SM-3):

- The API projection still showed only the legacy `price` / `condo_fee` / `iptu`.
- No view said which Listing decides a rent Property's monthly cost.
- `GET /properties` could not sort or cap by total.
- Coverage telemetry could not report cost completeness.

## Approach

- **One serializer.** `core/property_projection.py` is the AD-12 serializer behind list, by-ids, export, detail and the digest. Both mappers now share `_listing_views`, so every view carries the same cost fields.
- **Stored values, labelled.** Each Listing gains `id` and a nested `cost` object. Every figure is the stored column copied as is. The `*_state` fields are labels derived only from which columns are NULL or true. There is no arithmetic, no fallback to the legacy `price` / `condo_fee` / `iptu` / `base_price`, and a NULL component is never read as 0.
- **Nested `cost`, not flat keys.** A Listing already has a top-level `fees_bundled` read from `raw_json`, with a different meaning from the new column. Nesting keeps both. Inside the SQL the column travels as `cost_fees_bundled` and is moved under `cost.fees_bundled` by the serializer.
- **One deciding Listing per Property.** `deciding_listing_id`, `deciding_rule` and `total_monthly_cost` are set by `select_deciding_listing`. `select_primary_listing`, `price` and `primary_listing` are unchanged.
- **Sort and cap read `total_monthly_cost` only.** They use the same predicate as the deciding choice (active, rent, total not NULL), so the list order cannot disagree with the total shown. The SQL is static text with one bound parameter (BIN-135).
- **Coverage.** One grouped query counts active rent Listings of active Properties per Platform; the pure builder in `core/enrichment_coverage.py` adds `total` and the fractions.
- **No index, no migration.** The correlated subqueries use the existing `property_listings.property_id` index, like `sort_by=price`.

### Listing states

| Field | State | When |
|---|---|---|
| `rent_state` | `not-applicable` | Sale Listing |
| | `known` / `unknown` | Rent Listing with / without `rent_monthly` |
| `condo_fee_state`, `iptu_state` | `bundled` | `fees_bundled` is true |
| | `known` / `unknown` | Otherwise, value present / NULL |
| `total_state` | `not-applicable` | Sale Listing |
| | `incomplete` | Rent Listing, total NULL |
| | `bundled` | Rent Listing, total present, `fees_bundled` true |
| | `complete` | Rent Listing, total present, not bundled |

A row without the cost keys (older fake rows, digest fixtures) reads every component as `unknown`.

### Deciding rule

| Case | `deciding_listing_id` | `deciding_rule` | Property `total_monthly_cost` |
|---|---|---|---|
| An active rent Listing has a total | The one with the lowest total (ties: `platform`, then `id`, ascending) | `lowest-complete-total` | That Listing's stored total |
| No active rent Listing has a total (includes sale-only) | `primary_listing.id` | `lowest-headline-price` | `null` |
| No priced Listing | `null` | `null` | `null` |

### Sort and cap

| Parameter | Behaviour |
|---|---|
| `sort_by=total_monthly_cost` | Orders by the lowest total among active rent Listings. Properties without one sort last in both directions (`NULLS LAST`). |
| `max_total_monthly_cost=<n>` (≥ 0) | Keeps Properties with an active rent Listing whose total is at or under `n`. |
| `include_incomplete_totals=true` | With a cap: also keeps Properties that have an active rent Listing but none with a total. Alone: no effect. A sale-only Property stays out. |

The same parameters exist on `/properties/export`.

### Coverage block

`GET /admin/enrichment/coverage` gains `cost_completeness`: one row per Platform with `total`, `complete`, `bundled`, `incomplete` and the three fractions. The counts are mutually exclusive and sum to `total`. Rows are ordered by platform. A Platform with no active rent Listing has no row.

## How to Test

1. Run the gate:
   ```bash
   python scripts/agent/validate.py
   ```
   Expected: `VALIDATION PASSED (tier=backend)`.
2. Against a migrated database with cost data:
   - `GET /properties?sort_by=total_monthly_cost&sort_dir=asc` — totals ascend, Properties without a total come last.
   - `GET /properties?max_total_monthly_cost=4000` — every Property has `deciding_rule` `lowest-complete-total` and a total at or under 4000.
   - `GET /admin/enrichment/coverage` — for every `cost_completeness` row, `complete + bundled + incomplete == total`.

## Notes / Follow-ups

- **Deploy order.** The projection SELECTs Story 1.1's columns. The primary must be migrated (Story 1.1's operator steps) before an API image built from this story runs; otherwise every Property read fails. This story adds no operator step of its own.
- **Empty until the backfill runs.** Until Story 1.1's `tasks.backfill_listing_costs` has run on the primary, stored Listings have no total: every Property reads `lowest-headline-price`, and the cap returns nothing.
- **`PropertyListingModel.cost` is optional in the schema** so hand-built payloads without it still validate. The serializer always emits it.
- **Semantic search ignores the sort.** With `q`, results are ordered by embedding distance, as for every other `sort_by`. The cap still applies.
- **Saved searches** keep their own filter model (`saved_searches.py`, out of scope), so a saved search cannot store the cap yet.
- The UI does not render cost yet (Story 1.8), and the cohort price basis is unchanged (Story 1.3).
