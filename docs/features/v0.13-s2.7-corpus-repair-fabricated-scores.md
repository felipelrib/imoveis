# Corpus repair — rows poisoned with fabricated AI scores before story 3.2

> Feature branch: `bmad-loop/20260813-054802-28e6/2-7-corpus-repair-fabricated-scores` · Story: `v0.13-s2.7` · Status: implemented, **awaiting operator apply** (the migration ships un-applied against the primary corpus — see the operator procedure below)

## Problem

Before story 3.2 landed, every exception fallback inside the AI client persisted a **fabricated** result instead of failing: `condition_score` / `sentiment_score` set to `0.5` and `analysis` set to the literal string `"Error"` (`src/adapters/ai/client.py:683,712,870,906`). `run_enrichment` then blended those invented halves into `metrics_scoring.ai_score`, stored the fabrication under `meta['visual']` / `meta['sentiment']`, and committed.

That is not merely a wrong number on a row. `core.enrichment_rerun.mode_is_missing_ai` is literally `not score` (`src/core/enrichment_rerun.py:85-91`) and the SQL candidate push-down is `ai_score IS NULL OR ai_score = 0` (`:279-286`), so a truthy fabricated score removes the property from the enrichment candidate set **permanently** — no census, no re-run, no restart ever looks at it again.

Story 3.2 closed the tap (a degraded result now raises `AIResultDegradedError` *before* `SessionLocal()`, so nothing is written) but repaired nothing retroactively. These rows are the missing half of the Epic 3 → Epic 2 gate: story 2.1 computes cohort percentiles and must not compute them over a corpus still carrying known-fabricated scores, and the poisoned rows cannot heal themselves.

## Approach

- **A one-off, data-only Alembic migration** (`f3a7c81d5e42`) that runs a single set-based `UPDATE metrics_scoring SET ai_score = NULL` over exactly the rows carrying the fabrication marker. `mode=missing` then re-admits them and the running backfill re-enriches them on its next census — no process restart, no code change, no schema change.

- **Why a migration, and not the two alternatives.** The decision is on record because Epic 2's technical decisions require it (*"forensic predicates are one-off artifacts … the delivery mechanism is recorded with its rationale"*):

  | Mechanism | Verdict | Rationale |
  |---|---|---|
  | Data-only Alembic migration | **chosen** | `alembic_version` makes it run exactly once *by construction*, so it can never become a recurring path. The forensic predicate sits in a versioned one-off artifact, outside `src/`. And `scripts/agent/migrate-primary.sh` is already the sanctioned guarded path to the primary corpus: it takes `backfill:gemma:migrating` and refuses on a live `backfill:gemma:active` heartbeat, so **on that entry point** the repair inherits the backfill mutual exclusion (v0.13-fu6) for free — no new guard code. It is not the only entry point; see *Caveat: `migrate-primary.sh` is not the only path to `upgrade head`* below. |
  | `scripts/dev/` script | rejected | It matches the one-off-surgery precedent and has a nicer dry-run, but an unguarded script must never run against a live backfill — so it would have to **re-implement** the migration/backfill lock handshake, a divergent second copy of exactly the machinery v0.13-fu6 centralized. |
  | Admin endpoint | rejected | It would put the `analysis == "Error"` string inside feature code, on a re-runnable route. Story 3.2's contract forbids that explicitly: `degraded: bool` (`src/adapters/ai/client.py:328-340`) is the runtime marker and stays the only one. |

- **This deliberately widens the story's written AC.** The epic AC describes the signature as the marker *"with `ai_score` sitting on the configured `visual_weight`/`text_weight` blend of 0.5"* (`_bmad-output/planning-artifacts/epics.md:551`). The implementation drops the value half and repairs on the marker alone, which is a **larger** population than the AC literally names. That is a recorded deviation, not a reading of the AC — the rationale is immediately below, and the migration reports both populations so the widening is visible in the operator's output.

- **Why the marker, not the `0.5` blend, is the predicate.** With the shipped weights (`ai.visual_weight` 0.7 / `ai.text_weight` 0.3) a *doubly* fabricated row lands on exactly `0.5` (`0.35 + 0.15`). But a row whose visual half was fabricated beside an honest sentiment of `0.8` lands on `0.59` — still half-invented, still permanently uncandidatable. Keying on the blend value alone would knowingly leave that population poisoned forever. Keying on the marker cannot produce a false positive either: no honest path writes `analysis = 'Error'` (`neutral_sentiment_no_description()` writes `""` plus an explicit sentinel `reasoning`, BIN-243), and post-3.2 no degraded result is persisted at all — so the marker describes a **closed, pre-3.2-only population**. The asymmetry settles it: over-repair self-heals through one re-enrichment, under-repair is permanent. The migration still reports the on-blend sub-count separately so the operator sees both populations.

- **`json`, never `jsonb`.** `metrics_scoring.meta` is a Postgres `json` column. Casting it to `jsonb` rejects NUL unicode escapes that scraped free text legitimately carries, which would turn the repair into a hard failure. Extraction uses `->` / `->>` only, and every extraction is wrapped in a nested `CASE WHEN json_typeof(...) = 'object'` guard — `json -> text` is undefined for scalars and SQL `AND` is not guaranteed to short-circuit, so a row whose `meta` is `'"broken"'`, `'null'`, or `{"visual": 3}` has to be excluded *before* the extraction is attempted. Same shape as `src/adapters/db/enrichment_coverage_queries.py:87-131`.

- **Set-based, never read-then-write**, so a row honestly re-scored between planning and execution simply stops matching instead of being clobbered by a stale id list.

- **The predicate has exactly one definition.** It lives in `FABRICATION_PREDICATE_SQL` inside the migration; the integration suite loads that module *by path* (`importlib.util.spec_from_file_location`) rather than restating the string, because `alembic/versions` is not an importable package and because the story forbids the `'Error'` test from entering `src/`.

- **`downgrade()` is a deliberate, logged no-op.** The pre-image is not faithfully recoverable: doubly fabricated rows sat on the blend constant, but half-fabricated rows sat on an arbitrary value derived from their honest half. Restoring the constant to all of them would *invent* data — the exact failure this migration repairs. Downgrading leaves the rows as honest NULLs, which every consumer already handles.

## How to Test

```bash
bash scripts/agent/validate.sh backend   # lint + unit + integration + contract
bash scripts/agent/validate.sh all       # full gate before merge-back
```

`validate.sh backend` runs `alembic upgrade head` against the **ephemeral** test DB (`scripts/agent/ensure-test-db.sh`), so it proves the migration applies to an empty schema, affects 0 rows and does not change `alembic check`'s verdict (that check is informational-only here — PostGIS system tables always report as "extra"). The new suite (`src/tests/integration/test_corpus_repair_fabricated_scores.py`) then seeds the story's whole edge-case matrix against real Postgres and asserts:

- the include/exclude verdict of every matrix row, including the JSON-scalar rows, whose assertion is that the query **returns at all** rather than raising *"cannot extract element from a scalar"*;
- `apply_repair()`'s returned `{"repaired", "on_blend"}` counts;
- that every excluded row keeps its exact `ai_score` and its byte-identical `meta` text;
- the characterization lock: `mode_is_missing_ai` flips `False → True` for a poisoned row and stays `False` for the honest neutral-sentiment row.

Never run raw `pytest` — `validate.sh` owns the ephemeral stack.

## Notes / Follow-ups

### Operator procedure — applying the repair to the primary `realestate` DB

No agent applies this. The migration ships un-applied against the primary corpus; the guarded operator step is:

1. **Check what is running.** `PYTHONPATH=src python scripts/dev/backfill_gemma.py --status` — note `enriched` / `remaining`, and whether a runner holds the lease.
2. **Dry-run the guard.** `bash scripts/agent/migrate-primary.sh --dry-run` — probes `backfill:gemma:active` and `backfill:gemma:migrating` and changes nothing. If it reports a live heartbeat, stop the runner (`--stop`, or `systemctl --user stop imoveis-backfill`) and re-check; never delete either key by hand — both self-clear on their TTLs.
3. **Apply.** `bash scripts/agent/migrate-primary.sh` from the **primary** checkout. Run it from the primary checkout deliberately — the script's worktree refusal only fires when a `.env.local` *exists* and names a non-primary `COMPOSE_PROJECT_NAME` (`scripts/agent/migrate-primary.sh:51-57`); a worktree with **no** `.env.local` falls straight through to the primary defaults (`localhost:5432/realestate`) and would migrate the primary from that checkout's revision. It takes `backfill:gemma:migrating` for the whole upgrade, releases it on exit, and runs `alembic upgrade head`.
4. **Read the count.** The upgrade prints, at INFO on the `alembic` logger:
   `v0.13-s2.7 corpus repair: nulled N fabricated ai_score metrics rows (M of them sat on the 0.5 doubly-fabricated blend)`.
   `N` is the repaired population; `M` is the doubly-fabricated subset. `M < N` is expected and correct — the difference is the half-fabricated rows that a blend-value predicate would have missed. Both are **`metrics_scoring` row** counts, not property counts (`property_id` has no unique constraint), so a property with a duplicated metrics row contributes twice.
5. **Verify re-admission.** `PYTHONPATH=src python scripts/dev/backfill_gemma.py --status` again: `remaining` should have grown by roughly `N`, and `--dry-run` should now plan them. Expect it to grow by *less* than `N`: the candidate path is `active_only` and photo-gated, so inactive and photo-less repaired rows are re-admitted to the SQL predicate but not to the work queue. No restart is needed — the candidate push-down is already `ai_score IS NULL OR ai_score = 0`.
6. **Restart the backfill** and let it re-enrich the re-admitted rows normally.

The repair leaves no persistent per-row record: `meta` is deliberately untouched and `metrics_scoring.updated_at` uses SQLAlchemy's ORM-level `onupdate`, which does **not** fire for a raw SQL `UPDATE`. So `N`/`M` from step 4 are the outcome evidence — record them. If the log line is lost, this **read-only** query recovers the picture at any time (it is the migration's own predicate, run as a `SELECT`):

```sql
SELECT count(*)                                        AS marker_rows,
       count(*) FILTER (WHERE ai_score IS NOT NULL)    AS still_poisoned,
       count(*) FILTER (WHERE ai_score IS NULL)        AS repaired_or_never_scored
  FROM metrics_scoring
 WHERE CASE WHEN json_typeof(meta) = 'object' THEN
              COALESCE(CASE WHEN json_typeof(meta -> 'visual') = 'object'
                            THEN meta -> 'visual' ->> 'analysis' = 'Error'
                            ELSE false END, false)
           OR COALESCE(CASE WHEN json_typeof(meta -> 'sentiment') = 'object'
                            THEN meta -> 'sentiment' ->> 'analysis' = 'Error'
                            ELSE false END, false)
            ELSE false END;
```

`still_poisoned = 0` means the repair has been applied (or there was nothing to repair). Run it **before** step 3 too, and `still_poisoned` is the `N` you should expect.

### Caveat: `migrate-primary.sh` is not the only path to `upgrade head`

This is **DW-32** (`_bmad-output/implementation-artifacts/deferred-work.md`, open, high, scheduled in this same Wave 0), and this story is what raises its stakes: `scripts/start.sh:63` and `scripts/agent/run-services.sh:42` both run `alembic upgrade head` in the `api` container against the primary project, with **no** `backfill:gemma:migrating` lock and **no** `:active` heartbeat probe. Until DW-32 lands:

- A `./scripts/start.sh` (or `restart.sh`, which forwards to it) on the primary checkout can apply this repair without the mutual exclusion the operator procedure above relies on.
- `start.sh` captures the migration output into `$MIGRATION_OUTPUT` and echoes it **only on failure**, so on the success path the `N`/`M` line is discarded. If the stack was started before the deliberate apply, the migration is already applied and step 4 will print nothing — use the recovery query above instead.

Concurrent application is not corrupting for *this* migration specifically (poisoned rows are by definition outside a running pass's candidate snapshot, so there is no write conflict), but it does bypass the documented procedure and lose the outcome evidence.

### Residual: `combined_score` is deliberately not touched

`combined_score` / `combined_score_rent` / `combined_score_sale` blend `ai_score` (`src/adapters/metrics/scoring.py:98-107`), so a repaired row keeps the fabricated AI **term** in its combined score until it is next re-enriched or re-scored. This is bounded and self-healing, not debt left open:

- `blend_combined_score` reads `float(ai_score or 0.0)`, so **both** paths that next touch the row — re-enrichment (`src/adapters/queue/tasks.py:704`) and stat scoring (`src/adapters/metrics/scoring.py:164`) — recompute it honestly.
- It is off story 2.1's path entirely: 2.1's percentiles are **price/m²**-based, not score-based, so nothing in the gated work reads the stale term.
- Nulling it instead would drop the rows out of the top-deals digest (`src/core/top_deals_digest.py:31-32` filters `combined_score IS NOT NULL`) for a window, for no gate benefit.

**The self-healing is not universal.** Re-enrichment only reaches rows the candidate path visits, and that path is `active_only` (`src/core/enrichment_rerun.py:264-265`, `scripts/dev/backfill_gemma.py:266`) and photo-gated (`passes_photo_gate`). Two populations therefore keep a stale AI term in `combined_score` indefinitely:

- **Inactive properties.** `QueueCensus`'s own docstring (`src/core/backfill_runner.py:1216-1220`) records 494 inactive un-enriched listings on 2026-08-05, so this is a real population, not a corner case. Their next stat-scoring pass still recomputes `combined_score` honestly (`_update_metrics_score` reads `ms.ai_score or 0.0` and is not `active`-gated), so the term heals on the *scoring* path even where the *enrichment* path never returns.
- **Photo-less properties.** They are re-admitted to the SQL candidate set and then held by the photo gate, counted as `blocked_no_photos`. Their `ai_score` stays NULL — which is the honest outcome, and strictly better than the fabricated value they carried before.

Recorded here as a bounded residual rather than minted as ledger noise. The two genuinely unbounded findings around it *are* on the ledger — see below.

### Caveat: the attempt ledger is Redis-side and is not cleared on success

Row retirement also has a Redis half — the attempt ledger at `<prefix>:attempts`, with `is_quarantined` at `src/core/backfill_runner.py:1346-1347`, `backfill.max_attempts` 3 and a 30-day TTL — and it is **not** cleared on success. A pre-3.2 poisoned row left the candidate set after its one successful-looking attempt, so it should sit at `attempts == 1` and need nothing. That is expected, not guaranteed: after applying the repair, read `backfill_gemma.py --status` and only if repaired rows show up quarantined consider `backfill_gemma.py --reset-quarantine`. The migration itself never touches Redis.

### Ledger entries opened by this story's review

Both are pre-existing holes this work surfaced rather than caused, and both are recorded in `_bmad-output/implementation-artifacts/deferred-work.md`:

- **A second, still-live fabricated-`0.5` population the marker cannot see.** The non-exception `build()` paths in `src/adapters/ai/client.py:667,699,858,893` do `data.get("condition_score", 0.5)` / `data.get("sentiment_score", 0.5)`. A model that returns parseable JSON *without* the score key yields a fabricated `0.5` carrying neither `analysis = 'Error'` nor `degraded: true` — invisible to `mode_is_missing_ai`, invisible to story 3.2's breaker, and invisible to this repair. Story 3.2 closed the exception tap; this tap is still open.
- **Repaired rows keep their fabricated `meta` blobs.** That is deliberate (forensic evidence, and the recovery query above depends on it), but it has two consequences: `STAGES_VERDICT_ONLY` only requires `has_prior_visual_sentiment(meta)` (`src/core/enrichment_rerun.py:154-158`), so a `stages=verdict_only` rerun over the repaired population would feed `{"condition_score": 0.5, "analysis": "Error"}` into `client.summarize_deal` and persist a `deal_verdict` stamped `degraded: false`; and the enrichment-coverage card counts `meta -> 'visual' <> 'null'` as covered, so poisoned rows still read as visually enriched.

### Other notes

- The migration is a **one-off forensic artifact**. Nothing under `src/` may import it, and the `analysis == 'Error'` test must never become a runtime signal — `degraded: bool` is the runtime marker (story 3.2 / DW-17).
- The doubly-fabricated blend constant is **pinned at `0.5`**, not read from `get_config()`. The poisoned rows are frozen history — they were blended with the weights of the day — so deriving the constant from live config would move it off every poisoned row's value the moment the weights are retuned and report `on_blend = 0` with no signal, while making the test that seeds `ai_score = BLEND` tautological. Pinning also keeps `alembic/versions/` free of `src/` imports: alembic imports every version script to build its revision map, and `alembic history` / `heads` / `branches` do not run `env.py` first, so an `infra.config` import there breaks those commands whenever `src/` is not already on `PYTHONPATH`.
- Gate: this story gates `v0.13-s2.1` (cohort price/m² percentiles) — see `_bmad-output/planning-artifacts/epics.md` and the sequencing note in `sprint-status.yaml`. **The gate is not machine-enforced:** bmad-loop's `next_actionable` does not treat `awaiting-operator` as actionable, so with `2-7` at that status the queue advances to `2-1` (verified against the real parser). Until `2-7` is operator-confirmed `done`, `2-1` must not be started — the sequencing comment above the `2-1` key in `sprint-status.yaml` says so explicitly.
