# Backfill liveness is visible for the whole run — one ticker keeps the lease, the state and the `:active` heartbeat alive

> Feature branch: `feat/v0.14-s1.12-backfill-liveness-visible` · Story: `v0.14-s1.12` · Status: implemented

## Problem

A cloud backfill run is visible to everything else through three Redis keys under `backfill.redis_prefix`:

| Key | Meaning | TTL | Who reads it |
|---|---|---|---|
| `<prefix>:lease` | this process owns the run | `backfill.lease_ttl_seconds` (900 s) | a second runner, `--status`, the admin status endpoint, the supervisor |
| `<prefix>:state` | what the run is doing (`running`, `paused`, `backing-off`, `blocked`) | 120 s | `--status`, the admin status endpoint |
| `<prefix>:active` | rows may be written right now | 300 s | `scripts/agent/migrate-primary.sh` |

Each key was refreshed from a different event, so each had stretches where a live run stopped refreshing it:

| Entry | Key | Refreshed only | Stretch left uncovered | Effect |
|---|---|---|---|---|
| DW-9 | `:active` | when a row finished | one row slower than 300 s | `migrate-primary.sh` read an idle guard and migrated beside a live writer |
| DW-20 | `:state` | at a launch and when a row finished | one row slower than 120 s | `--status` and the admin endpoint said `idle` for a runner that held the lease |
| DW-21 | `:lease` | inside `run_backfill` and the two wait loops | the candidate fetch, the census, the gap between passes | the lease could lapse during a blocked database call and a second runner could start |
| DW-10 | `:lease` | — | a Redis outage longer than the lease TTL | the failures were logged and ignored, so the run kept launching on a lease that had expired |
| DW-34 | `<prefix>:supervisor:active` | in the supervisor's idle poll loop | the whole run the supervisor drives | `--status` said `supervisor: not running (--serve)` for a supervisor that was up |

## Approach

- **One `LivenessTicker`** in `src/core/backfill_runner.py` refreshes all three keys on a timer of its own. `main` builds and starts it right after `lease.acquire()` and stops it first in the exit `finally`, so it covers the whole run: the candidate fetch, every pass, the census, the budget sleep and the migration wait.
- **The run only says what is true.** `set_state(state)` records what the run is doing. `set_writing(True/False)` brackets a pass. `hold_heartbeat()` / `release_heartbeat()` bracket a pause with nothing in flight. The ticker does the refreshing.
- **A thread, not an asyncio task.** The uncovered stretches include blocking database calls outside any event loop, and a blocking section inside an enrichment delays a coroutine timer as much as it delays the row. The thread touches no asyncio object; the launch loop reads `liveness.lease_lost`, a property that reads the clock and may latch the loss, with no Redis I/O. `spec-dw-backfill-lease-background-renewer.md` (fu7) ruled a thread out, but it only had to cover awaits inside `run_backfill`.
- **Its own clock.** The fu7 timer never refreshed the state because `run_backfill`'s `clock` is injected and the unit tests pass finite sequences. The ticker takes a separate `clock` (default `time.monotonic`) and never calls the loop's.
- **Each key keeps its meaning.**

  | Key | Refreshed by the ticker | Cadence |
  |---|---|---|
  | lease | for the whole run | `lease_ttl_seconds / 3` (300 s) |
  | state | whatever the run last set, while the lease is held | `BackfillControl.refresh_interval_seconds` (30 s) |
  | `:active` | only inside a pass, from `set_writing(True)` to `set_writing(False)`, and not during a pause with nothing in flight | due every heartbeat TTL / 3 (100 s); beaten at the first wake-up at or after that, which is every 120 s with the shipped values |

  The thread wakes at the smallest of these (every 30 s) and runs only what is due, so a chore whose period is not a multiple of 30 s runs at the next wake-up after it falls due. 120 s is still well inside the 300 s TTL. During the budget sleep, the migration wait, the census and a pause with nothing in flight `:active` is not beaten, so a sleeping or paused runner still reads as idle to `migrate-primary.sh`.
- **Where a migration is allowed, stretch by stretch.** `<prefix>:active` means "rows may be written right now" and nothing else. `migrate-primary.sh` takes `<prefix>:migrating` first and then refuses if `:active` exists; the runner beats `:active` first and then reads `:migrating`. One of the two always sees the other, so a row is never launched into a migration, whichever stretch the migration starts in. The first acceptance criterion lists the heartbeat among what the ticker owns "across candidate fetch, census, in-flight rows and the inter-pass window": the ticker owns it there in the sense that it alone decides when the key is beaten, and outside a pass it does not beat it (ruling of the follow-up review, 2026-10-08, recorded in the spec's change log).

  | Stretch | Rows written | `:active` | `migrate-primary.sh` | `--status` and `GET /admin/backfill/status` | Why a migration starting here is safe |
  |---|---|---|---|---|---|
  | Candidate fetch and photo gating (pass start up to `_go`) | no | absent | allowed | `state` `running` (or `paused`), lease held (`active` true), `heartbeat_active` false | The fetch is a read. The migration either waits for the read's table lock or makes the read wait; the lease is renewed either way. Before its first launch the pass beats `:active` and reads `:migrating` (`_go`): with the key held it launches nothing, closes its session and goes to the migration wait |
  | Inside a pass: from the beat in `_go` to the clear, a slow row, the final drain, a pause with rows still in flight | yes | beaten (every 120 s, TTL 300 s) | refused | `running` or `paused`, `active` true, `heartbeat_active` true | The migration does not start |
  | Pause with nothing in flight | no | not beaten; lapses at most 300 s after the last beat | refused until the key lapses, then allowed | `paused`, `active` true, `heartbeat_active` false once lapsed | The pause poll reads `:migrating` on every poll and ends the pass as migration-blocked. A resume beats `:active` first, and the loop reads `:migrating` again after `sem.acquire()`, before the launch |
  | Census, and the gap up to the next pass | no | absent (cleared when the pass ended) | allowed | `running` or `backing-off`, `active` true, `heartbeat_active` false | Nothing is written until the next pass, which goes through the same beat-then-read in `_go` |
  | Budget sleep | no | absent | allowed | `backing-off`, `active` true, `heartbeat_active` false | The wake-up is a new pass: early gate, then beat-then-read in `_go` |
  | Migration wait | no | absent | it is the migration that is running | `blocked`, `active` true, `heartbeat_active` false | The wait ends when `:migrating` clears; the next pass checks again |
  | After a lost lease, while in-flight rows drain | yes, the rows already in flight | beaten until the pass ends, then left to lapse (at most 300 s) | refused | the lease and the state describe the successor | The displaced process may still write, so the guard stays up; it is bounded by the drain and errs on the side of refusing |
  | Dry run | no | never touched | allowed | no lease, no state | A dry run builds its ticker without the heartbeat |

  A migration that starts during the fetch or the census is therefore allowed on purpose: beating `:active` there would refuse migrations for reads that cannot collide with them, and beating it through the budget sleep would refuse every migration for the length of a multi-day run. What the fetch and the census needed was the lease renewal (DW-21), which they now have.
- **Pass start.** `_run` publishes the state before the candidate fetch: `paused` when a pause is pending, else `running`. The renew, the pause read and the publish are each guarded; a publish that fails is retried by the ticker.
- **The order with `migrate-primary.sh` is unchanged.** The pass beats `:active` on its own thread (`set_writing(True)`) before it reads `<prefix>:migrating`. A pause that ends beats on the launch loop's thread (`release_heartbeat()`) before the next launch, and the loop reads the migration key again after `sem.acquire()`.
- **The ticker decides lease loss.** A refused renew is a loss at once. A Redis error is logged, retried on every tick and changes nothing until `lease_ttl_seconds` have passed without one successful renew; from then on the lease has expired in Redis, so it is a loss. `lease_lost` is a property: the latched flag, or `clock() - last_successful_renew >= ttl`, where the time is stamped before the renew call that succeeded. The reader computes it, so it is true even when the ticker thread is stuck in a socket call.
- **A loss is terminal.** After it the ticker does not renew the lease and publishes no state: those keys describe the successor. `:active` is the exception. Rows already in flight drain after a loss and still write, so the timer keeps beating `:active` until the pass ends. No beating starts on a lost lease (`set_writing(True)` and `release_heartbeat()` do nothing then), and `set_writing(False)` does not clear the key. `run_backfill` reads the flag at the launch-loop head, after `sem.acquire()` and before every write of shared state, launches nothing more and lets in-flight rows drain. The CLI exits 7 as before. `_run_continuous` reads the flag after the census and `main` after a single pass, so a queue a successor drained is not reported as this run's completion. `main` reads it once more in the exit `finally`; that read changes no exit code, it only withholds the final state publish and the `clear_stop`.
- **The lease-lost exit needs no Redis.** After an outage as long as the lease TTL, Redis may still be down. The launch loop reads the lease flag before the migration key, the wait loops read it before the stop key, a census that raises after the loss does not replace the lease-lost outcome (the banner is printed without the queue summary, with the totals the run counted itself), and a single pass does not read the stop key once the lease is lost. A pass that dies on a Redis error before its first launch (the early migration gate, the ledger read in `partition_candidates`, the gate read in `_go`) while the ticker already reports the loss is also "lease lost" (`_lease_lost_pass`); only Redis errors are taken over, any other exception keeps its traceback. A displaced run therefore never reports or clears a stop aimed at its successor.
- **What still ends the run with an exception.** A Redis error at a synchronous site while the lease is not known lost (the renew at the launch-loop head and in the pause poll, the control reads, the renew in the two wait loops) propagates as before. The TTL rule covers the stretches where the loop is parked: a slow row, `sem.acquire()`, the candidate fetch, the census.
- **The synchronous renew sites stay.** The launch-loop head, the pause poll, the finished row and the two wait loops still renew, because those calls are the loop's stop decision. They go through `liveness.renew_now()`, so there is one bookkeeping.
- **`run_backfill` without a ticker is unchanged.** The existing tests are the lock. With `liveness=`, the asyncio renewer task is not created and the closing `idle` is not published (the run goes on after the pass; `main` publishes the final state). `backing-off` is still published.
- **Supervisor.** `_serve` wraps the run it drives in a second ticker that only keeps `<prefix>:supervisor:active` alive (`keepalives=`). The supervisor beats that key with its own `host:pid` (`Heartbeat(value=...)`); the run it drives lives in the same process, so that run's lease owner is the same `host:pid`. `--status` reads the key once and prints one of four lines:

  | Supervisor key | Lease | Line |
  |---|---|---|
  | absent | any | `supervisor : not running (--serve)` |
  | present | free | `supervisor : running — waiting for start requests` |
  | present | held by the supervisor's own process, or by an owner that cannot be compared | `supervisor : running — busy, a run holds the lease` |
  | present, carries a `host:pid` | held by another `host:pid` | `supervisor : running — idle; a run in another process (<owner>) holds the lease, so a start request waits` |

  "Cannot be compared" is a supervisor started before this change (its key holds `1`) or a lease whose meta hash is missing (owner `unknown`). The fourth line says "another process" and not who started the run, so it stays true when two supervisors share the prefix and the idle one beat the key last. Every other reader of the key (`runner_present` in the admin API) only asks whether it exists.

Not changed: the lease key layout, the owner-token CAS, `src/api/schemas.py`, `scripts/agent/migrate-primary.sh`, exit codes, the signal handlers, the pause TTL, `src/adapters/ai/client.py`.

`LivenessTicker` surface:

| Member | What it does |
|---|---|
| `LivenessTicker(*, lease=None, control=None, heartbeat=None, keepalives=(), clock=time.monotonic)` | every argument is optional; a ticker with none is valid |
| `lease`, `interval` | the lease it renews; seconds between wake-ups |
| `tick()` | runs the chores that are due; never raises |
| `start()` / `stop(timeout=5.0)` | daemon thread; also a context manager; `stop` writes nothing and never raises |
| `lease_lost` | property, no Redis call |
| `renew_now()` | CAS on the caller's thread; raises on a Redis error; `False` once lost |
| `set_state(state)` | remembers and publishes now unless the lease is lost; raises on a Redis error |
| `set_writing(True)` | beats `:active` now on the caller's thread (raises), then on the timer; starts nothing once the lease is lost |
| `set_writing(False)` | stops beating and clears the key; does not clear once the lease is lost; never raises |
| `hold_heartbeat()` / `release_heartbeat()` | pause with nothing in flight; hold does no Redis I/O; release beats now when writing is on, and does nothing once the lease is lost |
| `note_lease_lost(reason)` | latches a loss found elsewhere (a refused checkpoint write) |

`note_lease_lost` is not in the spec's sketch. `run_backfill` has a second detector of a lost lease, the refused checkpoint write, and the ticker has to stop renewing and publishing when that one fires.

## Notes / Follow-ups

- **Deploy.** The runner and the supervisor are host processes, so the change takes effect when they are restarted. Restart the `--serve` supervisor when no run holds the lease. No migration, no image rebuild, no config change. A supervisor still running the old code beats its key with `1`; `--status` then prints the plain busy line for any held lease.
- **A wedged run now reads as alive.** The ticker thread proves that the process exists, not that the run is progressing. If the main thread hangs for good (a call with no timeout, the DW-22 signal-handler deadlock), the thread keeps renewing the lease, re-publishing the state and, under `--serve`, beating the supervisor key, until someone kills the process. Before this story the lease lapsed after 900 s and a successor could start. A progress watchdog is runner-lifecycle work (Story 1.13) and is recorded as deferred in the spec. `docs/features/v0.13-s3.1-backfill-runner-hosting.md` said a wedged unit reads as absent; that still holds for a supervisor wedged while idle, not for one wedged while it drives a run.
- **Redis fails for longer than the `:active` TTL but less than the lease TTL.** The beat is retried at every wake-up (30 s) and the key can lapse while rows in flight still write to Postgres. `migrate-primary.sh` needs the same Redis to take its own key, so the exposure is the 30 s after Redis comes back. Unchanged in kind from before the story (the beat then came only from a finished row).
- **A streak of failures is two log lines.** `backfill_liveness_tick_failed` at the first failure of a chore and `backfill_liveness_tick_recovered` when it works again; the lease-lost line says when an outage became terminal.
- **Not covered: no socket timeout on the shared Redis client (DW-10 stays open for this).** `get_redis()` builds its client without one, so a Redis that accepts the connection and never answers blocks the calling thread. The ticker thread blocked this way no longer hides the loss (`lease_lost` is computed by the reader) and does not block the run's transitions: `set_state`, `set_writing` and `release_heartbeat` wait at most `_LIVENESS_LOCK_WAIT_SECONDS` (2 s) for the lock a tick holds while it writes, then go on without it, and a tick skips the state and `:active` chores when a caller holds the lock. But the launch loop's own Redis calls (`control.should_stop()`, the budget reservation) block the same way, and a blocked loop does not reach its next check. Adding a timeout changes every user of the client (API, workers, scripts), so it is outside this story. A client of the runner's own would not be enough either: inside a row the AI pacer and the enrichment pipeline call `get_redis()` themselves, on the event-loop thread, so the loop can still block there; and a timeout turns a hang into a raised error at sites whose behaviour on a Redis error (a row counted as failed, an attempt charged in the ledger, the AI breaker) has to be decided, not inherited. This is the second half of DW-10, which stays `open` in the ledger with that scope.
- **A row already in flight is not interrupted.** When the lease is lost, in-flight rows drain (cancelling mid-enrichment leaves half-written properties). The timer keeps beating `:active` while they drain, as every finished row did before this story, so `migrate-primary.sh` still sees a writer. The key is not cleared when that pass ends (a successor may be beating it); it lapses on its 300 s TTL.
- **The time between a takeover and the next renew.** A successor can only take the lease after it has expired, which needs a whole TTL without a renew, and the ticker reads that as a loss on its own. If the key is replaced by hand while the run is healthy, the run finds out at its next renew (at most 300 s later, or at the next launch, pause poll or finished row) and keeps re-publishing its state every 30 s until then.
- **A stuck tick at exit.** `stop()` waits up to 5 s for a tick in progress. A tick stuck in a socket longer than that can still complete the Redis call it is in after `main` has published the final state; `stop()` logs `backfill_liveness_tick_failed` with `chore=stop` when that happens, and every chore checks the stop flag again before its next Redis call. A renew that comes back refused after `stop()` (the owner has released the lease by then) is not reported as a lost lease. The thread is a daemon and does not keep the process alive.
- **For Story 1.13.** The exit path joins the ticker thread for up to 5 s (`liveness.stop()` in `main`'s `finally`); that is on the main thread after the run, not in a signal handler. The handlers are unchanged and still call `control.request_stop()` (DW-22). The ticker's locks (`_io_lock`, `_latch_lock`) are not re-entrant: a signal handler that touches the ticker (`set_state`, `lease_lost`) while the main thread holds one of them would deadlock, so a handler should only set a flag the loop or `tick()` reads.
- **Redundant renews.** The wait loops and the launch loop renew on their own cadence and the ticker renews on its timer. The cost is one extra CAS per 300 s.
- Story 1.13 (runner lifecycle) and Story 1.14 (transport-quota inference) touch the same files and were kept out: no new exit code or end state, no change to the signal handlers or the pause TTL, nothing in `src/adapters/ai/client.py`. The ticker's `tick()` is where 1.13 can read a stop flag set by a signal handler without Redis I/O.
- Ledger (`_bmad-output/implementation-artifacts/deferred-work.md`): DW-9, DW-20, DW-21 and DW-34 are closed by this story. DW-10 is half done: the TTL rule is in, the socket timeout is not, so the entry stays `open` with its scope narrowed to the timeout.
