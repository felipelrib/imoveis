# Cohort price-per-m² percentiles — the scoring stage stores how cheap a Property is inside its city × neighbourhood × listing-type cohort

> Feature branch: `feat/v0.14-s1.6-cohort-price-per-m2-percentiles` · Story: `v0.14-s1.6` · Status: done (primary migrated, rebuilt and recalculated on 2026-10-08)

## Problem

"Among the N% cheapest of its neighbourhood" (FR-30) could not be read from the database. The only stored percentile was the legacy `percentile_rank*`:

- a SQL `PERCENT_RANK`, where the cheapest member reads 0 and the value depends on n − 1;
- no minimum cohort size: a cohort of one is ranked, at 0;
- Properties without a neighbourhood are ranked together in an `Unknown` cohort;
- the cohort key is the neighbourhood label alone, so a label shared by two cities is one cohort (97 labels and 16,477 active Properties on the primary);
- the single-property path writes a fabricated `0.5`.

## Approach

- **New columns, legacy untouched.** `percentile_rank*` is on the wire, in the export and in the modal with its own definition. Redefining it in place would change the API silently. The new value lands in new nullable columns; Story 1.7 puts it on the wire and can retire the legacy fields there.
- **Characterization lock first.** `test_percentile_characterization_lock.py` landed in its own commit before any production change and is not edited afterwards. It pins the legacy output of the bulk stage, of the single-property path and of the AD-12 list projection. The Story 1.3 lock (`test_scoring_characterization_lock.py`) also passes unedited.
- **One definition, in `src/core/cohort_percentile.py`.** Pure (standard library only, AD-1) and built test-first. SQL only counts; the division, the tie rule and the minimum-size rule exist once, in Python, and both writers call them.
- **Inclusive share, not `PERCENT_RANK`.** With the inclusive share the badge sentence is literally true of every member: the cheapest of 20 reads 5%.
- **City in the key.** The primary has no spatial assignment and labels such as `Centro` exist in all three cities.
- **Labels are compared folded.** Platforms spell one neighbourhood several ways (`São Bento`, `Sao Bento`, `SAO  BENTO`). City and neighbourhood are compared in lower case, without Portuguese accents, with runs of whitespace collapsed and trimmed. On the primary this joins 537 spellings into 268 neighbourhoods holding 22,845 active Properties that would otherwise sit in split cohorts.
- **Null, never defaulted.** No `0.5`, no `0` for "unknown".
- **The bulk stage stays set-based.** The counts are two window functions in one extra CTE of the one existing statement. No statement per row.
- **The cohort median is computed once per cohort.** The stage's statement used to compute `neighborhood_median` with a subquery that ran once per row; that is where its 62 minutes on the primary went. It is now one `GROUP BY` joined back (own commit, `perf(v0.14-s1.6)`), with the same values. Done in this story because the story needs the full recalculation run again.

### Definition

| Term | Rule |
|---|---|
| Percentile | (cohort members with price/m² ≤ this Property's) ÷ cohort size. In (0, 1]; lower is cheaper; `0.25` reads "among the 25% cheapest". |
| Ties | Tied members share one value, the inclusive count. 30 / 40 / 40 / 50 reads 0.25 / 0.75 / 0.75 / 1.0. |
| Cohort member | An active Property with `area_m2 > 0`, an assigned neighbourhood and a row in `core.price_basis.COHORT_PRICE_SQL` for that listing type. |
| Price/m² | That relation's price ÷ area: `rent_monthly` when the Listing has one, the headline `price` otherwise (Story 1.3); sale is the published price. `pl.price`, `total_monthly_cost` and `properties.price` are never read here. |
| Cohort key | Listing type × city × neighbourhood. |
| Neighbourhood | The spatial FK's name when the Property has one, else the `props_json` label; folded (see below). No FK and a blank or missing label: unassigned, in no cohort. |
| City | The FK's city when the Property has one, else `props_json.city`; folded. A missing city is the empty string, which is a key like any other (no active Property on the primary lacks a city). |
| Folded | Unicode NFC, lower case, the accented letters `áàâãäåéèêëíìîïóòôõöúùûüçñ` replaced by their plain letter, any run of whitespace replaced by one space, trimmed. Done in SQL by `COHORT_NEIGHBOURHOOD_SQL` / `COHORT_CITY_SQL`; no extension is needed. |
| Dual Property | One percentile per listing type. |
| Listing-less Property (legacy `properties.price`) | Not a member: no percentile, no size, and not counted in any cohort. Its stat columns are scored as before. |

What a row holds after it was evaluated:

| Situation | Percentile | Cohort size | `percentile_evaluated_at` |
|---|---|---|---|
| Member, cohort at or above the minimum | value | size | set |
| Member, cohort below the minimum | NULL | size | set |
| Not a member (no area, no neighbourhood, no Listing price, inactive) | NULL | NULL | set |
| Row never evaluated (inserted by the enrichment task before scoring) | NULL | NULL | NULL |

### Threshold chosen

`scoring.percentile_min_cohort_size` in `configs/app_config.yaml`, default **10**, minimum 2 (config validation rejects a lower value; a cohort of one never has a percentile). A host overrides it with `IMOVEIS_SCORING__PERCENTILE_MIN_COHORT_SIZE`; no code change.

At 10 one member moves the value by at most 10 points and the 25% badge needs the two cheapest members. Members suppressed on the primary with the cohort key of this story (read-only, 2026-10-08):

| Minimum | Rent members suppressed (of 113,611) | Sale members suppressed (of 126,664) |
|---|---|---|
| 5 | 1,825 (1.6%) | 1,661 (1.3%) |
| **10** | **4,518 (4.0%)** | **3,721 (2.9%)** |
| 20 | 8,994 (7.9%) | 7,172 (5.7%) |
| 30 | 13,148 (11.6%) | 9,634 (7.6%) |

A stored percentile keeps the minimum that was in force when it was written. After changing the value, run the recalculation (operator step 3); until then a reader that must honour the new value can also require `percentile_cohort_size_<type>` at or above it.

**Ties** are not a setting: tied members share the inclusive count because that is what makes the badge sentence true. Changing it is a code change in `core/cohort_percentile.py`.

### Measurements on the primary (read-only, 2026-10-08, `alembic_version` `d5e6f7a8b9c0`)

- 200,081 active Properties; 0 with `neighborhood_id`, 0 `neighborhoods` rows, 3 without a label, 315 without an area, 0 active priced Properties without a Listing.
- 3 cities, none missing; 2,944 labels; 2,859 city × label keys after trim and lower-case, 2,590 after folding accents and whitespace too; 97 labels in more than one city (16,477 Properties).
- Legacy `percentile_rank_rent` = 0.5 on 1,007 rows, `percentile_rank_sale` on 817.
- The percentile counts for all members of both listing types (about 240,000), run alone with the folded key: 6.5 s (3.3 s before folding).
- The bulk stage took 62 minutes on 2026-10-08 (Story 1.3: 3,741 s, one transaction). Its statement computed the cohort median with a subquery that ran once per row over the whole `typed` CTE (`SubPlan` in the plan, about 240,000 × 240,000 row visits); the same statement without the median ran in 7.1 s.
- The statement as it is now (median once per cohort, percentile counts included), all 199,836 result rows: **7.8 s**. The old per-row subquery, evaluated once for each of the 5,080 stat cohorts, took 147 s for those 5,080 rows (about 29 ms a row, against 240,281 rows in the stage) and returned the same median as the joined form for every cohort, compared byte for byte (`float8send`); the join keeps all 240,281 rows.
- Single-property path, with the folded key: own key and price 4 ms, cohort counts 0.9 to 1.1 s (two sequential scans: 288,000 Listings and 200,000 Properties, the fold evaluated per Property; 386 ms before folding). Two extra statements per scored Property. For comparison the cached cohort statistics query it already runs takes 262 ms per listing type.
- What the fold does not cover: Postgres `\s` does not match a no-break space here, and 6 active Properties carry a no-break or other non-ASCII space in their label; 10 more are written with a typographic apostrophe (`D’abril`). Those labels are compared as written.
- The database `TimeZone` is `UTC`, so `percentile_evaluated_at` (naive UTC from the application) and the `now()` columns are on one clock.

These were measured read-only, with the SQL the stage runs. What is not measured is the whole request of operator step 3: after the statement, the stage loads and updates about 200,000 rows through the ORM and `recalculate_all_combined_scores` rewrites them once more. Expect minutes, not the hour it took.

No existing `metrics_scoring` column changes value or meaning (the median is computed another way and is the same number), and the stat cohort key (`_COHORT_KEY_SQL`) is the same.

How the two writers work:

- **Bulk (`compute_neighborhood_stats`).** A `pct_members` CTE over `listing_min` joined to `properties` and `neighborhoods` yields, per member, `COUNT(*) OVER (PARTITION BY type, city, neighbourhood)` and the same count `ORDER BY price/m²` (the default window frame includes peers, so ties share the inclusive count). It is not restricted by the optional label key: a keyed run still ranks against whole cohorts. A full run (no key) ends with one `UPDATE` that nulls the percentile and size of rows whose Property is no longer a member and stamps them.
- **Single path (`score_single_property`).** Statement 1 reads the Property's own cohort key and price/m² per type from the same expressions; statement 2 counts the other members of that cohort with those values bound, and the Property itself is added in Python, so the pair of counts is consistent even when its Listing changes between the two statements. When the Property has no usable price or area, an existing row is cleared and stamped; no row is created.


   ```sql
   WITH bulk AS (
       SELECT mode() WITHIN GROUP (ORDER BY percentile_evaluated_at) AS stamp FROM metrics_scoring
   ),
   member AS (
       SELECT t.listing_type, t.ppm, t.stored, t.stored_size,
              COALESCE(BTRIM(REGEXP_REPLACE(TRANSLATE(LOWER(NORMALIZE(p.props_json->>'city', NFC)),
                  'áàâãäåéèêëíìîïóòôõöúùûüçñÁÀÂÃÄÅÉÈÊËÍÌÎÏÓÒÔÕÖÚÙÛÜÇÑ',
                  'aaaaaaeeeeiiiiooooouuuucnaaaaaaeeeeiiiiooooouuuucn'), '\s+', ' ', 'g')), '') AS city,
              NULLIF(BTRIM(REGEXP_REPLACE(TRANSLATE(LOWER(NORMALIZE(p.props_json->>'neighborhood', NFC)),
                  'áàâãäåéèêëíìîïóòôõöúùûüçñÁÀÂÃÄÅÉÈÊËÍÌÎÏÓÒÔÕÖÚÙÛÜÇÑ',
                  'aaaaaaeeeeiiiiooooouuuucnaaaaaaeeeeiiiiooooouuuucn'), '\s+', ' ', 'g')), '') AS nb,
              ms.percentile_evaluated_at = bulk.stamp AS from_bulk
       FROM metrics_scoring ms
       JOIN properties p ON p.id = ms.property_id
       CROSS JOIN bulk
       CROSS JOIN LATERAL (VALUES
           ('rent', ms.price_per_m2_rent, ms.price_per_m2_percentile_rent, ms.percentile_cohort_size_rent),
           ('sale', ms.price_per_m2_sale, ms.price_per_m2_percentile_sale, ms.percentile_cohort_size_sale)
       ) AS t(listing_type, ppm, stored, stored_size)
       WHERE t.stored_size IS NOT NULL
   ),
   ranked AS (
       SELECT m.*,
              count(*) OVER w AS size,
              count(*) OVER (w ORDER BY ppm) AS at_or_below,
              bool_and(from_bulk) OVER w AS untouched
       FROM member m
       WINDOW w AS (PARTITION BY listing_type, city, nb)
   )
   SELECT listing_type,
          count(*) FILTER (WHERE untouched) AS checked,
          count(*) FILTER (WHERE NOT untouched) AS in_cohorts_rescored_since,
          count(*) FILTER (WHERE untouched AND (
                  size <> stored_size
               OR (size >= 10 AND (stored IS NULL OR abs(stored - at_or_below::float / size) > 1e-9))
               OR (size < 10 AND stored IS NOT NULL))) AS wrong
   FROM ranked
   GROUP BY listing_type
   ORDER BY listing_type;
   ```

A cohort in which any row carries another stamp was touched by the single-property path after the run; its rows are counted in `in_cohorts_rescored_since` and left out of the comparison, because their peers are expected to lag (see Notes). The query reads the label and city from `props_json`, which is the whole key on the primary today (no Property has a `neighborhood_id`). Replace `10` if the host overrides the minimum.

   This query was run read-only on the primary on 2026-10-08 against a stand-in for `metrics_scoring` holding the values the stage's own SQL produces from the live rows: `checked` 113,611 / 126,664, `wrong` 0 / 0, in 13 s. With one member of a cohort of ten or more given a NULL percentile it reports `wrong` 1; with wrong cohort sizes it reports them all.

   A small non-zero `wrong` some time after step 3 is not necessarily a defect. Two things the query cannot see leave old peers with a size one too large: the single-property path clearing a Property that stopped being a member, and a scrape changing a Property's label or city (the query reads the label as it is now). Both show as every row of one or two cohorts; a defect in the stage shows across cohorts. Run the query right after step 3 to keep that window short.

## Notes / Follow-ups

- **Peers go stale between full runs.** The single-property path writes the scored Property's own percentile and size. It does not rewrite the other members of that cohort, whose size and share moved by one. Those are corrected by the next `POST /admin/scoring/recalculate`, and no beat task runs it. Story 1.7 shows these values; if the drift matters there, schedule the bulk stage.
- **Every full run now updates every scored row.** `percentile_evaluated_at` is stamped on each evaluated row, so the bulk stage issues an `UPDATE` for rows whose scores did not change, and `metrics_scoring.updated_at` moves for all of them. Nothing in `src/` reads that `updated_at` today. The same request already rewrites every row once (`recalculate_all_combined_scores`), so a full run now leaves up to two dead row versions per row for autovacuum instead of one. The row writes happen at the end of the transaction, after the long `SELECT`. The effect on the run time is not measured (operator step 3).
- **A full run writes the snapshot it read.** The stamp is the time the run started. A row that the single-property path scored while the run was in progress is overwritten by the run's older counts and gets the run's earlier stamp. The stat columns behaved this way before this story.
- **A full run stamps the rows it scores, not every row.** A `metrics_scoring` row whose Property the stage does not score (inactive, no area, no price) and that holds no percentile keeps `percentile_evaluated_at` NULL after a full run. The single-property path stamps such a row when it is asked to score it. Story 1.9 should hold a match on `percentile_evaluated_at IS NULL` only for Properties that can be scored.
- **DW-39 is recorded, not changed.** The disagreement between the cached cohort statistics and the bulk stage on Listing-less Properties (DW-39) is as before this story. The stage's run time did change: see the median in Approach and Measurements.
- **The single-property path costs about one second of database time per scored Property.** Its cohort count scans the active Listings and Properties and folds every label (0.9 to 1.1 s on the primary). The folded key cannot use an index as written; an expression index on the folded label and city would need a migration and is not part of this story. Recorded as a deferred finding.
- **The stat cohort key still merges cities and splits spellings.** `neighborhood_mean*`, `z_score*`, `stat_score*` and the legacy `percentile_rank*` keep the exact label as key. Moving them to the key of this story changes stat scores and is out of scope; recorded as a deferred finding.
- **The legacy `percentile_rank*` is still served.** The API, the export and the modal read the old columns, fabricated `0.5` included, until Story 1.7.
- **Folding covers Portuguese accents, not every script or every space.** A letter outside the listed set (for example `ý` or `ø`) is compared as written, and so are a no-break space and a typographic apostrophe (16 active Properties on the primary, see Measurements). Two different neighbourhoods of one city whose names differ only by an accent would be merged; none is known.
- **The key has no state.** Two cities with the same name in different states would share cohorts for same-named neighbourhoods. The primary holds São Paulo, Belo Horizonte and Campinas.
- **A missing city is a cohort key.** Members of one label without a city are ranked together. No active Property on the primary lacks a city (2026-10-08).
- **A schema downgrade loses the percentiles.** They return with the next recalculation after a re-upgrade.
- Related: Story 1.3 (cohort price basis), Story 1.7 (badge and filter), Story 1.8 (panel sentence), Story 1.9 (saved-search matches wait for `percentile_evaluated_at`).
