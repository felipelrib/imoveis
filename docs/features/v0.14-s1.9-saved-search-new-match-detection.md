# Saved-search new-match detection — a saved search emails the new homes that match it, once a day

> Feature branch: `feat/v0.14-s1.9-saved-search-new-match-detection` · Story: `v0.14-s1.9` · Status: implemented; the primary is not migrated or rebuilt yet (see Operator steps)

## Problem

A saved search was a filter preset and nothing else. Nothing told the user that a new home matching it had appeared (FR-32). The notifier stack knew two messages only: price drops and the weekly top-deals digest.

## Approach

- **Two beat tasks on the `scrapers` queue.**
  - `tasks.match_saved_search_new_matches` (every 15 minutes) records, per notifying search, each new Property that matches it and is decidable.
  - `tasks.send_saved_search_new_match_alerts` (hourly) emails the recorded matches of each search, one message per search per local day.
- **Pull, not push.** The matcher reads stored facts. Nothing hooks `core/dedupe.py` or `scrape_listings`, and no queue message carries a "new Property" event.
  - A Property that is not decidable yet is simply not selectable. The next run looks again, for as long as it takes. Nothing is written for it, so nothing can be lost between persist and enrichment.
  - The matcher never enqueues enrichment.
- **One `WHERE` for the grid and the alert.** The list predicates moved from `api/properties.py` to `core/property_list_filters.py`. `GET /properties`, the export and the matcher call the same builder. A characterization lock landed first, in its own commit, and the move passed it unedited. (One line of the lock changed later, with the `accepts_pets` fix: see the fixed BUG (High) under Notes.)
- **Match at decision time.** Filters such as `min_score` and the percentile cap read enrichment output. A match is evaluated when the Property is decidable, with the SQL the click-through from the email would run.
- **The window is a stored date.** The sender runs every hour. A search is due when the local hour has reached `window_hour` and the search was not stamped for that local date. A worker that was down at the window hour sends at its next run. A second run the same day does nothing.
- **Email only.** The message goes to the notifier registry's `email` channel and to no other. The registry now remembers the channel type of each notifier; the task never builds an `EmailNotifier` itself.
- **Off by default.** `notify_new_matches` is false on every existing and new saved search. No email leaves until a search is switched on.

### Definitions

| Term | Rule |
|---|---|
| New | `properties.first_seen` is at or after the search's `notify_enabled_at`. There is no maximum age. `first_seen` is written once, when the Property row is created. |
| Not new | A Listing appearing, reappearing or reactivating on an existing Property. A platform outage and its recovery therefore produce no match. |
| Matches | The Property passes the list endpoint's `WHERE` for the parameters the saved search stands for: what the SPA sends when a search it stored is applied. For a blob the SPA cannot write (see `price_type` below) it is what `GET /properties` does with the stored values. |
| Decidable | `metrics_scoring.percentile_evaluated_at` is set and `meta.deal_verdict.verdict` is a non-blank string. The stamp means "evaluated", not "has a value": a suppressed cohort is decidable. A degraded (template) verdict counts, because the panel shows it. |
| Held | New, active, not decidable. Counted on every matcher run; examined again on the next one. A hold has no time limit: the Property is alerted when it becomes decidable, however late. |
| Overdue | Held and first seen more than `alerts.new_match.hold_warning_hours` (168) ago. Counted and logged as a warning. Still held, still alerted once decidable. |
| Local day | The calendar date in `alerts.new_match.window_timezone` (`America/Sao_Paulo`). |

### How a saved search becomes list parameters

`core.saved_search_alerts.match_filters_from_saved_search` mirrors `usePropertiesFiltersState.buildListQueryFilters` and `api.buildPropertyFilterParams`.

| Stored key | List parameter | Rule |
|---|---|---|
| `max_price` | `max_price` | |
| `price_type` | `price_type` | Only together with `max_price`. The SPA always stores one. A blob written through the API without it gets the list endpoint's own default: the listing type, else rent. (The SPA would reopen such a blob with its own state default, rent; the matcher follows the endpoint, so a sale search with a cap caps sale prices.) |
| `neighborhood` | `neighborhood_name` | |
| `city` | `city_name` | |
| `listing_type` | `listing_type` | `both` or missing means no type. |
| `is_furnished`, `accepts_pets` | same | Only when true. |
| `max_price_per_m2_percentile` | same | Only when 0 < x ≤ 1. |
| `min_bedrooms`, `min_parking`, `min_score`, `platform`, `property_type` | same | As stored. |
| `sort_by`, `sort_dir`, `min_price`, `max_bedrooms` | none | The list endpoint ignores them too. |
| `q` (non-blank) | none | The search is not matchable. See below. |
| any other key, or a blob that is not an object | none | The search is not matchable. See below. |

A search with a semantic query (`q`) returns a ranking, not a membership, so "a new home matches it" has no definition. Enabling such a search is accepted; the API reports `new_match_alerts_supported: false` and the matcher skips it.

The same holds for a stored blob that carries a key outside the saved-search wire (a camelCase blob from before the API normalised writes, say) or that is not an object. Reading an unknown key as "no such filter" would alert on far more than the grid lists, so such a search never fires, and `new_match_alerts_supported` is `false` for it (computed from the stored value itself). `SAVED_SEARCH_WIRE_KEYS` is pinned by unit tests against the API model that writes the blob and against the key table of `frontend/src/savedSearchFilters.ts`.

What can carry an unknown key today: nothing the application writes. Every `POST` / `PATCH` goes through `SavedSearchFilters.to_wire`, which accepts the camelCase aliases, drops keys it does not know and stores the snake_case wire only; the SPA's `toSavedSearchWire` writes a subset of that wire (the percentile key of Story 1.7 included). Only a row written before the API normalised writes, or by hand, can be muted by this rule. The primary has no saved search at all (measured 2026-10-08).

The Total Monthly Cost cap (`max_total_monthly_cost`) is not part of the saved-search wire: neither the SPA nor the API stores it, so a reopened saved search does not carry it either. The alert agrees with the reopened search, not with the grid the user was looking at when saving. That gap predates this story.

### What the two tasks return

| Task | Result keys |
|---|---|
| Matcher | `status` (`ok` / `skipped`), `searches`, `matched`, `unsupported`, `errors`, `held`, `oldest_held_hours`, `held_overdue` |
| Sender | `status` (`ok` / `skipped` / `no_email_channel`), `searches_due`, `emails_sent`, `properties_alerted`, `withdrawn`, `errors` |

- `held` counts new active Properties that are not decidable, from the earliest newness floor among the notifying searches. It is not restricted to Properties that would match a search: whether one matches is only known once it is decidable.
- `held_overdue` counts the held Properties first seen more than `hold_warning_hours` ago. A value above zero logs the warning `saved_search_new_match_held_overdue`: new Properties are not getting a verdict. They stay held.
- A search that fails is rolled back, logged and counted in `errors`; the other searches still run.

### Row states

`saved_search_new_matches` holds one row per search × Property.

| Status | Meaning | Set by |
|---|---|---|
| `pending` | Matched, waiting for the search's daily window (or for room in an email: at most `max_items_per_email` leave per day). | Matcher |
| `sent` | Emailed. `sent_at` is set. | Sender, after at least one email notifier accepted the message |
| `withdrawn` | Must not be emailed: the Property is inactive, the search no longer notifies, or the row was matched under an earlier enabling of the search. | Sender |

- The unique constraint on (`saved_search_id`, `property_id`) makes "at most once per search × Property" true for two workers too (`ON CONFLICT DO NOTHING`).
- A failed send leaves the rows `pending` and the window date unstamped. The next hourly run tries again.
- One sender at a time per search, in three steps (changed in review pass 3: the first version kept the row lock for the whole send).
  1. Claim. The sender takes the search's row lock (`FOR NO KEY UPDATE SKIP LOCKED`), reads the search's state again (on / off, enable moment, window date), reads the pending rows, stamps today's window date and commits. The lock lasts for these statements only.
  2. Send. The email leaves with no lock and no transaction open. A `PATCH` or `DELETE` of the search does not wait for the mail server.
  3. Mark. The rows the email carried become `sent`. If the send failed instead, the window date is put back to what it was, so the next hourly run tries again.
- A second run that starts meanwhile either skips the locked row (step 1 in progress) or finds the day already claimed. The lock does not block the matcher's inserts.
- With no email channel (`alerts.enabled: false` or no `email` in `alerts.channels`) nothing is sent, the rows stay `pending` and the result says `no_email_channel`.
- Deleting a search keeps its rows with `saved_search_id` NULL, so the weekly digest still knows the Property was alerted.

### The email

Plain text, `pt-BR` or `en` from `ui.locale`. Subject: `2 imóveis novos na busca “Savassi 2q”` (the name on one line, whatever it holds). The SMTP conversation has a 30 second timeout.

| Line | Shown when |
|---|---|
| Search name and count | always |
| Title, or the stored type when there is no title | always |
| Neighbourhood, city | stored |
| Headline price (`/mês` for rent), area, bedrooms | stored |
| Verdict text | always (a match is decidable) |
| `entre os N% mais baratos do bairro` | the percentile of the relevant listing type is not NULL. N follows the card badge rule (rounded up, at least 1). |
| `<app_base_url>/properties/<public_id>` (the SPA route of the detail panel) | `alerts.new_match.app_base_url` is set |
| `+N nesta busca chegam no próximo aviso.` | more than `max_items_per_email` matches are pending. The email carries the oldest ones (by match moment, then by the Property's `first_seen`) and only those are marked sent; the rest stay `pending` and leave in the next day's email. The subject counts what the email carries. |
| `N imóveis novos ainda estão em análise …` | something is held |
| Why the email was sent and where to switch it off (Buscas salvas) | always |

The relevant listing type is the search's `listing_type` when it is `rent` or `sale`, otherwise the Property's primary Listing type. The email says nothing about a drop threshold; that is the drop email of Story 1.10.

### API

`GET /saved-searches`, `GET /saved-searches/{id}`, `POST` and `PATCH` return five more fields. Story 1.10 is a UI story on top of them.

| Field | Type | Meaning |
|---|---|---|
| `notify_new_matches` | bool | The per-search switch. Default false. |
| `min_price_drop` | number ≥ 0 or null | Minimum price drop in reais (absolute, as in `queda de R$ 240 — seu mínimo: R$ 100`). Stored and returned. No rule reads it in this story. |
| `notify_enabled_at` | string (naive UTC) or null | When the switch was last turned on. Read-only. |
| `new_match_alerts_supported` | bool | False when the filters carry a non-blank `q` or an unknown key, or are not an object. Such a search never fires. Read-only. |
| `last_new_match_alert_on` | date string or null | Local date of the last new-match email. Read-only. |

- `POST` accepts `notify_new_matches` and `min_price_drop`. `PATCH` accepts both; `"min_price_drop": null` sent explicitly clears the value, an absent key leaves it.
- Turning the switch on (false → true, or creating with true) stamps `notify_enabled_at`. Turning it off leaves the stamp. Turning it on again stamps a new one. A `PATCH` with `true` on a search that is already on does not move the stamp.
- A negative or non-finite `min_price_drop` is a `422`.

### Config (`alerts.new_match`)

| Key | Default | Rule |
|---|---|---|
| `enabled` | `true` | Master switch of both beat tasks. |
| `match_interval_minutes` | `15` | > 0 |
| `window_hour` | `7` | 0 to 23, local |
| `window_timezone` | `America/Sao_Paulo` | A timezone `zoneinfo` knows |
| `hold_warning_hours` | `168` | ≥ 1. Reporting only: a hold never expires. |
| `max_items_per_email` | `20` | ≥ 1 |
| `app_base_url` | `""` | Empty: no link in the email |

Recipient and SMTP are the existing `alerts.digest_email` and `alerts.smtp_*`. A host overrides a key with `IMOVEIS_ALERTS__NEW_MATCH__<KEY>`.

### Weekly digest

`select_top_deals(..., alerted_owner=...)` leaves out a Property that has a `sent` row for that owner, or a `pending` row under a search that still notifies. `send_top_deals_digest` passes the principal. Without the argument the selection is as before.

### How a Property becomes decidable

`run_enrichment` → `_persist_ai_scores` → `score_single_property` stamps `percentile_evaluated_at`, and `_write_deal_verdict` stores the verdict, in one transaction. No bulk recalculation is involved: a Property enriched by the normal pipeline is matched by the next matcher run. An integration test follows that path with the two production writers (`_persist_ai_scores` and `_write_deal_verdict`).

Both drivers of that authority release a held match: the live `ai_enrich` task (enqueued by `scrape_listings` for every created or updated Property that passes the photo gate) and the backfill runner. The `verdict_only` stage does not stamp the percentile; it only runs on rows that were scored before.

### Decisions taken in this story

Product-visible:

| Question | Decision | Why |
|---|---|---|
| Default of the flag | Off for every existing and every new saved search. | A flag that defaults to off never emails anyone unasked. |
| Daily window | From 07:00 `America/Sao_Paulo`, one email per search per local day. If nothing is pending at 07:00 the day stays open and the first match of the day leaves at the next hourly run. | A morning email; a late first match is not kept for a day. |
| How long a match is held | Until it is decidable, with no limit; it is then alerted, late. A hold longer than 168 hours is reported as overdue (warning log, task result). Changed in review pass 2: the first version stopped looking after 168 hours. | The acceptance criterion says "held until the verdict exists and the percentile has been evaluated, never dropped". UX-DR11 only forbids alerting early; nothing in the planning documents licenses giving up. |
| More matches than fit in one email | The 20 oldest leave; the rest stay pending for the next day's email. Changed in review pass 2: the first version marked all of them sent. | A match marked sent without being shown is a dropped alert, and the weekly digest would leave it out too. |
| "Genuinely new" | The Property row was created after the search was switched on. A Property that existed and gains a Listing of the searched type (a flat for sale that is now also for rent) is not a new match. | The story says "creates a new Property"; this is also what makes an outage harmless. |
| Platform outage | Not recognised; it cannot produce a match. Newness is never derived from a Listing appearing or reappearing. | No detector to get wrong. |
| What counts as a verdict | Any stored verdict text, including a degraded (template) one. | The panel shows it; the alert never lands on a pending analysis. |
| Semantic (`q`) searches | Never fire; the API says so. | A ranking has no "new member". |
| Recipient | `alerts.digest_email`, the address the weekly digest already uses for the single principal. | AD-11: no second subscriber identity. |
| Email text | pt-BR by default (`ui.locale`), plain text, at most 20 homes with a `+N` line for the ones that come next. No threshold wording. | UX microcopy is pt-BR; the threshold sentence belongs to the drop email of Story 1.10. |
| `min_price_drop` | Stored in reais (absolute), no default, read by nothing yet. | UX-DR13 states the threshold in reais. |

Technical:

- No hook in the persist path; the matcher reads `properties.first_seen`. An integration test runs the real `match_or_create_property` twice and pins that a re-scrape leaves `first_seen` alone.
- What the claim-send-mark order does when something breaks between the steps. Every case errs towards late, none towards lost:

  | Failure | Result |
  |---|---|
  | The send fails (mail server down, refused login) | The day is given back; rows stay `pending`; the next hourly run tries again. |
  | The worker is killed after the claim and before the send, or giving the day back fails | The day stays claimed with nothing sent. Rows stay `pending` and leave in the next day's email. |
  | The email left and marking the rows then failed | The day stays claimed; the rows stay `pending` and are emailed again the next day. This is the only path to a duplicate, and it repeats at most once a day, not every hour. |
  | The search is deleted while its email is being sent | The email leaves. Its rows are kept with no search and stay `pending` (see Notes). |
- A match is not re-checked against the filters at send time (at most a day later); the email shows the current price.

The statement re-evaluates every Property created since the search was enabled on each run, so its cost grows towards the whole-table figure above and stays there: under a second per notifying search every 15 minutes.

Review pass 3 (the same question asked again for held Properties: does a growing hold make a run expensive?). Floor at the year 2000, so every one of the 200,195 active Properties is a candidate and 172,882 of them are held (not decidable). Each statement was run twice; the first figure is with a cold cache.

| Measurement | Value |
|---|---|
| Matcher `SELECT`, typical search (rent, up to R$ 4.000, 2+ bedrooms, cheapest half) | 1,330 ms then 134 ms, 768 rows |
| Matcher `SELECT`, a search with no filter at all | 894 ms then 166 ms, 27,313 rows |
| Matcher `SELECT`, typical search plus `accepts_pets` and `min_score` | 632 ms then 352 ms, 728 rows |
| Hold report over the whole table | 214 to 233 ms; `held` 172,882, `held_overdue` 145,210 |

A held Property costs one row of a sequential scan and one cheap test (the verdict is missing), nothing more: it is not stored, not queued and not counted per search. The work per run is one statement per notifying search, linear in the Properties created since that search was switched on. Ten searches with the whole corpus as candidates are 1.5 to 13 seconds of database time every 15 minutes; 30,000 held Properties are a sixth of what was measured here. No bound per run was added. Not measured: the `INSERT` half, because the primary does not have the table yet. A Property already recorded for the search is offered again on every run and refused by the unique index (`ON CONFLICT DO NOTHING`), one index probe per recorded row.

**What this means for alerts on the primary today.** The percentile stamp is not what holds a match: the bulk run stamped the corpus, and enrichment stamps a new Property itself. The verdict is. No Property has received a verdict since 2026-08-13, so on the primary as it runs today every new match is held, `held_overdue` grows, and no email leaves. Nothing is lost: when enrichment produces verdicts again, the held Properties created since a search was switched on are matched and leave 20 per search per day, oldest first. The typical search above would have had 1,234 candidates in a week, which at 20 a day is two months of emails; whoever restarts enrichment after a long gap should expect that backlog (switching the search off and on discards it and starts a new floor). Alerts start to flow when enrichment (live `ai_enrich` or a backfill pass with the verdict stage) runs again for new Properties; the matcher needs nothing else. Why enrichment stopped is not visible from the database and was not investigated here (Redis and the worker logs are outside the read-only probe).

### Operator steps (primary stack)

The new code selects the new columns, so the primary is migrated before the rebuild. The old code ignores them, so stopping after step 1 is safe.

1. Migrate the primary database, from the primary checkout, in Git Bash:
   ```bash

   ```
   Expected: `alembic_version` becomes `f7a8b9c0d1e2`; every saved search reads `notify_new_matches = false`.
2. Rebuild and restart the API, the workers and beat so they run the new tasks and schedule:
   ```bash
   ./scripts/restart.sh --build
   ```
   Steps 1, 2 and 5 can be run by an agent operator. Steps 3 and 4 need a person: step 3 is a credential, step 4 decides that real email may leave.
3. Check the mail settings before turning any search on. The committed `alerts` section points at `localhost:1025` and `admin@example.com`. A host sets the real values in `.env.local` (`IMOVEIS_ALERTS__DIGEST_EMAIL`, `IMOVEIS_ALERTS__SMTP_HOST`, `IMOVEIS_ALERTS__SMTP_PORT`, `IMOVEIS_ALERTS__SMTP_USER`, `IMOVEIS_ALERTS__SMTP_PASS`) and, for the link in the email, `IMOVEIS_ALERTS__NEW_MATCH__APP_BASE_URL`. With no reachable mail server the sender logs the failure every hour and keeps the matches pending. The email notifier speaks plain SMTP and logs in without STARTTLS or SSL (all three of its methods; see Notes), so the server must accept that: a local relay does, a public provider on port 587 or 465 does not.
4. Turn a search on. Until Story 1.10 ships the toggle, through the API:
   ```bash
   curl -X PATCH http://localhost:8000/saved-searches/<id> -H "X-API-Key: $API_KEY" \
        -H "Content-Type: application/json" -d '{"notify_new_matches": true}'
   ```
5. Read-only checks (record the results under "Operator results" below):
   ```sql
   SELECT version_num FROM alembic_version;                                   -- f7a8b9c0d1e2
   SELECT count(*) FILTER (WHERE notify_new_matches) AS on_, count(*) AS total FROM saved_searches;  -- on_ = 0 right after the migration
   SELECT status, count(*) FROM saved_search_new_matches GROUP BY status;     -- no rows until a search is on
   SELECT name, notify_new_matches, notify_enabled_at, new_match_last_window_on FROM saved_searches;
   -- can anything be released? decidable new Properties of the last 7 days
   SELECT count(*) AS new_active,
          count(*) FILTER (WHERE ms.percentile_evaluated_at IS NOT NULL
                             AND NULLIF(btrim(ms.meta->'deal_verdict'->>'verdict'), '') IS NOT NULL) AS decidable
   FROM properties p LEFT JOIN metrics_scoring ms ON ms.property_id = p.id
   WHERE p.active AND p.first_seen >= now() - interval '7 days';
   ```
   The beat schedule is checked in the beat container log: both `match-saved-search-new-matches` and `send-saved-search-new-match-alerts` appear after the rebuild. Invoking the matcher once by hand inside a worker container is safe (it sends nothing): `celery -A adapters.queue.tasks call tasks.match_saved_search_new_matches` queues one run; the worker log then shows `saved_search_new_match_run` with `searches: 0` while no search is switched on.

## Notes / Follow-ups

- **`held` is not per search.** It counts every new active Property that is not decidable, because a Property cannot be tested against `min_score` or the percentile cap before it is decidable. The line in the email says so (`os que corresponderem a esta busca`).
- **A Property whose enrichment never completes stays held for good.** It is never alerted early and never given up on; `held_overdue` and the warning log are the signal. Nothing re-enqueues it from here. The count also includes Properties that enrichment skips on purpose (the photo gate), which can never become decidable, so `held_overdue` does not return to zero by itself.
- **Editing the filters of a notifying search does not move the floor.** Properties created since the search was enabled that match the new filters and were not matched before are recorded on the next run and arrive in one email. Switching the search off and on starts a new floor.
- **Matches recorded while the search was on are withdrawn when it is switched off before the window.** They do not come back if it is switched on again: the new floor is later than their `first_seen`.
- **A pending row of a deleted search stays `pending` for good.** It is never emailed (no search to send for) and the digest does not exclude it. It is one small row per Property; nothing cleans it up.
- **`min_price_drop` is stored and read by nothing.** Reais, absolute, non-negative, no default. Story 1.10 adds the drop rule and the email that states it.
- **The timestamps assume a UTC database session.** `first_seen` is the server's `now()` and the floor is naive UTC from the application, as in Story 1.6. The primary and the test stack run `TimeZone=UTC`.
- **The warning `saved_search_new_match_held_overdue` repeats on every matcher run** while something is overdue (96 times a day at the default cadence). It describes a state, not an event.
- **A long gap in enrichment releases a backlog, 20 homes per search per day.** This is a product behaviour, stated here so it can be changed.
  - There is no age limit on a match. When verdicts arrive after a gap, every Property created since the search was switched on that matches it is recorded.
  - One email per search per local day carries at most `alerts.new_match.max_items_per_email` (20) of them, the oldest first: by the moment the match was recorded, then by the Property's `first_seen` (a backlog is usually recorded by one run, so in practice the oldest Property goes first). The newest homes of a backlog therefore arrive last.
  - The email says how many are still waiting: `+N nesta busca chegam no próximo aviso.`
  - The rest stay `pending` and leave on the following days. 1,234 waiting matches (the typical search, one week of gap) are 62 daily emails.
  - To change it: raise `max_items_per_email` (`IMOVEIS_ALERTS__NEW_MATCH__MAX_ITEMS_PER_EMAIL` on a host) for bigger emails, or switch the search off and on to discard the backlog and start from now. Sending the newest first, or skipping a backlog older than some age, would be a code change and a product decision; neither is implemented.
- **The search row is locked only while the sender claims the day**, not while the email is sent (review pass 3). The SMTP timeout of 30 seconds applies to each step of the mail conversation, so one send can take longer than 30 seconds in total; nothing waits for it.
- **A search deleted while its email is being sent.** The email leaves. Its rows are kept with no search (`saved_search_id` NULL) and stay `pending`, so the weekly digest may list one of those homes again. Same state as the next note; it needs a delete inside the seconds of a send.
- **`accepts_pets=false` on the list endpoint means "not known to accept pets"**: the exact complement of `accepts_pets=true`, so it keeps a Property whose Listing says no and one that says nothing. Two of the three scrapers (QuintoAndar, Zap) store only "accepts" or nothing, so "says no" exists for OLX alone; a filter on the explicit no would list OLX homes only. Nothing in the application sends `false`: the filter bar sends the parameter only when ticked, and a saved search drops a `false`. Stated in `docs/api.md`.
- **The beat tasks share the `scrapers` queue with scraping.** With a long scrape backlog (about 10,400 queued on the primary on 2026-10-08) a matcher or sender run waits its turn; several queued sender runs then start close together, which is what the row lock is for. How late they run on the primary was not measured.
- **The email notifier has no TLS.** `send_new_matches`, like `send_batch` and `send_digest` before it, opens `smtplib.SMTP` and calls `login` without `starttls()`; there is no config key for it. A provider that requires TLS refuses the login, the send raises and the matches stay pending. Predates this story (deferred in the spec).
- **A row withdrawn because its Property was inactive at the window does not come back** when the Property is reactivated.
- **Matches wait without an age limit while no email can be sent** (no channel, mail server down). The first successful send carries them all, and the digest leaves them out meanwhile.
- **The digest's own selection is otherwise untouched.** It still has no `active` filter and still compares `first_seen` with an aware timestamp.
- **`price-drop` email methods still swallow SMTP errors.** Only `send_new_matches` raises; `send_batch` and `send_digest` log and return, as before.
- **Peer percentiles drift between full recalculations** (Story 1.6 notes). A match under a percentile cap is decided on the value stored when the Property became decidable.
- **The stored date uses the timezone in force when the email was sent.** Changing `window_timezone` can make one search due twice, or not at all, on the day of the change.
- **Mail settings are not validated at startup.** An empty `alerts.digest_email` makes every send fail (`ValueError`), which keeps rows pending and counts an error per hour.
- **BUG (High), fixed in review pass 2**: the `accepts_pets` list filter applied the jsonb `?` operator to `properties.props_json`, which is `json`, so `GET /properties?accepts_pets=true` (and `false`) was a 500 on Postgres and a notifying search with the filter failed on every matcher run. It predated this story. The predicate now casts the amenities value to `jsonb` and wraps it in `COALESCE(..., false)`, so a Property without an `amenities` key counts as "not known to accept pets" in the negated form. Regression test on Postgres (`test_accepts_pets_runs_on_postgres_for_the_list_and_the_matcher`) and a parity row; verified read-only on the primary (see Measured on the primary).
- **BUG (Medium), fixed in review pass 3**: the sender kept the saved search's row lock from before the email was sent until its rows were marked, so `PATCH /saved-searches/<id>` and `DELETE` waited for the mail server (30 seconds per step of the SMTP conversation against a server that does not answer). Introduced in review pass 2 with the one-sender-per-search lock. Confirmed on Postgres before the fix: an `UPDATE` of the search from a second connection during the send ended in `lock timeout`. The sender now claims the day in a short transaction, sends with no lock held and marks afterwards. Regression tests: `test_search_can_be_edited_while_its_email_is_being_sent`, `test_search_deleted_while_its_email_is_being_sent`, `test_failed_send_gives_the_day_back_as_it_was`.
- **BUG (Low), fixed in review pass 3**: matches recorded by one matcher run share one `matched_at`, and the email order fell back to the Property id, so "oldest first" was arbitrary inside a backlog. The order is now `matched_at`, then `first_seen`. Regression test: `test_matches_recorded_by_one_run_leave_oldest_property_first`.
- **BUG (Medium), fixed in review pass 2**: `evaluate_watchlist_alerts` built `PriceDropAlert(title=...)`, a field the dataclass does not have. Confirmed by running the task path in a unit test: `TypeError` on the first watchlist entry whose drop reaches its threshold, before any notifier ran. The argument is gone; `test_watchlist_alert_task.py` is the regression test. It predated this story. Checked in review pass 3: the alert carries every field the three notifiers read (`property_id`, `old_price`, `new_price`, `drop_pct`, `platform`, `listing_type`); none of them reads a title. Left as found, outside this story: the task takes the cheapest Listing of the Property whether it is active or not, and a Listing without a price would fail the comparison.
- **No Property has received a verdict on the primary since 2026-08-13** (see Measured on the primary). Until enrichment runs for new Properties, every new match stays held and no email leaves.
