# UI follow-ups — dashboard plurals and the shared bottom strip

> Feature branch: `feat/v0.14-s1.11-ui-follow-ups` · Story: `v0.14-s1.11` · Status: implemented

## Problem

Two follow-ups recorded by `v0.13-s2.6` (`docs/features/v0.13-s2.6-ui-contract-debt.md`) were
still open. This story closes both.

1. **`v0.13-fu12` — dashboard counts did not agree with their nouns.** The dashboard interpolated
   a count into a fixed plural, so one queued Property read `✔ 1 enfileirados para
   enriquecimento` in pt-BR, one photo-gated Property read `1 bloqueados pelo filtro de fotos`,
   and the Ollama line dodged the question with `1 modelo(s) carregado(s)`.
2. **`v0.13-fu13` — the toast stack and the compare bar shared the bottom of the viewport by
   luck.** The stack was right-anchored and the bar centred, and they stayed apart only at the
   1280×720 viewport the e2e suite uses. In a narrower window a toast could cover the compare bar
   and, sitting at `z-index: 9999`, take its clicks for the 4 s it was up.

## Approach

- **Every live dashboard count key is a `…One` / `…Many` pair, selected with `n === 1` at the
  call site.** It is the convention the catalogs already use (`properties.compareSelectedOne`),
  so there is no new plural mechanism and `frontend/src/i18n/index.ts` is unchanged. Zero selects
  `…Many`.
- **Two counts in one sentence get two pairs.** The enrich-missing line carries a queued count
  and a skipped count. The skipped part became its own pair, `enrichSkippedNoImages{One,Many}`,
  passed into `enrichResultOkSkipped{One,Many}` as `{skipNote}`; each count picks its own form.
  Four keys for the cross product would have been the alternative.
- **Dead copy is deleted, not split.** `rerunWouldQueue` and `rerunQueued` were named by no call
  site in `frontend/src`, so they were removed from both catalogs.
- **Two keys beyond the five in the follow-up note.** `verbQueued` renders in the same sentence
  as `rerunSkipPhotoGate` (`Enfileirados 1 (…)`), and `modelsLoaded` was the `(s)` dodge the note
  named. Both are split. In `en` a pair may hold the same text twice (`Queued`).
- **The sharing rule: the compare bar owns the bottom strip.** While `.compare-bar` is in the
  document the toast stack starts above it (`bar bottom + bar height + 8px`); otherwise it rests
  on the 16px inset. It is one rule at every width, in `frontend/src/index.css`:

  ```css
  :root { --toast-stack-bottom: 16px; --compare-bar-bottom: 24px; --compare-bar-height: 57px; }
  :root:has(.compare-bar) {
    --toast-stack-bottom: calc(var(--compare-bar-bottom) + var(--compare-bar-height) + 8px);
  }
  ```

  Why not a breakpoint: the bar is content-sized and its width depends on the locale, so any
  pixel threshold repeats the luck the follow-up was filed for. `:has()` keeps `ToastProvider`
  and the Properties page ignorant of each other — neither imports or measures the other.
- **The bar's height is a token so the offset is arithmetic.** `--compare-bar-height` is 57px,
  the bar's measured natural height, so the bar does not visibly change. The bar also gets
  `max-width: calc(100vw - 32px)` and keeps its content on one line; the stack's width is clamped
  to `min(380px, 100vw - 32px)`.
- **Rejected as the sharing mechanism:** a width clamp on the toast (no room is left beside a
  centred bar below about 700px; the stack's own `max-width` above only keeps it inside the
  viewport); moving the compare bar (three compare specs and muscle memory pin it); an offset
  measured by the page and pushed into the provider (couples the app-root provider to one page).
- **The e2e measures real boxes.** The narrow-viewport cases assert the 8px gap between the
  stack and the bar, which pins the offset, and that the count and both buttons lie inside the
  bar's box, which pins the height token against the content it was measured from.

## How to Test

1. The gate covers both halves:
   ```bash
   python scripts/agent/validate.py --tier frontend
   ```
   The catalog pins and the retired-key guard run in the unit step; the result lines and the
   bottom strip run in the Playwright step.
2. Manual, plurals (pt-BR): on the Dashboard, run `Enriquecer pendentes` when exactly one
   Property is pending — the line reads `✔ 1 enfileirado para enriquecimento`. With one Ollama
   model loaded the services card reads `1 modelo carregado`.
3. Manual, bottom strip: narrow the window to about 900px, open `/properties`, enter Compare
   mode, select four Properties and click a fifth twice. The two warnings sit above the compare
   bar, and `Limpar seleção` and `Abrir comparação` respond while they are up. Open a Property: the same holds
   over the detail panel. Leave Compare mode and raise a toast (a failing CSV export): it rests
   16px above the bottom edge, right-aligned.

## Notes / Follow-ups

- **Closes `v0.13-fu12` and `v0.13-fu13`.** The tracking keys in `sprint-status.yaml` are moved by
  the orchestrator, not by this change.
- **Toasts now sit higher on `/properties` whenever the compare bar is up, at every width**,
  including 1280px, where they used to rest on the bottom inset beside the bar. That is the rule,
  not a side effect: one position per state instead of one that depends on the window.
- **Below about 460px the bar is narrower than its content.** The bar is capped at the viewport
  width less 32px and keeps its content on one line, and its pt-BR content with four selected is
  about 428px wide, so in a window narrower than that the buttons overflow the bar's right edge.
  Before this change the bar itself ran off both sides of such a window. The narrowest width the
  e2e covers is 640px; the product is desktop-only (EXPERIENCE.md). Recorded as a deferred
  finding in the story spec; no ledger entry covers it yet.
- **BUG (Low)**: the Dashboard e2e cases never mocked `GET /api/system/alerts` (`fetchAlerts`;
  the common mock matched `/api/alerts**` only), so Vite proxied the read to whatever listens on
  `API_PORT` — fixed here by a mock in `installCommonMocks`. The suite still has no catch-all
  that fails a test on an unmocked `/api` call, so the same leak can recur; recorded as a
  deferred finding in the story spec.
- **A toast can sit over the lower right of the detail panel** for the 4 s it is up, as it could
  since the panel shipped; with the compare bar up it now sits 65px higher. The rule defined here
  is toast against compare bar only. Recorded as a deferred finding.
- **DESIGN.md is not edited.** Its toast line still says only "never covers the filter bar". The
  sharing rule is recorded here, in the `index.css` comment block and in the e2e header; carrying
  it into the UX contract is a planning-artifact edit, recorded as a deferred finding.
- **`:has()` is required.** Without it the stack stays on the 16px inset and the old overlap
  returns. Every current evergreen browser supports it; the app has no other browser target.
- **Scraper Control count strings are untouched** (`scraper.activeProgress`, `scraper.logCounts`):
  outside this story.
- **Not changed, as before:** toasts keep their type-coded colours (no DESIGN tokens), there is
  no `desfazer` action and no dismiss API; the save-search dialog, the compare view (DW-55) and
  focus under the detail scrim (DW-57) are as they were. DW-55 and DW-57 stay open. The dialog is
  now under test with toasts up: its overlay dims the compare bar without unmounting it, so the
  stack keeps its place above the bar and does not touch the centred dialog.
- **The `(s)` guard is narrow.** `test_no_catalog_value_dodges_agreement` only rejects a literal
  `(s)` / `(es)` in a catalog value. Like the other catalog tests it cannot tell that a
  noun ought to agree with its count; only the split and the call-site selection do that.
