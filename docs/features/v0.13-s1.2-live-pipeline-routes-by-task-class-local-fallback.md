# Live pipeline routes by task class with local fallback — one routing authority, cloud degrades to local

> Feature branch: `feat/v0.13-s1.2-live-pipeline-routes-by-task-class-local-fallback` · Story: `v0.13-s1.2` · Status: implemented

## Problem

Story 1.1 added the per-task-class `ai.enrichment_routing` map and validated it, but nothing consumed it. The live Celery `ai`-queue pipeline built one client from the scalar `cfg.ai.backend` and passed it uniformly to every task class (`tasks.ai_enrich`, `tasks.embed_property`), so incremental enrichment could not route per task class, and there was no single authority deciding cloud-vs-local (degrading to local when cloud is unavailable). A map that routed visual/sentiment/deal_verdict to different local backends would have been silently ignored.

## Approach

- **One routing authority in `adapters.ai.client`.** `resolve_enrichment_backend(task_class, cfg, *, for_backfill=False)` maps a task class → concrete backend from `cfg.ai.enrichment_routing`. The map wins for *local* values; a *cloud* value (`gemini`/`gemma`) is honored only in `for_backfill` mode when a key is present, otherwise it degrades to the operator's validated-local scalar `cfg.ai.backend` (warning logged, never a failure — NFR-4). The live path always runs with `for_backfill=False`, so it never executes cloud (AD-13/AD-4).
- **`RoutingAIClient` dispatches per task class.** It builds one underlying local client per *distinct* resolved backend (default all-`ollama` config builds exactly one client and behaves like today's single `OllamaClient`) and routes `analyze_visuals`/`analyze_text`/`summarize_deal`/`embed` to the VISUAL/SENTIMENT/DEAL_VERDICT/EMBEDDING client respectively. It composes each underlying client's `session_context()` via `AsyncExitStack`. `run_enrichment`/`_write_deal_verdict`/`analyze_visual_and_sentiment` signatures are untouched — they still receive one `client` that happens to dispatch.
- **Factories.** `_build_local_client(backend, cfg)` extracts the ollama/lmstudio construction formerly inline in `create_ai_client`. `create_ai_client(task_class=…)` resolves a **local** client for a given task class (never the cloud branch); the no-arg scalar behavior — including the defensive cloud branch — is unchanged. `create_enrichment_client(cfg=None, task_classes=…)` returns a `RoutingAIClient` (default trio visual+sentiment+deal_verdict).
- **Live wiring.** `ai_enrich` builds `create_enrichment_client(cfg, task_classes=<stage set>)` via a stage→task-classes map (`all`→visual+sentiment+deal_verdict, `visual+sentiment`→visual+sentiment, `verdict_only`→deal_verdict). `embed_property` uses `create_ai_client(task_class=EMBEDDING)`.
- **1.2 ↔ 1.3 boundary.** The `for_backfill` resolver branch is delivered and unit-tested here but **not** wired into the runner — that is story 1.3. `backfill_runner.py` and `backfill_gemma.py` are untouched, keeping 1.2 ∥ 1.3 conflict-free.

## How to Test

1. Automated:
   ```bash
   bash scripts/agent/validate.sh fast    # lint + unit (test_ai_routing.py + test_ai_enrich_stages.py)
   ```
2. AI-client-change gate:
   ```bash
   bash scripts/agent/validate-ai.sh      # golden pass (or CI-safe skip if Ollama unreachable)
   ```
3. Manual sanity:
   - Default config routes every task class to `ollama`, so `create_enrichment_client(cfg)._clients` has exactly one client.
   - Set `ai.enrichment_routing.visual: gemma` (with `ai.backend: ollama`) → `resolve_enrichment_backend(VISUAL, cfg)` returns `ollama` (degrade, warning logged); with `for_backfill=True` and a `GEMINI_API_KEY` set it returns `gemma`.
