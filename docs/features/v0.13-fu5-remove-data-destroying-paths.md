# Remove data-destroying paths from dev scripts

> Feature branch: `feat/v0.13-fu5-remove-data-destroying-paths` · Story: `v0.13-fu5-remove-data-destroying-paths` · Status: implemented

## Problem

Two convenience dev scripts could wipe the primary stack's named volumes with a single flag, no
confirmation, and no TTY check:

| Command | Destroyed |
|---|---|
| `scripts/stop.sh --volumes` | `imoveis_postgres_data`, `imoveis_redis_data`, `imoveis_image_store` |
| `scripts/clean.sh --volumes` | same — **zero prompts** |
| `scripts/clean.sh --all` | same + images (prompted only about *images*, while silently implying volume loss) |

Both ran `compose_cmd down -v`, which resolves to the **primary** project (`-p "$COMPOSE_PROJECT_NAME"`).
Those volumes hold the entire scraped corpus (~26k properties), all AI-enrichment work (a multi-day
Gemma backfill), every downloaded photo (~6.5k property image dirs), and the backfill's Redis
checkpoint/budget state. That is days of scraping and enrichment behind one mistyped flag — an
unacceptable blast radius for a script named "stop".

This is the same class of hazard BIN-60 addressed by making volume deletion *opt-in*; experience since
then (repeated accidental stack teardowns during parallel agent sessions) shows opt-in is still too easy
to hit. The capability is now removed outright.

## Approach

- **`stop.sh`**: takes no flags at all. Any argument fails closed with an explanation. Always
  `compose_cmd down` — containers stop, volumes always survive.
- **`clean.sh`**: `--volumes` removed; `--all` no longer implies volume loss. `--all` still removes local
  images and prunes build cache — those are rebuildable in minutes, so the blast radius is time, not data.
- **Fail closed, loudly.** `--volumes` errors (exit 1) rather than silently no-op'ing. A silent no-op
  would be worse: the operator would believe data was wiped, or a stale wrapper script would "pass".
  The refusal message prints the deliberate manual procedure (`docker volume rm imoveis_…`) for the rare
  case where destruction is genuinely intended.
- **Left intentionally untouched** (audited, already correct):
  - `scripts/agent/test-stack.sh` — `down -v` on the ephemeral `<workspace>-test` project, asserted
    `!=` primary. Throwaway volumes by design; this is how validation cleans up.
  - `scripts/agent/teardown.sh` — `down -v` only in its non-primary branch; it refuses the primary
    project outright without `--primary`, and refuses `--volumes` on primary unconditionally.
  - `scripts/agent/docker-cleanup.sh` — already documents and honours "never `docker volume rm` /
    `system prune --volumes`".

None.

## How to Test

```bash
bash scripts/agent/validate.sh backend
```

The regression suite asserts, for both scripts: no non-comment `down -v` / `--volumes`, no direct
`docker volume rm` outside the quoted manual procedure, `--volumes` exits non-zero with an explanation,
and `clean.sh --all` still removes images while preserving volumes.

Verified the tests genuinely catch the original defect: running the `_DOWN_V` matcher against
`origin/main:scripts/stop.sh` matches `compose_cmd down -v` (i.e. they fail before this fix).

Manual:

```bash
bash scripts/stop.sh --volumes   # exits 1, explains, deletes nothing
bash scripts/clean.sh --volumes  # exits 1, explains, deletes nothing
```

## Notes / Follow-ups

- Plain `stop.sh` / `clean.sh` still run `docker compose down`, which **stops** postgres/redis. That
  destroys no data, but it *will* interrupt a running backfill. To stop only app services while a
  backfill runs:
  `docker compose --env-file .env.local stop api worker_ai worker_scraper beat`.
- Possible follow-up: have `stop.sh` / `clean.sh` warn (or require `--force`) when the backfill
  heartbeat key `backfill:gemma:active` is alive, mirroring the guard `migrate-primary.sh` already uses.
  Not done here to keep this change strictly about *data destruction*.
- `scripts/agent/run-services.sh` with no arguments rebuilds the whole stack including postgres —
  disruptive to a running backfill (not destructive). Naming services avoids it.
