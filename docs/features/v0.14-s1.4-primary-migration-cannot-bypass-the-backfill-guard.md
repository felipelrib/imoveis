# Primary migration cannot bypass the backfill guard — `start.sh` stops migrating the primary, and `migrate-primary.sh` finds the runner's keys wherever they are configured

> Feature branch: `feat/v0.14-s1.4-primary-migration-cannot-bypass-the-backfill-guard` · Story: `v0.14-s1.4` · Status: implemented

## Problem

Migrating the primary `realestate` database is meant to be one explicit operator step, `bash scripts/agent/migrate-primary.sh`, which excludes itself from a running cloud backfill: it takes a migration lock in Redis, then refuses while the runner's heartbeat is alive. Two doors went around it.

- **DW-32.** `scripts/start.sh` ran `alembic upgrade head` in the `api` container of whatever compose project it started. On the primary project that is the primary database, with no lock and no heartbeat probe. Starting the stack after a pull that carried a migration would run DDL under a live backfill. Story 1.5 found the corpus-repair migration applied to the primary this way, without anyone choosing to apply it.
- **DW-8.** `migrate-primary.sh` talked to `localhost:${REDIS_PORT}` db 0 and used two literal key names. The runner takes its endpoint from `REDIS_URL` and its key names from `backfill.redis_prefix`. With a non-default value on either, the two sides wrote into different keyspaces: neither saw the other's key and both proceeded. The only test connecting them pinned the default prefix.

## Approach

- **`start.sh` refuses and points; it does not delegate.** On the primary project it runs no `upgrade`, `downgrade` or `stamp`. It reads the schema state, prints one line when the schema is at head, and warns with both revisions and `bash scripts/agent/migrate-primary.sh` when a migration is pending. The stack starts and the exit code is 0 either way. Delegating would make "start the stack" migrate the primary whenever nothing happened to be running; the decision stays with the operator, at the cost of one extra command after a pull that carries a migration.
- **"Primary" has one definition.** It is the compose project named `${PRIMARY_COMPOSE_PROJECT:-imoveis}`, the definition `migrate-primary.sh` already used. A checkout without `.env.local` resolves to `imoveis` (the default in `scripts/lib.sh`), so it is primary. `start.sh` compares the name as Compose resolves it: lower case, only `a-z0-9_-`, so a differently spelled primary is still the primary; and an empty name (`COMPOSE_PROJECT_NAME=` in `.env.local`) counts as the primary, because `docker compose -p ""` falls back to the directory name, which in the primary checkout is `imoveis`. `migrate-primary.sh` still compares the `.env.local` value exactly, so `start.sh` can only treat more checkouts as primary than that script accepts, never fewer.
- **Isolated projects keep migrating.** A compose project with another name owns its own Postgres volume and cannot reach the primary database. `migrate-primary.sh` refuses such a checkout, so removing the step there would leave it with no migration path. That branch is one function, `migrate_isolated_project`, and holds the only schema-changing alembic call in the file.
- **The schema check is read-only.** It runs in the `api` container and compares the rows of `alembic_version` with the heads of the migration scripts in the image. It creates nothing. When the table is missing it reports the database as `none`. When the check cannot answer, the state is reported as unknown, with the same command. When the database holds a revision the checkout's migrations do not contain (the database is newer than the code, or another branch migrated it), it says so and does not point at the migration step, because no migration from that checkout applies.
- **The hand-run `stamp head` advice is gone**, on every project.
- **`migrate-primary.sh` follows the runner.** It resolves the Redis endpoint and the key prefix once, through `infra.config.load_config()` (`cfg.redis.url`, `cfg.backfill.redis_prefix`), after sourcing `.env.local`, which is the runner's own environment file. Keys are `<prefix>:migrating` and `<prefix>:active`. Every client is built with `redis.Redis.from_url`. The runner side (`src/core/backfill_runner.py`, `scripts/dev/backfill_gemma.py`, `src/infra/config.py`) is unchanged: it is the reference.
- **Fail closed.** If the resolution raises, or the prefix is empty, the script refuses before any Redis call, for a real run and for `--dry-run`. It does not fall back to the old defaults.
- **`REDIS_PORT` is no longer an input.** The runner never reads it. When it disagrees with the runner's endpoint the script follows the runner and prints a warning.
- **The Redis URL is never printed.** It can carry a password. It is exported once as `GUARD_REDIS_URL` for the script's own Python snippets; log lines show `host:port/db`. A URL the Redis client cannot parse (a password with an unencoded `/`, `?` or `#`) is refused at the resolution step in the script's own words, because the parser's message quotes part of the password.
- **Every existing property of the guard is unchanged:** lock before the heartbeat probe, `SET NX EX` with a per-invocation token, renewal and release by token compare-and-swap, a dry run that writes nothing, an unreachable Redis that refuses. The script never deletes `<prefix>:active`, and removes `<prefix>:migrating` only through the compare-and-swap of its own token.

### Audit of `scripts/*.sh` against the primary stack

Read on 2026-10-08. The question for each helper: can it change the primary schema or data, outside `migrate-primary.sh`?

|---|---|---|
| `scripts/start.sh` | `up -d --build`; before this story also `alembic upgrade head` | Fixed here (DW-32) |
| `scripts/setup.sh` | Creates `.env.local` from the template when it is missing, installs frontend deps, calls `start.sh` | None after this story |

| `scripts/dev.sh` | `start.sh --no-frontend`, then Vite in the foreground | None after this story |
| `scripts/stop.sh` | `down`; `--volumes` was removed in v0.13-fu5 and now exits with a message | None; volumes are kept |
| `scripts/clean.sh` | `down`, or `down --rmi local --remove-orphans` plus `docker builder prune -f` with `--all` | None; volumes are kept |
| `scripts/test.sh` | `run --rm api python -m pytest …` in the checkout's own `api` container | See the finding below |
| `scripts/install-backfill-runner.sh` | Installs, removes or reports the systemd unit of the backfill runner | None |
| `scripts/install-backfill-runner.ps1`, `scripts/windows/backfill_host.py` | Install and host the backfill runner on Windows; the runner writes enrichment rows through the app's own write path | No schema change; no migration call |

## How to Test

1. The gate (the harness tier is selected because `scripts/` changed):
   ```bash
   python scripts/agent/validate.py
   ```
2. The two test files alone, while developing (about 4 minutes on the Windows host):
   ```bash
   python -m pytest src/tests/unit/test_migrate_primary_guard.py src/tests/unit/test_migrate_primary_only_path.py -q -o addopts=
   ```
   Both files use doubles only: a fake `redis` module, a stub `alembic` package, and stub `docker` / `curl` executables. Neither opens a connection to a real Redis, database or Docker daemon. The `start.sh` tests refuse to run unless `docker` resolves to the stub.
3. On the primary checkout, read-only, to confirm the resolution on the real host:
   ```bash
   bash scripts/agent/migrate-primary.sh --dry-run
   ```
   Expected: the first guard line names the primary Redis as `host:port/db`, both keys are reported under the configured prefix (`backfill:gemma` unless overridden), no `REDIS_PORT` warning, exit 0. It writes nothing.

What the tests prove:

- On the primary project, at head, pending or unreadable, `start.sh` issues no Docker command containing `alembic upgrade`, `downgrade` or `stamp`, starts the stack, and exits 0. On an isolated project it issues exactly one `alembic upgrade head`, for that project.
- A new one-line `alembic upgrade|downgrade|stamp` invocation (or `command.upgrade(...)`) in `scripts/`, `.claude/hooks/`, `deploy/`, a root compose file or a root Dockerfile fails the scan, which names the file and line. The allowlist is `migrate-primary.sh`, `validate.py` (ephemeral test database) and one call inside `migrate_isolated_project`. The scan and the two static script checks are plain Python and carry no `harness` mark, so they run in every gate tier above `docs`, including after a change that touches only a Dockerfile or a compose file.
- With `REDIS_URL=redis://localhost:6379/7` and `IMOVEIS_BACKFILL__REDIS_PREFIX=backfill:alt`: the script's lock and probe land at db 7 under `backfill:alt`; the runner's `MigrationGate`, built from `get_redis()` and `get_config()`, reports a migration in progress while alembic runs and names the script's token; a heartbeat written by the runner's `Heartbeat.beat()` makes the script refuse with "heartbeat is ALIVE"; nothing is written at db 0 or under `backfill:gemma`.
- An unresolvable configuration (a `REDIS_URL` that does not parse, or an empty prefix) refuses with no Redis call, for real and dry runs.
- No run issues a `delete`, and every compare-and-swap carries the invocation's own token.
- The read-only schema check is executed for real against a SQLite file: no version table and an empty one give `pending:none-><head>`, the head gives `current`, the revision below it gives `pending:<below>-><head>`, an unknown revision gives `foreign:<rev>-><head>`, and the database file is byte-identical afterwards.
- The same program, run against the gate's PostgreSQL after `alembic upgrade head`, answers `current` and leaves `alembic_version` as it was (integration suite).
- A project name Compose would normalize to the primary name (`Imoveis`, `imoveis.`) is treated as the primary, and so is an empty name. A database revision the checkout does not contain is reported as such, without the pointer to `migrate-primary.sh`.
- A config that fails validation refuses with the field and the message and with `input_value=<hidden>`. A password that breaks the Redis URL (set through `REDIS_URL` or `IMOVEIS_REDIS__PASSWORD`) refuses with no Redis call and no part of the password in the output, for real and dry runs.
- One run resolves the config from the throwaway checkout's own `src` and `configs`, so the script's own `PYTHONPATH` lines are exercised.
- The real redis-py client, built the script's way and the runner's way from one URL, addresses the same host, port, db and password (no connection is opened).

The tests of the first pass were written first and failed against the scripts as they were (10 in each file). The tests added after review were checked the same way where a mutation applies; see the spec's review log.

## Notes / Follow-ups

- **A fresh install now needs one more command.** `setup.sh` no longer leaves the primary database migrated. `start.sh` reports the schema as behind (`none` → head) and `setup.sh` prints the step. The API container runs against an empty schema until `migrate-primary.sh` has been run.
- **A port-remapped primary needs `REDIS_URL`.** Before, the script followed `REDIS_PORT` and the runner did not, so on such a host they disagreed silently. Now the script follows the runner and warns. If `.env.local` sets `REDIS_PORT` to something other than 6379 without a matching `REDIS_URL`, the script reaches the runner's endpoint, finds no Redis there and refuses. `.env.local.example` already says `REDIS_URL` is needed in that case.
- **The script needs the app's Python dependencies.** The resolution imports `infra.config` (pydantic, PyYAML). The project `.venv`, which the script already prefers, has them. With a bare system Python the script now refuses at the resolution step instead of at `import redis`.
- **The resolution reason is printed on failure, without values.** It is the exception type and message from the config loader, cut to 300 characters, with every `input_value=…` the validator quotes replaced by `<hidden>`. A plain parse error (`ValueError` from reading `REDIS_URL` or `DATABASE_URL`) is cut at its first quote, since what follows is a piece of the value. A validation message that names a bad value in its own text (for example an unknown backend name) still shows that one value.
- **The real scripts were not run for this story.** The primary stack is live on the development host, so `start.sh` and `migrate-primary.sh` were exercised only through the doubles. Step 3 above is the read-only check on the real host.
- **The read-only schema check has not run inside the `api` container.** The program is executed against SQLite (five database states) and against the gate's PostgreSQL at head, with the host interpreter and the same `psycopg2` the image pins, and every answer is covered through the stub on the shell side. What has not run is the delivery: the program piped through `docker compose run --rm -T api python -` into the image. If that fails, `start.sh` reports the state as unknown and still points at `migrate-primary.sh`; it never migrates.
- **A primary spelled differently has no migration path until it is renamed.** With `COMPOSE_PROJECT_NAME=Imoveis` (reachable only through the Compose v1 fallback; Compose v2 rejects the name) or an empty name, `start.sh` reports and points at `migrate-primary.sh`, which refuses a `.env.local` that does not name the primary exactly (an empty name it accepts). The refusal names the project; the fix is the spelling in `.env.local`. The `.env.local` check of `migrate-primary.sh` is outside this story.
- **`PRIMARY_COMPOSE_PROJECT` redefines the primary for both scripts.** It is a seam the tests and `scripts/ops/docker-cleanup-lib.sh` use; nothing sets it on a host. Exporting it with another name while the stack runs as `imoveis` makes `start.sh` treat `imoveis` as an isolated project and migrate it.
- **Audit finding — `scripts/test.sh integration|e2e|all` on the primary project** runs the integration suite in the primary `api` container, whose `DATABASE_URL` is the primary database. `src/tests/db_isolation.py` refuses that database unless `IMOVEIS_ALLOW_PRIMARY_DB_WIPE=1` is set, so the expected result is a refusal, not a wipe. This was read, not run. The supported way to run those suites is `validate.py`, on the ephemeral stack. Not changed here.
- **Audit finding — `stop.sh`, `restart.sh` and `clean.sh` take the primary containers down without looking at the backfill heartbeat.** A host-side runner loses Postgres and Redis in the middle of a pass. No schema or data is changed and volumes are kept. `clean.sh --all` also prunes the host-wide Docker build cache. Not changed here.
- **Same resolution, not the same process.** The script resolves from its shell environment plus `$REPO_ROOT/.env.local`. A runner installed with another env file (`--env-file`), or started by hand from a shell with different exports, resolves from something else, and the script cannot see that. The script prints the endpoint and both key names on every run; compare them with `backfill_gemma.py --status` when the runner is not started from `.env.local`. Recorded as a deferred finding.
- **The scan is a tripwire.** It reads one line at a time in `scripts/`, `.claude/hooks/`, `deploy/` and the root compose files and Dockerfiles. A command split over several lines, an aliased import of `alembic.command`, or application code under `src/` is outside it.
- **The behavioural tests are `harness`-marked.** They run when `scripts/`, `.claude/` or the `test_migrate*` files change and in the full tier. A forced `--tier backend` run does not include them (gate behaviour that predates this story; recorded as a deferred finding).
- **Unrelated test file touched: `src/tests/unit/test_windows_backfill_host.py`.** Three of its test functions (8 cases) hand the real checkout to the Windows backfill host, which refuses a linked git worktree by design. The harness gate was therefore red in every story worktree, whatever the story changed. They are now skipped in a linked worktree and run as before from the primary checkout. Making them run everywhere (a fixture checkout, as the rest of that file uses) is recorded as a deferred finding.
- **Not addressed: DW-9.** The heartbeat is beaten per completed row, so one slow enrichment can let it lapse under a live writer. The lock taken before the probe still stops a runner that starts during the upgrade.
- **Not addressed: a missing `.env.local` in `migrate-primary.sh`.** The script still runs on defaults there (open ledger finding from v0.13 story 2.7).
- Related: DW-8 and DW-32 (resolved in the ledger by this story), DW-3 / DW-4 (the guard itself, v0.13-fu6), Story 1.5 (how the corpus repair reached the primary), Story 1.6 (gated on this story).
